Lesson 0005

Serving State: Projection Tables, Redis, and Staleness Contracts

The fifth mental model: fast read paths are built from deliberately stale copies. The engineering skill is to say which copy is authoritative, which copy is expendable, how stale it may be, and how you prove it is healthy.

Mission link: this is the practical layer behind dashboard APIs, Redis-backed materialized views, PostgreSQL read models, cache hit rates, backfills, and production claims about low-latency reads.

Where This Fits

Lesson 0004 explained how a stream processor turns replayable facts into state. This lesson starts at the serving boundary: how does an API read that derived state quickly without pretending every copy is source truth?

Keep Reference 0005: Serving State, Cache, and Projection Checklist nearby. It is the compressed checklist for this lesson.

Concise Answers From Lesson 0004

  1. Subscription then merchant: key by subscription first to dedupe, order lifecycle changes, and compute a delta; key by merchant second to aggregate all deltas for one dashboard owner.
  2. Per-subscription state: store the last version, status, plan, quantity, price, and event ID; avoid storing unbounded event history inside the stream job.
  3. Processing vs event time: processing time is acceptable when wall-clock worker behavior is the product behavior; event time is required when the business fact's timestamp determines the result.
  4. Watermark delay: it trades freshness for tolerance of late and out-of-order events.
  5. Redis write twice: checkpoint recovery restores internal state and source position, but an external sink write may have already happened before the failed checkpoint completed.
  6. Freshness metrics: distinguish Kafka lag and event age from watermark lag, window age, projection update age, and reconciliation drift.

The Big Idea

A production read path is often a chain of copies. The billing database owns subscription truth. Kafka owns replayable facts. A stream job owns derived computation. A PostgreSQL projection table or materialized view owns query-shaped serving rows. Redis owns hot, expendable copies for low-latency reads.

The key word is owns. Each layer owns a different job. When teams get into trouble, they usually blur those jobs: a cache becomes the only place a value exists, a projection has no rebuild path, or a dashboard says "real time" without an age metric.

Serving-state shape:

request write
  -> source-of-truth database transaction
  -> outbox event
  -> Kafka topic
  -> stream processor
  -> projection table or materialized view
  -> Redis cache for hot reads
  -> dashboard API with freshness metadata

PostgreSQL's materialized view docs describe stored query results that can be refreshed from their defining query, with the important caveat that the stored result may not be current. Redis's cache docs frame cache entries as copies of persistent data that can be evicted and recached. Those two ideas are the heart of this lesson: derived state is useful because it is not the source, but it must be honest about that fact.

Scenario: Merchant Dashboard Reads

Suppose the product needs a merchant dashboard that loads in under 150 ms and shows current MRR, active subscriptions, failed payments, and usage spikes. Computing that directly from normalized billing tables on every request would be slow, expensive, and easy to overload during traffic spikes.

A stronger design separates truth, projection, and cache:

Truthsubscriptions, invoices, and committed billing events.
ComputeStream job turns subscription facts into merchant-level metrics.
Projectmerchant_dashboard_summary stores query-shaped rows.
Cachedash:{merchant_id} stores hot JSON with TTL.
ServeAPI returns data plus as_of and freshness status.

The dashboard API is now fast because it reads one shaped object, not dozens of source tables. But correctness is preserved because the shaped object is still derived. If it looks wrong, you can trace back to source facts and rebuild it.

Three Serving-State Shapes

Do not reduce everything to "use Redis." Redis is a tool inside a serving strategy. The strategy usually combines durable projections and volatile caches.

Shape Use when Production contract
Projection table The app needs durable, query-shaped rows maintained incrementally. Upserts are idempotent, versioned, indexed, observable, and rebuildable.
PostgreSQL materialized view A stored query result can be refreshed periodically from its definition. Readers accept refresh lag; refresh cost and locking behavior are understood.
Redis cache Hot reads need lower latency or the backing store needs load relief. Values are expendable; misses, expiry, eviction, and Redis failure are planned.

PostgreSQL lets you refresh a materialized view, and the CONCURRENTLY option can avoid locking out concurrent selects when its requirements are met. That is useful, but it is still a refresh model. A projection table maintained by stream events is a different model: it changes incrementally as facts arrive.

Projection Tables: Durable Derived State

A projection table is not just a denormalized table. It is a contract: this row answers this read path, was derived from these source facts, and can be corrected or rebuilt.

Minimal projection row:

merchant_dashboard_summary
  merchant_id          primary key
  current_mrr_cents    integer
  active_subscriptions integer
  failed_payment_count integer
  source_version       bigint
  as_of_event_time     timestamp
  updated_at           timestamp

The version fields matter. If a replayed old event tries to write source_version = 41 after the projection already has source_version = 43, the update should be rejected or ignored. Without a guard, replay can move the dashboard backward.

A projection table should have an answer for four questions: What source facts produced this row? What version or timestamp prevents stale overwrites? How can this row be rebuilt? How do we detect drift from source truth?

Redis: Volatile Acceleration

Redis is commonly useful because memory access and simple data structures make hot reads fast. The danger is forgetting the word cache. A cache should usually be safe to lose. Redis's eviction docs explicitly discuss removing keys when memory limits are reached, and its INFO stats include keyspace_hits, keyspace_misses, and evicted_keys for checking cache behavior.

A simple cache-aside read path looks like this:

GET dash:{merchant_id} from Redis
if hit:
  return cached JSON
if miss:
  read merchant_dashboard_summary from PostgreSQL
  SET dash:{merchant_id} JSON EX 30
  return JSON

The EXPIRE command sets a timeout after which a key is deleted. TTL gives you a maximum stale duration if the value is not actively invalidated sooner. TTL is not a correctness proof by itself. It is a bounded-risk tool.

Choice What it buys What it costs
Short TTL Less stale data after missed invalidations. More misses and more backing-store load.
Long TTL Higher hit rate and lower backing-store load. Stale data lasts longer after source changes.
Event invalidation Values can be removed or updated soon after a fact changes. The invalidation path itself can fail or arrive out of order.
Versioned value Older writers cannot overwrite newer derived state. Every writer and reader must preserve the version contract.

Staleness Is a Product Contract

Instead of saying "real time," name the contract. A merchant dashboard might be allowed to show MRR that is up to 30 seconds old. A checkout authorization screen may require a fresh source read. A fraud decision may use a stale feature cache if the model was designed for that staleness.

The contract should be visible in both code and telemetry:

  1. Freshness budget: maximum age the product accepts, such as 30 seconds.
  2. Served timestamp: include as_of_event_time or projection_updated_at.
  3. Fallback behavior: decide whether to serve stale, bypass cache, read source, or return degraded status.
  4. Alert threshold: alert on user-visible freshness breach, not merely one delayed internal job.

Google's SRE guidance is useful here because serving-state health is still service health: watch latency, traffic, errors, and saturation. For derived state, add projection age, cache hit rate, evictions, miss bursts, hot keys, and reconciliation drift.

Failure Matrix

Failure Weak design Stronger design
Redis loses keys Dashboard breaks because Redis was the only copy. API reloads from projection table and repopulates cache.
Hot key expires Hundreds of requests recompute the same value at once. Use request coalescing, jittered TTLs, stale-while-refresh, or prewarming.
Stream job lags API keeps serving old data with no visible warning. Response includes as_of; alerts fire on projection age breach.
Replay writes old events Old state overwrites newer dashboard values. Projection updates require increasing version or newer event time.
Materialized view refresh blocks Readers stall during a large refresh. Use the right refresh mode, indexes, schedule, or an incremental projection table.
Projection drift Team notices only after a customer reports wrong numbers. Reconciliation compares source truth and derived totals continuously or on schedule.

How to Defend the Resume Bullet

Suppose someone asks: "How did your real-time dashboard stay fast and correct?" A strong answer separates source truth, projection, cache, freshness, and recovery.

Strong answer shape:

  1. Billing facts were committed to the source database and emitted through the outbox into Kafka.
  2. A stream job computed merchant-level deltas and wrote a durable projection table shaped for dashboard reads.
  3. Projection writes were idempotent and guarded by event version or event time to survive replay and backfill.
  4. The API used Redis for hot dashboard objects, but Redis was treated as expendable acceleration, not source truth.
  5. Cache entries had TTLs and could be invalidated or overwritten from new projection versions.
  6. Responses exposed as_of metadata, and alerts watched projection age, hit rate, evictions, latency, errors, and drift.
  7. Rebuilds replayed retained facts into a controlled target before cutover, with side effects disabled.

Reflection Questions

No homework is required. These are the checks that show whether you can reason about serving state:

  1. For a merchant dashboard, why might you keep both a PostgreSQL projection table and a Redis cache?
  2. What user-visible promise is stronger: "real time" or "MRR is usually under 30 seconds old"? Why?
  3. What can go wrong if a replayed event updates a projection without a version guard?
  4. When should an API bypass Redis and read from source or projection directly?
  5. Which metrics would you put on a dashboard for cache health and projection freshness?
  6. How would you rebuild the dashboard projection without emailing users or triggering partner webhooks?

Ask follow-up questions about any unclear piece. Useful debugging questions here are: "What is source truth?", "What is derived?", "How stale may it be?", "Can this cache disappear?", and "What proves the user saw fresh-enough data?"
