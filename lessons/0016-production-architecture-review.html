Lesson 0016

Production Architecture Review

The sixteenth mental model: senior backend design is not naming enough tools. It is making explicit claims, backing them with mechanisms, testing the failure modes, and knowing which evidence would prove the system is working.

Mission link: this is the review script for defending resume-style systems across APIs, databases, events, streams, caches, deployments, observability, SLOs, and incidents.

Where This Fits

Lesson 0015 taught how to respond when the user promise is already burning. This lesson moves earlier: how do you review a design before launch, before an interview deep dive, or after a postmortem action item changes the architecture?

Keep Reference 0016: Production Architecture Review nearby. It is the compact checklist for this lesson.

Concise Answers From Lesson 0015

  1. Incidents are coordination problems: responders must coordinate decisions, production changes, communication, evidence, and handoff.
  2. Declare before root cause: user impact, fast burn, multi-team work, or prolonged uncertainty is enough.
  3. Mitigate before curiosity: stop user harm while diagnosis continues.
  4. Track live state: roles, impact, timeline, hypotheses, actions, owners, and next update time belong in the incident document.
  5. Rollback is partial: it can stop new harm while leaving lag, bad data, or cleanup work behind.
  6. Postmortems must change systems: useful action items have an owner, priority, concrete change, and verification signal.

The Big Idea

A production architecture review should turn a diagram into testable engineering claims. "We use Kafka" is not a claim. "Subscription lifecycle events are ordered by subscription ID, replayable for 30 days, and consumed idempotently into the revenue projection" is a claim. It can be tested, broken, monitored, and defended.

Designing Data-Intensive Applications is the backbone source here because it repeatedly asks what guarantees a system provides around storage, replication, partitioning, transactions, and derived data. The AWS Well-Architected Reliability Pillar is the operational companion: design for failure, test recovery, manage change, and make workloads resilient. The Google SRE chapters on Service Level Objectives and Effective Troubleshooting turn the same review into user promises and evidence paths.

Review loop:

claim
  -> mechanism
  -> invariant
  -> failure mode
  -> control
  -> evidence
  -> owner

The trap is reviewing boxes instead of promises. A diagram tells you where components sit. A review tells you what must remain true when traffic spikes, messages duplicate, schemas change, caches go stale, queries slow down, rollouts fail, and people respond under pressure.

Scenario: Revenue Platform Launch Review

Suppose you are reviewing a subscription revenue platform before launching to larger merchants. The system accepts subscription changes through an API, commits ledger facts in PostgreSQL, publishes outbox events to Kafka, computes projections in Flink, stores serving state in Redis and PostgreSQL projection tables, and exposes merchant dashboards.

APICommands, idempotency, deadlines.
PostgresFacts, constraints, transactions.
KafkaOrdering, retention, replay.
FlinkState, time, checkpoints.
ServingFreshness, cache, projection.

A shallow review asks whether each component exists. A useful review asks whether the design survives the specific pressures implied by the product promise: duplicate writes, hot tenants, late events, slow queries, stale dashboards, bad deploys, and recovery after a failed stream sink.

Step 1: Start With Promises and Claims

Review from the user journey inward. For each critical journey, state the product promise, then state the architecture claim that supports it. If the claim is vague, the design cannot be defended yet.

User promise Architecture claim Evidence you need
Subscription changes commit safely. Each intended command creates at most one durable ledger fact. Idempotency table behavior, unique constraints, transaction boundary, retry tests.
Dashboard data is fresh enough. Projection age stays under five minutes for 99.5% of dashboard views. Freshness SLI, Redis key age, stream lag age, sink latency, burn alerts.
Analytics can be repaired. Events can be replayed into projection state without double-counting. Replay runbook, deterministic aggregation, checkpoint behavior, idempotent sinks.
Releases do not silently corrupt state. Schema and rollout changes are compatible across old and new workers. Compatibility tests, canary coverage, rollback path, migration plan.

This is where SLO thinking from Lesson 0014 matters. A review without a user promise becomes a component inventory. A review with promises can prioritize which failures deserve the most design effort.

Step 2: Walk State, Time, and Ownership

Most hard backend failures are failures of state, time, or ownership. Something became true in one place but not another. Something happened twice, late, out of order, or before a consumer was ready. Something had no clear owner when repair was needed.

State: What is the source of truth? Which derived states can drift? What invariant belongs in the database instead of only in application code?

Time: What ordering is required? What can arrive late? What can be replayed? What freshness does the user actually need?

Ownership: Who owns schema compatibility, DLQs, replay, backfills, SLO alerts, runbooks, and cleanup after temporary mitigations?

For the revenue platform, the ledger may be source of truth for accepted billing facts, Kafka may be the replayable history for downstream projection, Flink may hold checkpointed derived state, and Redis may hold fast but rebuildable serving state. Those are different kinds of memory. Reviewing them as if they were interchangeable hides the real risk.

Step 3: Force Failure Modes Into the Open

A good review asks "what breaks this?" before production does. Tie each failure mode to a control and an evidence signal.

Failure mode Control Evidence
Client retries duplicate a subscription command. Idempotency key, unique constraint, safe response replay. Duplicate-request test and idempotency conflict metric.
Outbox publisher crashes after database commit. Durable outbox row, polling publisher, retry with ownership. Outbox age, publish lag, stuck-row alert.
One merchant creates a hot partition. Partitioning review, per-tenant throttles, skew dashboard. Lag and processing time by partition and tenant cohort.
Redis serves stale projection state. Freshness timestamp, stale label, rebuild path, bounded TTL. View freshness SLI and stale-response count.
Deployment changes event shape unsafely. Backward-compatible schema, canary, rollback, dual-read period. Consumer error rate, DLQ count, canary SLO status.
Database backfill saturates production. Bounded batches, lock monitoring, pause switch, off-peak rollout. WAL rate, lock waits, replica lag, user latency.

Step 4: Review the Evidence Path

Architecture is not production-ready until operators can tell whether the claims are holding. The evidence path should connect user symptoms to component causes without guessing.

Evidence chain for stale dashboards:

dashboard freshness SLI burns
  -> affected merchants and response freshness timestamps
  -> Redis key age and miss rate
  -> projection table update age and query latency
  -> Flink sink latency, checkpoint duration, backpressure
  -> Kafka lag age by partition
  -> outbox publish lag and recent deploy history

This is the same discipline used in incidents, but a review asks for it before the page. If no signal would distinguish Redis staleness from Flink backpressure from PostgreSQL lock waits, the system is not merely under-instrumented; it is hard to operate.

Step 5: Make the Design Defensible

When someone challenges the architecture, answer with the review loop rather than a tool list. State the claim, the mechanism, the known tradeoff, and the signal that proves it works.

Weak answer: "We used Kafka, Flink, Redis, and Kubernetes for scalability."

Strong answer: "We separated durable billing facts from derived dashboard state. PostgreSQL enforced accepted ledger invariants; outbox events made publication retryable; Kafka gave replayable ordered histories by subscription; Flink maintained checkpointed projections; Redis served low-latency reads with freshness timestamps. The main tradeoff was eventual consistency, so we made freshness user-visible, alerted on freshness burn, and kept replay and rebuild paths for repair."

Notice the shape: every tool is attached to a problem, every guarantee has a boundary, and every tradeoff has an operational signal.

Reflection Questions

No homework is required. These are the checks that show whether you can review a production design rather than just describe it:

  1. Pick one claim in the revenue platform and name its mechanism, invariant, failure mode, control, evidence, and owner.
  2. Why is "Kafka makes it scalable" weaker than an ordering and replay claim?
  3. Which states are source-of-truth, derived-but-durable, and cache-only in the scenario?
  4. What evidence would distinguish a stale Redis cache from a slow Flink sink?
  5. What rollout or schema question would you ask before launching the design?
  6. How would you turn the strong answer shape into a resume-bullet defense?

Concise answer key: a strong claim names a user promise and the mechanism that protects it; Kafka needs explicit ordering, retention, replay, partition, and consumer semantics; ledger facts are source-of-truth, projections are derived durable state, and Redis is fast rebuildable serving state; Redis key age, projection update age, sink latency, checkpoint duration, and lag age separate likely causes; rollout review should ask about compatibility, canaries, rollback, and mixed-version behavior; resume defense should connect problem, mechanism, tradeoff, metrics, and recovery path.

Ask follow-up questions about any unclear piece. Useful review questions here are: "What exactly is the claim?", "Where is the invariant enforced?", "What would falsify this?", "What signal proves it is healthy?", and "Who owns repair when it breaks?"
