Real-Time Metrics Platform Design Drill

The nineteenth mental model: a real-time metrics system is not a faster batch job. It is a derived-data contract with explicit metric semantics, event ordering, stateful recovery, serving freshness, and correctness evidence.

Mission link: this is the design defense behind delivering sub-30s MRR and churn metrics for 1M+ merchant accounts using Kafka, Flink, Redis, and production SLOs.

The Big Idea

A real-time metrics platform maintains derived data. The product promise is not "we used Flink." The product promise is closer to: "For each merchant, dashboard MRR and churn reflect accepted billing lifecycle facts within 30 seconds, with known correction behavior and a repair path."

Kafka's design documentation frames logs as partitioned, ordered histories where consumers track offsets and can rewind for replay. Flink's stateful stream processing docs explain that stateful operators remember information across events, and its checkpointing model combines stream replay with state snapshots for recovery. Google's SRE SLO chapter is the operational anchor: choose indicators that represent what users actually care about.

Derived-data contract:

metric definition
  -> accepted source facts
  -> ordered event history
  -> stateful aggregation
  -> materialized serving state
  -> freshness and correctness SLOs
  -> replay, audit, and repair path

The trap is starting with the pipeline diagram. Start with the metric contract. If "churn" means different things to product, finance, support, and engineering, low latency only makes the wrong answer arrive faster.

Step 1: Define the Metric Before the Pipeline

Metric semantics are part of the system design. MRR and churn are business concepts that need engineering definitions precise enough to implement, test, replay, and explain.

Question Why it matters Contract example
What fact changes MRR? Prevents support notes, retries, or partial attempts from changing revenue. Only accepted subscription lifecycle facts update metric state.
What counts as churn? Separates cancellation intent, failed payment, grace period, and actual lost revenue. Churn starts when the subscription reaches a terminal unpaid or canceled state.
Which time matters? Event time and processing time answer different questions during lag and backfill. Business reporting uses effective event time; freshness uses processing time.
How are corrections handled? Real systems receive reversals, late events, manual fixes, and schema changes. Corrections emit new facts and recompute affected subscription and merchant state.

This is where senior judgment shows up early. Before debating partitions or Redis TTLs, force the product promise into a metric contract that can survive retries, late events, replays, and support escalations.

Step 2: Name the Ordering Boundary

Kafka gives order within a partition, not global order across the whole company. A billing lifecycle pipeline should say which entity needs ordered transitions. If subscription state changes must be interpreted in order, the event key should preserve order for that subscription. If merchant aggregates are the serving target, the stream may need a second keyed aggregation by merchant.

Two-stage shape: first normalize and dedupe subscription lifecycle facts keyed by subscription ID; then aggregate merchant metrics keyed by merchant ID.

Why: subscription ordering protects state-machine correctness, while merchant keying puts all merchant-level metric updates in the place that owns the merchant aggregate.

The design decision is not "partition by merchant" or "partition by subscription" in the abstract. It is: what must be sequential for correctness, what must be colocated for aggregation, and where will repartitioning cost, skew, and failure recovery appear?

Step 3: Treat Stream State as Recoverable Memory

A Flink operator can keep per-subscription state, per-merchant aggregate state, timers, watermarks, and correction metadata. That state is valuable because it prevents every dashboard read from re-scanning the billing ledger. It is risky because bugs, late events, and sink failures can preserve the wrong answer quickly.

Flink's checkpointing documentation says state needs checkpoints so recovery can restore state and stream positions with failure-free semantics. The practical design question is what happens at the sink boundary: did the Redis or database write happen once, twice, or not at all after a failure?

Risk Control Evidence
Duplicate event after replay changes totals twice. Event ID dedupe, versioned state update, idempotent sink write. Replay test, duplicate count, aggregate checksum.
Late correction arrives after dashboard state moved forward. Correction event contract, bounded lateness policy, affected-key recompute. Correction age, recompute count, audit diff size.
Checkpoint recovery replays records already written to Redis. Upsert by metric key and version, not blind increments. Sink idempotency test and version conflict metric.
Hot merchant creates skew and lag. Skew detection, split aggregate strategy, tenant throttles, capacity review. Lag age by key cohort and task busy time.

Exactly-once processing is a system-level claim, not a magic adjective. You defend it by explaining the source offsets, checkpointed state, sink behavior, and what the system does when replay crosses an external side effect.

Step 4: Materialize for Reads Without Moving Truth

Redis can make dashboard reads fast, but it should not become the only place where metric truth exists. Treat it as a serving projection with a freshness timestamp, source version, and rebuild path.

The Redis eviction docs describe cache entries as copies of persistently stored data and expose hit/miss and eviction signals through runtime info. The Redis EXPIRE command attaches timeouts so keys can be automatically deleted. For this platform, TTLs and eviction are serving controls, not correctness mechanisms.

Metric read response:

{
  "merchant_id": "m_123",
  "mrr_cents": 8120000,
  "churned_subscriptions_30d": 41,
  "computed_at": "2026-06-30T14:03:22Z",
  "source_watermark": "2026-06-30T14:03:10Z",
  "pipeline_version": "billing-metrics-v7"
}

Those extra fields make staleness observable. A dashboard, support tool, or on-call engineer can tell whether the answer is fresh, stale, rebuilding, or from an old pipeline version.

Step 5: Make Freshness and Correctness Separate

Fresh and wrong is not success. Correct and one day late may also fail the product. Define both.

Promise Useful SLI Likely alert or review
Dashboard freshness Age of metric response at read time. Page if P99 freshness exceeds 30s for active merchants.
Pipeline progress Event-time watermark lag and Kafka lag age. Ticket on sustained lag before user freshness burns.
Metric correctness Diff against authoritative batch or ledger audit. Block rollout if sampled merchant diffs exceed tolerance.
Recovery readiness Time to replay or rebuild affected merchant projections. Review after replay drill or incident repair miss.
Serving health Redis hit rate, key age, eviction count, API P95. Alert only when it threatens the user promise.

Google's SRE framing matters here: pick a few indicators that represent real user needs. For a real-time metrics platform, freshness, correctness, and availability usually matter more than whether every internal component has a green dashboard.

Step 6: Defend the Resume Bullet

If someone asks how you delivered sub-30s MRR and churn metrics, avoid reciting technology names. Make the derived-data contract explicit.

Weak answer: "We used Kafka, Flink, and Redis to make metrics real time."

Strong answer: "We first made MRR and churn precise enough to compute from accepted billing lifecycle facts, including effective time and correction behavior. Kafka carried replayable events keyed to preserve subscription ordering, then Flink maintained subscription and merchant aggregate state with checkpoints. Redis served merchant metrics as a materialized read model, but every value included computed-at, watermark, and pipeline-version metadata so stale answers were visible. The main tradeoff was eventual consistency, so we separated freshness SLOs from correctness audits, tracked lag age, checkpoint health, sink idempotency, Redis hit rate, and batch-vs-stream diffs, and kept replay and rebuild runbooks for repair."

That answer is defensible because it connects product semantics, distributed systems mechanics, tradeoffs, and evidence.

Reflection Questions

No homework is required. These are the checks that show whether you can defend a real-time derived-data system rather than list tools:

  1. What exact fact changes MRR, and what fact changes churn?
  2. Which entity needs ordered events, and which entity owns the final aggregate?
  3. Why is a Redis materialization not the source of truth?
  4. How can the pipeline be fresh but wrong?
  5. What evidence would you show after a replay to prove metrics were repaired?
  6. How would you answer if someone challenged "exactly once" at the Redis sink boundary?

Concise answer key: only accepted billing lifecycle facts should change metrics; subscription ID often protects lifecycle ordering while merchant ID owns the aggregate; Redis is a fast projection that can be evicted, stale, or rebuilt; fresh-but-wrong happens when the stream quickly applies bad semantics, duplicates, missed corrections, or schema mistakes; replay repair needs audit diffs, checksums, affected-key counts, freshness recovery, and sink conflict metrics; exactly-once defense must name source offsets, checkpointed state, idempotent or transactional sink behavior, and replay tests.

Ask follow-up questions about any unclear piece. Useful review questions here are: "What does this metric mean?", "Where is the ordering boundary?", "Can this side effect replay safely?", "How stale is this answer?", and "What proves the derived state matches truth?"
