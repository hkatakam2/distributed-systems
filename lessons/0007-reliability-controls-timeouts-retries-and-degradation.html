Lesson 0007

Reliability Controls: Timeouts, Retries, Backoff, and Degradation

The seventh mental model: reliability controls are pressure valves. They bound how long work waits, decide which failures deserve another attempt, isolate scarce capacity, and preserve the most important user promise when a dependency is sick.

Mission link: this is the practical layer behind production incident mitigation, SLO defense, retry-safe APIs, dependency failure design, cascading failure prevention, and backend answers that show operational judgment.

Where This Fits

Lesson 0006 showed how to detect and debug slow, stale, or wrong behavior across a distributed path. This lesson asks the next production question: once a boundary is slow or failing, what should the system do?

Keep Reference 0007: Reliability Controls Checklist nearby. It is the compressed decision sheet for this lesson.

Concise Answers From Lesson 0006

  1. Freshness breach versus nonzero lag: freshness breach is user-visible and measurable; some lag may be normal or harmless.
  2. Slow dashboard evidence: metrics show rate and severity, traces show where time went, logs identify the affected request or version, and domain checks prove whether the result was fresh and correct.
  3. Broken async trace context: you lose the causal link from user action to event, consumer update, projection write, and later read.
  4. Projection log fields: include trace ID, request ID, event ID, merchant ID, source version, partition, offset, update result, and as-of timestamp.
  5. Fast 200 but wrong MRR: compare source truth to the projection, inspect replay/version guards, check cache version, and look for drift.
  6. Early mitigation: rollback a bad deploy, bypass a sick cache, serve a degraded response, pause a dangerous consumer, or route reads to a safer source.

The Big Idea

A distributed system fails badly when callers keep waiting, retrying, and queueing after the useful deadline has already passed. The right move is not "always retry." The right move is to decide what each boundary is allowed to spend, repeat, reject, isolate, or degrade.

The gRPC deadline guide frames deadlines as the point after which a client no longer wants the result. AWS guidance on retry with backoff, jitter, and circuit breakers adds the production control layer. Google's SRE chapter on handling overload is the broader operating model: protect the service and preserve the most important work.

Reliability-control path:

dashboard request budget: 150 ms
  -> Redis lookup budget: 15 ms, no retry, fallback to projection
  -> projection DB budget: 60 ms, one safe retry for transient error
  -> analytics enrichment budget: 25 ms, circuit breaker, optional
  -> response: core dashboard now, degraded enrichment if needed
  -> telemetry: timeout, retry, breaker, pool, and degraded-response metrics

The engineering skill is to make the failure behavior explicit before the incident. Otherwise the default behavior becomes unbounded waiting, synchronized retries, shared-pool exhaustion, and mystery partial failures.

Scenario: Dashboard Depends on Three Boundaries

Suppose the merchant dashboard from earlier lessons reads a Redis cache, falls back to a PostgreSQL projection, and calls a recommendation service for optional "next best action" cards. The user contract is under 150 ms and the core MRR numbers must be fresh enough to trust.

Request150 ms total user-visible deadline.
RedisFast path, tiny timeout, no retry.
ProjectionDurable fallback, bounded retry if safe.
RecommendOptional feature, circuit breaker.
RespondCore dashboard, clear degraded state.

If Redis is slow, waiting 500 ms is already a bug because the request deadline is 150 ms. If the recommendation service is down, failing the whole dashboard is also a bug because that feature is optional. Reliability design starts by naming which parts are critical and which can degrade.

Deadlines: Stop Spending After Value Expires

A timeout says how long one operation may wait. A deadline says when the overall result stops being useful. Deadlines are stronger because every downstream call can receive the remaining budget instead of inventing its own local wait time.

Budget split example:

total dashboard deadline = 150 ms
gateway and auth          = 20 ms
application logic         = 25 ms
Redis cache lookup        = 15 ms
projection read           = 60 ms
optional enrichment       = 25 ms
response overhead         = 5 ms

Deadlines also make cancellation meaningful. If a caller has gone away or the deadline is exceeded, continuing expensive work can hurt other users. The service should stop work it no longer needs, release the resource, and record the timeout as a signal.

Retries: Repeat Only When It Helps

A retry is a bet: the first attempt failed because of a transient condition, and another attempt can succeed before the user's deadline expires. That bet is often reasonable for connection resets, temporary 503s, or leader changes. It is dangerous for non-idempotent writes, long-running operations, and overloaded dependencies.

Retry question Good answer Bad answer
Is duplicate execution safe? Idempotency key, event ID, version guard, or read-only operation. "Probably fine" for a charge, email, or partner webhook.
Is there enough time left? Retry only if the remaining deadline can cover another attempt. Retry after the user-visible deadline has already passed.
How many attempts? Small bounded count or retry budget. Unbounded loop hidden inside every client.
Where should retries live? At the layer with context about idempotency and user value. At every layer, multiplying one request into many attempts.

Connect this back to Lesson 0002: write retries require a contract that makes duplicate intent harmless. Without that contract, retrying can turn a temporary network failure into duplicate business side effects.

Backoff and Jitter: Avoid Retry Storms

When many clients fail at once, immediate retries can become the outage. Backoff waits longer after repeated failures. Jitter adds randomness so clients do not all retry on the same schedule.

bad retry behavior
  t=0 ms: 10,000 clients fail
  t=1 ms: 10,000 clients retry together
  t=2 ms: 10,000 clients retry together again

better retry behavior
  t=0 ms: 10,000 clients fail
  t=20-80 ms: first retry attempts spread out
  t=80-250 ms: later attempts spread out more
  stop when retry budget or deadline is exhausted

Backoff and jitter are not politeness. They reduce correlated pressure, improve recovery chances, and make overload visible instead of hiding it behind waves of client traffic.

Circuit Breakers: Fail Fast While Recovery Happens

A circuit breaker is useful when a dependency is clearly failing or too slow. Instead of sending every request into a known-bad path, the breaker opens and fails fast or returns a fallback. After a delay, it allows limited probe traffic to see whether the dependency has recovered.

State Behavior Dashboard example
Closed Calls flow normally while errors and latency stay acceptable. Recommendation service enriches the dashboard.
Open Calls fail fast or use fallback because the dependency is unhealthy. Dashboard omits recommendations instead of waiting.
Half-open Small probe traffic tests whether normal calls can resume. A few recommendation calls are allowed and measured.

Breakers are not a substitute for fixing the dependency. They are a containment device. Instrument state changes, open duration, fallback rate, and user-visible impact.

Bulkheads and Load Shedding: Contain the Blast Radius

The bulkhead pattern isolates capacity so one path cannot consume everything. In backend systems, that usually means separate connection pools, worker pools, queues, or concurrency limits for critical versus optional work, tenants, or dependencies.

Isolation examples:

  1. Separate DB connection pool for checkout writes and dashboard reads.
  2. Separate worker pool for webhook delivery and internal projection updates.
  3. Per-tenant concurrency limits so one large merchant cannot starve everyone.
  4. Queue length and queue age limits so stale work is rejected before it wastes capacity.

Load shedding is the direct version: reject or drop lower-priority work when accepting it would harm more important work. A 503 with a retry hint can be healthier than accepting work that will time out after consuming scarce resources.

Graceful Degradation: Preserve the Core Promise

Graceful degradation means the system returns a smaller or older result that is still honest. It is not silently lying. For the dashboard, useful degradation might mean returning core MRR and subscription counts while omitting recommendations, marking analytics as delayed, or serving a stale-but-labeled summary within a freshness policy.

Failure Weak behavior Stronger behavior
Redis slow Wait until the whole request times out. Timeout quickly and read the projection table.
Projection slow Stack retries until database pressure increases. One bounded safe retry, then serve labeled stale data or fail clearly.
Recommendation down Fail the dashboard because optional cards are missing. Open the breaker and return the core dashboard without cards.
Tenant traffic spike Let one tenant saturate every worker. Enforce tenant limits and protect critical shared work.

How to Defend the Resume Bullet

Suppose someone asks: "How did your backend handle dependency failures without cascading outages?" A strong answer names the user contract, the controls, and the evidence.

Strong answer shape:

  1. We defined a user-visible deadline for the API and passed smaller budgets to downstream calls.
  2. Critical dependencies had explicit timeouts, cancellation, and metrics for deadline exceeded errors.
  3. Retries were limited to idempotent or read-only operations, with bounded attempts and backoff with jitter.
  4. Optional dependencies used circuit breakers and fallback responses so they could not fail the core workflow.
  5. Connection pools, worker pools, and queues were isolated by priority or dependency to prevent shared exhaustion.
  6. Under overload, lower-priority work was shed before it harmed critical requests.
  7. Dashboards tracked timeouts, retry attempts, breaker state, pool saturation, degraded responses, and user-visible latency and errors.

Reflection Questions

No homework is required. These are the checks that show whether you can reason about reliability controls:

  1. Why is a deadline stronger than a local timeout for a chain of service calls?
  2. When is retrying a failed write safe, and when can it create duplicate business effects?
  3. How do backoff and jitter change the shape of traffic after a shared failure?
  4. What should happen when an optional dependency is down but the core dashboard can still be served?
  5. Which resources would you isolate with bulkheads in a billing or dashboard system?
  6. What metrics would tell you that retries are making an outage worse instead of better?

Ask follow-up questions about any unclear piece. Useful reliability questions here are: "What is the user deadline?", "Is this retry safe?", "What should degrade?", "Which pool can saturate?", and "What protects critical work first?"
