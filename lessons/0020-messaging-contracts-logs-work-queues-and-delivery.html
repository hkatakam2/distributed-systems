Lesson 0020

Messaging Contracts: Logs, Work Queues, and Delivery

The twentieth mental model: messaging systems are not interchangeable pipes. A log, a queue, and a command channel make different promises about history, routing, replay, ordering, acknowledgement, and failure ownership.

Mission link: this is the production judgment behind replacing monolithic inventory polling with Kafka for high-throughput inventory streams and RabbitMQ-style queues for SKU update delivery across fulfillment centers.

Where This Fits

Lesson 0019 used Kafka and Flink for derived metrics. This lesson separates two messaging contracts that often get blurred: replayable event history and routed work delivery.

Keep Reference 0020: Messaging Contracts nearby. It is the compact checklist for choosing and defending the right messaging shape.

Concise Answers From Lesson 0019

  1. Metric before topology: define what changes MRR or churn before debating partitions, operators, or Redis keys.
  2. Ordering is scoped: Kafka preserves order within a partition, so choose the key around the entity whose transitions must be sequential.
  3. Stream state is recoverable memory: checkpoints plus replay restore internal state, but external sinks still need idempotent or transactional behavior.
  4. Redis is a projection: it accelerates reads but should expose freshness metadata and remain rebuildable from source facts.
  5. Freshness and correctness differ: a pipeline can be fresh but wrong, or correct but too stale for the product promise.

The Big Idea

When someone says "we used Kafka and RabbitMQ," the senior answer is not a comparison chart of brand names. It is the delivery contract: which messages form a durable history, which messages represent pending work, who can replay, who owns failure, and what proof shows no important update was lost.

Kafka's design documentation frames Kafka around partitioned logs, retained records, consumer positions, and replay. RabbitMQ's AMQP model frames delivery around publishers, exchanges, queues, bindings, routing keys, and consumers. RabbitMQ acknowledgements and publisher confirms then define the handoff points between publisher, broker, and consumer.

Messaging contract questions:

is this durable event history or pending work?
who needs to consume it, once or many times?
what ordering boundary matters?
when is a message safe to acknowledge?
what happens after crash, retry, or poison message?
what signal proves end-to-end delivery and freshness?

The trap is treating "guaranteed delivery" as magic. In production, it usually means at-least-once delivery plus durable publishing, acknowledgements, idempotent handlers, dead-letter ownership, monitoring, and reconciliation.

Scenario: Inventory Sync Across Fulfillment Centers

Suppose each fulfillment center produces inventory changes for SKUs. The old system polls every few minutes and reconciles in bulk. The new requirement is faster sync, lower polling waste, and reliable processing of important SKU updates during peak sale traffic.

A strong dual-messaging design starts with one source fact, one stable update ID, and two different uses of that fact. Kafka is useful when the company needs a replayable stream for projections, analytics, audits, and multiple subscribers. RabbitMQ is useful when a routed unit of work must be assigned, acknowledged, retried, or dead-lettered.

History Versus Work

Kafka and RabbitMQ can both move messages, but they encourage different reasoning. Kafka asks: "What happened, in what partitioned order, and where is each consumer in the log?" RabbitMQ asks: "Which queue should receive this work, which consumer has it, and was it acknowledged after processing?"

Need Log-shaped answer Queue-shaped answer
Many teams need the same facts. Keep retained events in Kafka; each consumer group tracks its own position. Use fanout routing only when each queue owns its copy of the work.
Rebuild a projection from old facts. Replay the log from an offset or timestamp. Queues usually represent pending work, not long-term replay history.
Distribute task execution. Consumers in a group share partitions, but partition count and keys shape parallelism. Competing consumers pull from a queue and acknowledge when work is done.
Route work by type or destination. Use topics and keys, often with more explicit stream topology. Use exchanges, bindings, and routing keys to route messages into queues.
Handle poison messages. Use retry topics, DLQs, pause or skip policies, and replay ownership. Use negative acknowledgements, retry queues, and dead-letter exchanges.

The decision is not "Kafka is for scale, RabbitMQ is for reliability." Both can be reliable when configured and operated correctly. The real decision is whether the product needs replayable event history, routed pending work, or both.

Design the Dual Path Without Split-Brain

Dual messaging is powerful and dangerous. If one publisher writes to Kafka and another writes to RabbitMQ from a different source, the system can disagree about what happened. Keep one source fact and one update identity across both paths.

Safer inventory shape:

inventory transaction commits:
  update_id = "sku_42:fc_9:seq_88401"
  sku_id, fulfillment_center_id, quantity_delta, effective_time

outbox publisher emits the same update_id to:
  Kafka topic: inventory.stock-events
  RabbitMQ exchange: inventory.sku-updates

all consumers:
  dedupe by update_id
  apply idempotent side effects
  report freshness and failures by update_id

This makes Kafka and RabbitMQ two delivery views over the same fact, not two competing truths. If one path lags or fails, reconciliation can compare update IDs and repair the missing side.

Handoff Points Decide Failure Behavior

RabbitMQ's reliability story depends on explicit handoffs. Publisher confirms tell the publisher that the broker has accepted a message under the configured durability path. Consumer acknowledgements tell the broker that the consumer is done with a delivery and it can be removed from the queue. If a consumer crashes before acknowledgement, the broker can redeliver.

Kafka's consumer story is offset-based. A consumer processes records and commits its position. If it commits too early, a crash can lose work. If it commits after processing, a crash can cause reprocessing. That is why idempotent handlers matter in both systems.

Boundary Weak habit Stronger contract
Publisher to broker Fire and forget. Use confirms, retry with idempotent message IDs, and alert on publish failures.
Broker to consumer Acknowledge before side effects. Acknowledge only after durable, idempotent processing completes.
Consumer to database Blindly increment or overwrite. Upsert by SKU and version or dedupe by update ID.
Retry to poison handling Retry forever in the hot path. Use bounded retries, dead-letter exchanges, ownership, and repair tools.

The phrase "guaranteed SKU update delivery" should be translated into a defensible contract: important updates are durably published, delivered at least once, processed idempotently, retried under limits, dead-lettered with ownership, and audited against source facts.

Ordering and Parallelism Are Tradeoffs

Inventory systems usually need per-SKU or per-SKU-per-location ordering, not global ordering. Kafka makes that explicit through partition keys. RabbitMQ queues can preserve simple queue order, but multiple consumers, redeliveries, priorities, and retries can change the practical processing order. If a SKU cannot tolerate out-of-order updates, design the work key and handler around that fact.

Useful rule: order the smallest entity that needs sequential state, then parallelize across independent entities.

For inventory, that often means serializing updates for one SKU at one fulfillment center while allowing different SKUs and locations to process independently.

If ordering is strict, include a monotonically increasing version or sequence in the message and reject stale updates. If ordering is soft, accept out-of-order delivery but make the projection converge by applying versioned upserts rather than blind deltas.

Operate the Contract, Not the Broker Name

Monitoring should match the promise. Kafka lag alone does not prove SKU sync is healthy. RabbitMQ queue depth alone does not prove important updates were applied. Watch the end-to-end age and correctness of the inventory view.

Concern Useful signal Decision it supports
Kafka stream progress Consumer lag age, processing rate, rebalance count, partition skew. Scale consumers, fix hot keys, or reduce per-event work.
RabbitMQ delivery health Ready messages, unacked messages, redeliveries, confirm latency. Add workers, slow publishers, investigate stuck consumers.
Poison messages Dead-letter count, retry age, failure reason, owner queue. Repair data, patch handler, or replay affected updates.
SKU freshness Age from source update to visible projection by SKU and location. Page or degrade when the product promise is breached.
Correctness Reconciliation diff between source facts, Kafka offsets, queue processing, and projection. Find missing updates and prove repair completed.

Defend the Resume Bullet

If someone asks how you replaced polling with Kafka and RabbitMQ, avoid saying "Kafka is fast and RabbitMQ is guaranteed." Explain the contracts and controls.

Strong answer: "Polling was wasting work and adding sync latency, so we moved inventory changes to event-driven delivery. We kept a single source fact with a stable update ID. Kafka carried the high-throughput stock-event history for projections, analytics, replay, and multi-subscriber consumers. RabbitMQ carried routed SKU update work where workers needed explicit acknowledgement, retry, and dead-letter handling. We treated delivery as at-least-once, so handlers deduped by update ID and applied versioned idempotent writes. The main tradeoffs were ordering, retry pressure, and split-brain risk between paths, so we used one outbox source, bounded retries, dead-letter ownership, and reconciliation. We defended the change with source-to-projection freshness, Kafka lag age, queue depth, unacked messages, redelivery rate, DLQ rate, processing latency, and audit diffs."

That answer transfers beyond Kafka and RabbitMQ. The same judgment applies to Pub/Sub plus Cloud Tasks, Pulsar plus SQS, or any design that separates event history from pending work.

Reflection Questions

No homework is required. These are the checks that show whether you can defend a messaging architecture rather than list middleware:

  1. Which inventory messages are durable facts, and which messages are pending work?
  2. What stable update ID would let Kafka consumers, RabbitMQ workers, and reconciliation agree on the same fact?
  3. When is it safe for a RabbitMQ consumer to acknowledge a SKU update?
  4. When is it safe for a Kafka consumer to commit its offset?
  5. How can "guaranteed delivery" still produce duplicate processing?
  6. What signals prove inventory updates are fresh, processed, and repairable?

Concise answer key: durable facts are source inventory changes while pending work is the routed processing task; use one update ID from the source transaction or outbox; acknowledge or commit only after durable idempotent processing; at-least-once delivery can redeliver after crashes, lost acknowledgements, or retries; prove the system with end-to-end freshness, Kafka lag age, RabbitMQ ready and unacked counts, redelivery rate, DLQ rate, processing latency, idempotency conflicts, and reconciliation diffs.

Ask follow-up questions about any unclear piece. Useful review questions here are: "Is this history or work?", "Who can replay?", "When do we acknowledge?", "What happens to poison messages?", and "What proves the update reached the visible inventory view?"
