Lesson 0001

From a Request to a Real-Time Distributed System

The first mental model: a serious backend system is not just an API and a database. It is a chain of decisions about facts, time, state, failure, and operations.

Mission link: this is the base pattern behind resume bullets about high-throughput APIs, event-driven pipelines, Redis materialization, stream processing, retries, reconciliation, and observability.

The Big Picture

Most production backend systems are built around one tension: users want simple fast operations, while the business needs durable correctness under traffic, failure, and change.

At small scale, you can often write request logic like this:

request -> validate -> update database -> return response

At production scale, that shape breaks down. One request may need to update billing state, notify other services, refresh analytics, trigger emails, update search, emit audit history, and expose fresh read models. Doing all of that synchronously makes the request slow and fragile. Doing all of it asynchronously makes correctness harder.

The industry response is to separate accepting facts from reacting to facts.

Production pattern:

request
  -> validate command
  -> commit durable fact
  -> publish event
  -> process event stream
  -> update serving state
  -> observe lag, errors, latency, correctness

For a compact version of this shape, keep Reference 0001: Production Backend System Map open while studying this lesson.

First Principles

1. A request is not a fact yet

A request is an attempt. It can time out, be retried, fail validation, race with another request, or arrive twice. A production system needs a moment where the attempted command becomes a durable business fact.

Example: POST /subscriptions/{id}/cancel is a command. subscription_canceled is a fact. Confusing these creates bugs: downstream systems should usually react to facts, not intentions.

2. The database is not the only useful memory

A relational database is excellent for durable source-of-truth state, constraints, and transactional updates. But the fastest way to answer a high-volume query may be a cache, a denormalized table, a search index, or a stream-built materialized view.

This is why a resume bullet might say "built a Redis materialization layer." Redis is not magic. The deeper idea is: precompute the read shape that the API needs, keep it close to the request path, and accept the burden of keeping it fresh and correct.

3. A log turns time into an engineering tool

An append-only log records events in order within a partition. Systems such as Kafka, Pulsar, Kinesis, and Google Pub/Sub all give engineers a way to decouple producers from consumers and replay work. The log lets you ask: "What happened, in what order, and can I reprocess it?"

Jay Kreps's article on the log as a unifying abstraction is the primary reading for this lesson. Kafka's own documentation is the canonical tool reference.

4. Stream processing is controlled forgetting

A stream processor turns event history into current derived state. It cannot remember everything forever, so it groups by key, keeps state, windows time, checkpoints progress, and defines recovery behavior. Flink, Beam, Spark Structured Streaming, Kafka Streams, and Materialize all make different tradeoffs around these ideas.

Apache Flink's stateful stream processing docs are the primary source for state and checkpoints.

5. Observability is part of the design, not decoration

In a distributed system, the failure is rarely "the system is down." More often, one dependency is slow, one partition is lagging, one consumer is retrying poison messages, one cache key is hot, or one deployment changed a payload contract. Observability is how engineers make invisible distributed behavior inspectable.

The Google SRE chapter on monitoring distributed systems and the OpenTelemetry docs are the sources to return to here.

One Production Scenario

Imagine a billing platform needs real-time monthly recurring revenue and churn metrics for many merchants. A simple batch job computes metrics once a day, but product and operations teams now need updates in under 30 seconds.

The naive answer is "query the database more often." That usually fails because billing state is complex, queries are expensive, and repeated aggregation over many accounts creates load on the source-of-truth database. The production answer is to treat billing changes as a stream of facts and maintain a derived read model.

APISubscription changes enter through controlled commands.
FactBilling lifecycle events are committed durably.
LogEvents are appended to partitioned streams.
ProcessorOperators update per-merchant metrics.
ServingRedis or another low-latency store serves reads.

What the experienced engineer is actually doing

  • Choosing the source of truth for business facts.
  • Defining event schemas and compatibility rules.
  • Partitioning events so ordering is preserved where it matters.
  • Maintaining keyed state for aggregates such as active subscriptions, MRR, and churn.
  • Checkpointing stream progress so failures can resume without corrupting state.
  • Serving precomputed state through a fast read path.
  • Measuring freshness, lag, correctness, latency, and error rate.
  • Building repair paths for missed, duplicated, late, or malformed events.

Design Decisions and Tradeoffs

Decision Common options Tradeoff
Where is truth? Database row, event log, outbox table, ledger Database-first is familiar and transactional. Log-first improves replay and integration but requires stronger event discipline.
How do events leave the service? Direct publish, transactional outbox, CDC, database triggers Direct publish is simple but can lose events around transaction boundaries. Outbox and CDC are more reliable but add moving parts.
How is work distributed? Queue, partitioned log, pub/sub, workflow engine Queues are good for task distribution. Logs are good for replayable ordered histories. Workflow engines are good for long-lived orchestrated state.
How are reads made fast? Cache-aside, write-through cache, materialized view, denormalized table Caches are easy to add but can be stale. Materialized views are intentional and scalable but require repair and freshness monitoring.
What happens on failure? Retry, backoff, DLQ, skip, stop-the-world, reconciliation Retries help transient failures but amplify load. DLQs preserve bad messages but require ownership. Reconciliation repairs drift but may be expensive.
How fresh must state be? Strong read-after-write, bounded staleness, eventual consistency Stronger freshness usually costs coordination, latency, and availability. Bounded staleness is often enough for analytics and dashboards.

How to Defend the Resume Bullet

Suppose someone asks: "How did you get MRR and churn metrics under 30 seconds?" A weak answer names tools. A strong answer explains the system pressure and the tradeoffs.

Strong answer shape:

  1. Start with the user-visible problem: daily batch metrics were too stale for operations.
  2. Explain the source facts: subscription lifecycle and invoice/payment events.
  3. Explain why synchronous computation was rejected: expensive, fragile, and hard to scale under read load.
  4. Explain the architecture: durable event stream, keyed stream processor, checkpointed state, Redis materialized read model.
  5. Explain correctness hazards: duplicates, out-of-order events, late events, schema evolution, replay, and reconciliation.
  6. Explain operations: consumer lag, processing latency, Redis hit rate, P95 API latency, DLQ count, checkpoint failures, and data freshness SLO.

The point is not to pretend every company uses Kafka, Flink, and Redis. The point is to show that you understand why an engineer reaches for a durable log, a stream processor, and a serving projection.

Reflection Questions

No homework is required, but these are the questions that reveal whether you own the material:

  1. For a subscription cancellation, what is the command and what is the durable fact?
  2. What ordering guarantee do you need for billing lifecycle events: global order, merchant order, subscription order, or no order? Why?
  3. If the stream processor crashes after updating Redis but before committing its checkpoint, what can happen after restart?
  4. How would you detect that Redis has drifted from the source of truth?
  5. When would you choose a queue instead of a replayable log?
  6. What metric would page an engineer: API P95 latency, consumer lag, DLQ count, freshness age, or all of them under different SLOs?

Ask follow-up questions about any unclear piece. The fastest path is to interrogate the system: "What fails?", "What is the source of truth?", "What can be retried?", "What can be replayed?", and "What does the user observe?"
