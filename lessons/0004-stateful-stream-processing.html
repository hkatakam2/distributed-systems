Lesson 0004

Stateful Stream Processing: Keys, Time, and Checkpoints

The fourth mental model: a stream processor is a distributed state machine. It reads replayable facts, groups them by key, remembers just enough state, and survives failure by restoring state plus input position.

Mission link: this is the practical core behind Flink jobs, real-time materialized views, MRR projections, inventory availability, backfills, freshness SLOs, and defensible claims about exactly-once processing.

Where This Fits

Lesson 0003 explained how Kafka-style logs scale through partitions, consumer groups, offsets, and replay. This lesson starts after records are consumed: how do you turn an infinite stream of facts into correct, queryable state?

Keep Reference 0004: Stateful Stream Processing Checklist nearby. It is the compressed checklist for this lesson.

Concise Answers From Lesson 0003

  1. Why not global order: subscription lifecycle correctness needs order per subscription, not one expensive order for every unrelated customer.
  2. 12 partitions, 20 consumers: at most 12 consumers actively read that topic inside one group.
  3. Commit before Redis: a crash can make the consumer skip the Redis update forever.
  4. Redis then crash before commit: the event can replay, so the Redis write must be idempotent, versioned, or recomputed.
  5. Hot partition signal: inspect lag, event age, processing time, and top keys per partition, not only average group lag.
  6. Replay side effects: disable or guard emails, payments, webhooks, partner calls, and any irreversible external action.

The Big Idea

Stateless consumers handle one record at a time. Stateful stream processors remember facts across records: the latest subscription version, a running merchant MRR total, a five-minute usage window, or a dedupe set of event IDs.

Flink's stateful stream processing model groups stream records by key, lets operators maintain state, and uses checkpoints for fault tolerance. The important production question is not "are we using Flink?" It is: what state is remembered, what key owns it, what time closes it, and what recovery point proves it can be rebuilt?

Stateful processing shape:

Kafka event stream
  -> assign event time and watermarks
  -> key by the correctness boundary
  -> update local keyed state
  -> emit derived facts or aggregate updates
  -> checkpoint state plus input positions
  -> write idempotent materialized view

Scenario: Build an MRR Projection

Suppose the product needs a fast merchant dashboard showing monthly recurring revenue. The source of truth is still billing state and billing events. Redis or PostgreSQL projection tables are serving state: fast to read, but derived.

A strong pipeline separates two correctness boundaries:

Sourcebilling_events records subscription changes.
SubscriptionKey by subscription_id to dedupe and compute delta.
MerchantRe-key by merchant_id to aggregate MRR.
CheckpointPersist operator state and Kafka positions.
ViewUpsert merchant totals with version or event-time guard.

The first key protects lifecycle correctness for one subscription. The second key groups all deltas that contribute to one merchant's dashboard. Re-keying is a real design move: it changes both the data distribution and the state that each task owns.

Keyed State: Local Memory With a Contract

Keyed state is state scoped to the current record's key. If all events for sub_123 go through the same keyed operator, that operator can remember the last seen version, status, plan, quantity, and price for sub_123. It can then reject duplicates, ignore stale updates, or emit a precise revenue delta.

State choice What it enables What can go wrong
subscription_id state Correct lifecycle deltas and duplicate suppression. A missing version guard can apply old events after new ones.
merchant_id state Fast merchant-level totals for dashboards and alerts. A large merchant can become a hot key with slow updates.
Global state Simple mental model for tiny streams. One bottleneck, weak parallelism, and expensive recovery.
No state Simple event forwarding and filtering. No dedupe, no aggregates, no memory of prior facts.

Good keyed state is deliberately small. Store what the next event needs, not every historical event forever. If state can grow without bound, you need retention, TTL, compaction, snapshots, or a source-of-truth lookup strategy.

Event Time: Time From the Fact, Not the Worker

Processing time is when a worker handles a record. Event time is when the business fact happened. For dashboards and billing, event time is usually the better semantic clock because backlogs, retries, and replays should not move yesterday's cancellation into today's revenue.

Watermarks are how a stream processor tracks progress through event time. A watermark says, roughly: the system believes it has seen events up to this event-time point, with some allowed disorder. When the watermark passes a window boundary, the window can produce a result.

Choice Use when Failure mode
Processing time The wall-clock behavior of the job is the product behavior. Backlogs and replays change the apparent timing of facts.
Event time The business fact's timestamp determines the result. Late and out-of-order events need explicit handling.
Watermark delay You expect bounded out-of-order arrival. Too short drops corrections; too long delays freshness.
Allowed lateness Late events should update already emitted windows. Downstream sinks must tolerate corrected outputs.

This is the tradeoff behind many "real-time" systems: stricter freshness usually means less tolerance for late data; stronger event-time correctness usually means waiting longer or emitting corrections.

Windows: Finite Questions Over Infinite Streams

A stream does not end, so aggregate questions need boundaries. Windows create finite buckets over an unbounded stream. A five-minute usage total, hourly checkout conversion, and daily active merchant count are all windowed questions.

Common window choices:

  1. Tumbling: fixed, non-overlapping buckets such as usage per five minutes.
  2. Sliding: overlapping buckets such as a one-hour error rate refreshed every five minutes.
  3. Session: activity grouped until a period of inactivity, useful for user journeys.

For an MRR total, you may not need a time window at all. A running keyed aggregate can update the current merchant total after each subscription delta. For usage billing or rate metrics, windows are the natural shape because the question itself has a time boundary.

Checkpoints: The Recovery Contract

A checkpoint records the stream processor's state and the input positions that produced that state. After a crash, the job restores the checkpointed state and resumes from the checkpointed input positions. That is why replayable sources and deterministic state updates matter.

Failure path:

checkpoint C1: MRR state = $1000, Kafka offset = 100
process offsets 101..130, write projection = $1120
worker crashes before checkpoint C2 completes
restore C1
replay offsets 101..130
projection write may happen again

The processor can restore its internal state, but external sinks still need a contract. Redis, PostgreSQL, search indexes, and partner APIs do not magically join the processor's checkpoint unless the connector and sink protocol support it. The safe default is idempotent upsert, version checks, event IDs, transactional sink support where available, and reconciliation against source truth.

Operations: What to Watch

Stateful jobs fail differently from stateless consumers. They can be caught up on Kafka while watermark progress is stuck, or they can have healthy watermarks while checkpoints are timing out. Watch the pipeline from source to serving state.

Signal What it tells you Question to ask
Kafka lag and event age Whether source facts are being read promptly. Which partition, key, or dependency is holding progress?
Watermark lag Whether event-time results are fresh. Is one source partition idle or far behind?
Checkpoint duration and failures Whether state can be captured reliably. Is state too large, storage slow, or backpressure severe?
State size Whether memory and recovery cost are growing. Do we need TTL, compaction, or a smaller state model?
Sink latency and failures Whether the materialized view can keep up. Is Redis, PostgreSQL, or the connector the bottleneck?
Projection drift Whether derived state still matches source truth. Can reconciliation explain and repair the difference?

How to Defend the Resume Bullet

Suppose someone asks: "How did the real-time MRR projection stay correct during failures and backfills?" A strong answer names the state, time, checkpoint, sink, and operating model.

Strong answer shape:

  1. Billing facts came from a replayable Kafka topic populated from committed outbox events.
  2. The job first keyed by subscription to dedupe, enforce version order, and compute revenue deltas.
  3. It then keyed by merchant to maintain the current MRR aggregate used by the dashboard.
  4. Event-time timestamps and watermarks controlled time-bounded outputs where the business question needed windows.
  5. Checkpoints captured Flink state and Kafka positions, so crashes restored a known processing point.
  6. The serving sink used idempotent upserts or version guards, because replay after recovery can repeat external writes.
  7. Operations watched lag, watermark progress, checkpoint health, state size, sink latency, and reconciliation drift.

Reflection Questions

No homework is required. These are the checks that show whether you can reason about stateful stream processing:

  1. For an MRR projection, why might the job key by subscription first and merchant second?
  2. What state would you store per subscription, and what would you avoid storing?
  3. When would processing time be acceptable, and when would event time be required?
  4. What does a watermark delay trade off?
  5. Why can an external Redis write happen twice after checkpoint recovery?
  6. Which metrics distinguish "Kafka is caught up" from "the event-time view is fresh"?

Ask follow-up questions about any unclear piece. Useful debugging questions here are: "What is the key?", "What state is owned by that key?", "Which clock drives the result?", "What checkpoint restored?", and "Can the sink tolerate replay?"
