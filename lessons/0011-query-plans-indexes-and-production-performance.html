Lesson 0011

Query Plans, Indexes, and Production Performance

The eleventh mental model: a slow database query is not fixed by saying "add an index." It is fixed by proving how PostgreSQL reaches rows, why that path is expensive, and what production cost the fix adds.

Mission link: this is the judgment behind high-throughput APIs, dashboards, materialized views, idempotency tables, job queues, multitenant data access, and defending a performance improvement beyond "we optimized SQL."

Where This Fits

  2. Duplicate requests: a unique database constraint arbitrates races better than application memory.
  3. Conditional updates: keep the predicate with the write so concurrent updates cannot overwrite a stale decision.
  4. Repeatable Read limit: stable snapshots can still miss cross-row conflicts such as write skew.
  5. Serializable retry: retry the whole transaction because the database rejected the observed execution.
  6. Contention signals: watch waits, aborts, retries, deadlocks, conflicts, and transaction duration.

The Big Idea

PostgreSQL builds a query plan for each query. The plan is a tree of operations: scans at the bottom, then joins, sorts, aggregates, limits, and other nodes above them. The official Using EXPLAIN guide emphasizes that plan choice depends on the query shape and the properties of the data.

An index lets the database find specific rows faster, but PostgreSQL's index documentation also notes the tradeoff: indexes add overhead. A senior performance answer therefore has two halves: why this access path is faster, and what cost it adds to writes, storage, vacuuming, and rollout.

Slow query decision path:

symptom
  -> exact SQL and parameters
  -> EXPLAIN plan
  -> estimated rows versus actual rows
  -> access path and filters
  -> smallest useful index or query change
  -> production rollout and proof

Scenario: Recent Open Orders

Suppose a merchant dashboard needs the 50 newest open orders. The endpoint is now slow for large merchants.

SELECT id, created_at, total_cents, status
FROM orders
WHERE merchant_id = $1
  AND status = 'open'
ORDER BY created_at DESC
LIMIT 50;

The weak diagnosis is "we need an index on orders." The production diagnosis asks a sharper question: can PostgreSQL quickly jump to this merchant's open rows in the right order, stop after 50, and avoid scanning or sorting a large fraction of the table?

Subsetstatus = 'open' names the hot working set.

Read the Plan Before Designing the Index

EXPLAIN shows the plan PostgreSQL expects to use. EXPLAIN ANALYZE executes the query and shows actual row counts and timing, so use it only where executing the query is safe. The PostgreSQL docs call out that costs are planner units, while actual times are real milliseconds; the more important diagnostic is often whether estimated rows are close to actual rows.

Plan clue What it suggests Question to ask
Seq Scan on a large table. The planner expects reading broadly to be cheaper than using an index. Is the predicate selective, or does it really touch many rows?
Filter removes many rows. The condition is checked after rows are reached. Could this predicate become an Index Cond?
Large Sort before Limit. PostgreSQL may find many rows, sort them, then discard most. Can index order produce the first page directly?
Bad estimate versus actual rows. The planner may be choosing from wrong assumptions. Are statistics stale, skewed, or missing correlation?
High loops on an inner node. A small operation may be repeated many times. Is a join order or nested lookup exploding?

Design the Index From the Query Shape

For the recent-open-orders query, a useful index aligns the stable filter and order:

CREATE INDEX CONCURRENTLY orders_open_recent_idx
ON orders (merchant_id, created_at DESC)
INCLUDE (id, total_cents, status)
WHERE status = 'open';

This is not magic syntax. It is a workload argument:

  1. merchant_id is the leading equality filter, so the index can jump into one merchant's range.
  2. created_at DESC matches the requested order, so PostgreSQL may avoid a separate sort.
  3. WHERE status = 'open' makes it a partial index over the hot subset, as described in the partial index documentation.
  4. INCLUDE columns can help narrow output avoid table visits, but PostgreSQL warns that included columns duplicate data and can bloat the index.

The multicolumn index documentation is the key source here: a B-tree index is most efficient when query constraints match the leading columns. In practice, put equality filters that strongly partition the search before the range or ordering column you want to page through.

Do Not Worship Index Scans

A sequential scan is not automatically bad. If a query needs most of a table, reading the table directly can beat random index-driven heap lookups. PostgreSQL's EXPLAIN examples show the planner switching among sequential scans, bitmap scans, index scans, hash joins, merge joins, and sorts based on estimated cost.

Production rule: the plan is good if it does the least necessary work for the current data shape and workload.

An index that helps one endpoint can hurt another path by slowing inserts, updates, deletes, vacuum, replication, cache residency, and backup size. For high-write tables such as events, idempotency attempts, jobs, and ledger rows, every extra index is part of the write path.

When the Planner Is Wrong

The planner estimates selectivity: how many rows will match each condition. PostgreSQL's planner statistics documentation explains that these estimates come from approximate statistics updated by ANALYZE and VACUUM ANALYZE. Statistics can be stale, or they can miss relationships between columns.

Common bad-estimate shape:

WHERE merchant_id = $1
  AND region = 'us-east'
  AND status = 'open'

The planner may assume these predicates are independent.
In reality, one large merchant might dominate open orders in one region.

The fix might be an index, but it might also be fresh ANALYZE, better statistics, a query rewrite, or moving a high-fanout read to a projection built in earlier lessons. Do not solve every database performance problem by adding another B-tree.

Rollout Is Part of the Design

On a large live table, a standard index build can block writes. The CREATE INDEX docs explain that CONCURRENTLY builds without locks that prevent concurrent inserts, updates, or deletes, although it has caveats and still consumes resources.

Concern Production habit Metric or check
Build pressure Schedule with I/O headroom and watch progress. Disk I/O, CPU, replication lag, progress view.
Write overhead Compare insert/update latency before and after. p95/p99 write latency, WAL volume, lock waits.
Planner choice Confirm the post-change plan uses the intended path. EXPLAIN (ANALYZE, BUFFERS) before and after.
Maintenance Keep autovacuum and statistics healthy. dead tuples, analyze age, vacuum activity, bloat.
Unused index Verify real usage before keeping it forever. pg_stat_user_indexes, query latency, I/O.

PostgreSQL's routine vacuuming guide connects this to operations: vacuuming reclaims dead row space, updates planner statistics, and supports visibility information used by some index-only scans. Database performance is not static after the migration lands.

How to Defend the Resume Bullet

Suppose someone asks: "You said you optimized a slow dashboard query. What did you actually do?" A strong answer sounds like a diagnosis, not a slogan.

Strong answer shape:

  1. The slow path was the merchant open-orders dashboard, where large merchants saw high p95 latency.
  2. EXPLAIN ANALYZE showed PostgreSQL scanning many merchant rows, filtering by status, sorting by creation time, then returning only 50.
  3. We added a partial multicolumn index on (merchant_id, created_at DESC) for open orders, with narrow included columns for the response.
  4. The index matched the equality filter, hot subset, order, and limit, so the database could stop after the first page instead of sorting a large candidate set.
  5. We built it concurrently, monitored I/O and replication lag, compared before/after plans, and watched read latency, write latency, and index usage.
  6. We accepted the storage and write overhead because the endpoint was hot and the indexed subset was small.

Reflection Questions

No homework is required. These are the checks that show whether you can reason about database performance as production engineering:

  1. Why is "add an index" not a complete diagnosis?
  2. What is the difference between Index Cond and Filter?
  3. Why can a sequential scan be the right plan?
  4. How does ORDER BY ... LIMIT change index design?
  5. When might fresh statistics help more than a new index?
  6. What production risks should you watch while building an index on a live table?

Concise answer key: name the query path and access pattern; Index Cond restricts index access while Filter checks reached rows; broad reads can favor sequential scans; order plus limit rewards an index that can emit the first page directly; bad estimates can come from stale or insufficient statistics; watch locks, I/O, replication lag, write latency, query plans, and index usage.

Ask follow-up questions about any unclear piece. Useful performance questions here are: "What changed in the plan?", "Were estimates close to actuals?", "Does the index match the query order?", "What write cost did we add?", and "How did we prove it helped?"
