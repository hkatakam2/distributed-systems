Lesson 0013

Capacity, Backpressure, and Bottlenecks

The thirteenth mental model: production performance is not "make everything faster." It is finding the limiting resource, controlling demand, and protecting the user promise when load exceeds some part of the system.

Mission link: this zooms back out across high-throughput APIs, Redis caches, PostgreSQL, Kafka/Flink pipelines, Kubernetes scaling, retries, and incident defense for claims like 10K+ req/sec, 50K+ queries/min, and 5M+ events/day.

Where This Fits

Lesson 0012 was intentionally deep on stored-data change. This lesson returns to the whole system path: when traffic rises, which boundary saturates first, what signal proves it, and what control keeps the system useful?

Concise Answers From Lesson 0012

  1. Migrations are rollouts: code, schema, data, indexes, replicas, and rollback paths all move on different clocks.
  2. Expand first: old and new code must coexist before readers depend on the new shape.
  3. Backfills are writers: they create WAL, locks, bloat, replica lag, and user-facing risk.
  4. Validate before enforcing: "the job finished" is not the same as "the data is safe to depend on."
  5. Contract late: remove fallback only after old versions and rollback paths no longer need it.

The Big Idea

Every production path has a capacity story. Requests arrive, each request creates work, work waits behind shared resources, and one boundary eventually becomes the limit. That boundary may be CPU, a database connection pool, a Kafka partition, a Redis hot key, a third-party API, a lock, a stream checkpoint, or a human-owned recovery process.

The Google SRE chapter on handling overload is the primary source for this lesson because it frames overload as a systems problem: protect critical work, shed less important work, throttle clients, and avoid retry-driven collapse. The same principle appears in gRPC deadlines: callers must stop spending work after the result is no longer useful.

Capacity reasoning path:

name the user promise
  -> draw the critical path
  -> estimate demand and fanout
  -> find the saturated boundary
  -> apply backpressure, shedding, caching, batching, or scaling
  -> verify latency, errors, freshness, saturation, and cost

The trap is scaling the visible layer without finding the limiting layer. Doubling API pods can make latency worse if each pod opens more database work than PostgreSQL can serve. Increasing consumer count does not help a Kafka consumer group beyond the number of assignable partitions. Raising retry counts can convert a slow dependency into a full overload event.

Scenario: Inventory Availability During Peak Traffic

Suppose an inventory availability API normally serves 2,000 requests per second at 80 ms P95. During a sale event it receives 10,000 requests per second. Each request checks Redis for hot SKU availability, may fall back to PostgreSQL for misses, and emits an availability-check event to Kafka for analytics and reconciliation.

ClientBursty reads and retries.
APIPods, thread pools, connection pools.
RedisHot keys, TTLs, memory, misses.
PostgresSource reads, locks, indexes, I/O.
KafkaEvents, partitions, lag, consumers.

The weak answer is "add more pods." The production answer asks: which part is saturated, what demand is legitimate, and what can be slowed, cached, dropped, or degraded without breaking the product promise?

First Estimate: Work Multiplies Across Boundaries

Start with rough math. At 10,000 requests per second, one extra database query per request means 10,000 database queries per second. If Redis hit rate drops from 99 percent to 95 percent, database fallback traffic increases fivefold. If each slow request triggers two client retries, apparent demand can become larger than real user demand.

Useful memory rule: work in progress is roughly arrival rate times latency.

If 10,000 requests per second take 200 ms end to end, about 2,000 requests are in flight. If latency rises to 1 second under the same arrival rate, about 10,000 requests are now in flight. That extra in-flight work consumes threads, memory, queues, sockets, and connection pools.

This is why latency is not just a user-experience metric. Rising latency creates more concurrent work, which can cause more waiting, which raises latency again.

Find the Bottleneck, Not the Loudest Symptom

The service with the highest error rate is not always the limiting resource. It may be the first place where a downstream limit becomes visible. Use the signal that matches the boundary.

Boundary Useful saturation signal What it usually means
API pods CPU, run queue, thread pool wait, request queue depth Per-request work is too expensive or concurrency is too high.
Connection pool Pool wait time, active connections, timeout count The service is asking the database for more concurrent work than the pool allows.
PostgreSQL Wait events, locks, I/O, slow queries, index usage The database is the limiting shared resource, not just the caller.
Redis Hit rate, memory, eviction, hot key latency, command latency The cache may be protecting the source or quietly failing to protect it.
Kafka consumers Consumer lag, event age, rebalance frequency, processing time Producers are adding work faster than the group can complete it.
Stream processor Watermark lag, checkpoint duration, backpressure, sink latency State, time, or output sinks are limiting freshness.

PostgreSQL's monitoring statistics are useful here because database bottlenecks often show up as waits, activity states, table/index pressure, and I/O behavior. Redis's eviction documentation is a reminder that cache memory pressure and hit/miss behavior are capacity signals, not implementation trivia.

Backpressure: Slow the Work Before the Limit Breaks

Backpressure is not failure. It is a deliberate signal that says "this boundary cannot accept unlimited work right now." Without it, queues grow until users see timeouts, memory is exhausted, or retries amplify load.

Situation Bad reflex Better control
Database pool is full. Increase pool size blindly. Cap concurrency, reduce queries, cache hot reads, and protect write paths.
Redis misses surge. Let every miss hit PostgreSQL. Coalesce requests, serve bounded stale data, or shed low-priority reads.
Consumer lag grows. Retry failed events in a tight loop. Use bounded retries, DLQ ownership, pause unsafe partitions, and repair later.
External dependency slows. Wait forever and retry harder. Use deadlines, jittered backoff, circuit breakers, and degraded responses.

The skill is choosing what to protect. A checkout inventory answer may reject quickly rather than risk overselling. An operations dashboard may serve a stale-but-labeled answer while the projection catches up. An analytics event can often be buffered or dropped after durability rules are satisfied.

Scaling Is a Control, Not a Diagnosis

Kubernetes can add pods, but autoscaling only helps when the pod layer is the limiting resource or when more pods do not overload the next dependency. The Horizontal Pod Autoscaling docs describe a controller that adjusts workload scale based on observed metrics. That is useful, but the chosen metric matters.

Scaling question sequence:

what metric proves pod capacity is the limit?
what dependency receives more load per added pod?
what limit prevents new pods from overwhelming that dependency?
what signal tells autoscaling to stop or slow down?
what does the system do while new capacity starts?

For an API, scaling pods may be correct when CPU is saturated and database/cache pressure is low. It may be wrong when pool waits, database waits, or Redis hot key latency are already the limit. For Kafka consumers, adding consumers helps only until all partitions in the consumer group are assigned; after that, reducing per-event work, changing partitioning, batching, or fixing a slow sink may matter more.

Defend the Resume Bullet

Suppose someone asks: "How did you sustain 10K+ req/sec at sub-200 ms P95 during peak traffic?" A strong answer is not "we used Redis and Kubernetes." It explains the capacity argument.

Strong answer shape:

  1. Traffic was bursty and SKU popularity was highly skewed, so hot-path reads had to avoid repeated source-database work.
  2. We measured API latency, Redis hit rate, hot key behavior, database pool waits, database query latency, and upstream dependency latency.
  3. Redis served the common availability shape with TTLs and freshness boundaries, while misses were controlled so they did not stampede PostgreSQL.
  4. API concurrency, connection pools, timeouts, and retries were tuned together, so adding pods did not simply add unbounded database pressure.
  5. Lower-value or stale-tolerant reads could degrade before critical checkout behavior was put at risk.
  6. The result was defended with before/after P95 latency, throughput, hit rate, pool wait time, error rate, and freshness signals.

Reflection Questions

No homework is required. These are the checks that show whether you can reason about capacity as production judgment:

  1. Why can adding API pods make a database bottleneck worse?
  2. What signals distinguish an API bottleneck from a database bottleneck?
  3. Why does a lower Redis hit rate create more than a cache problem?
  4. When should an API serve stale data, reject quickly, or wait for fresh source truth?
  5. Why do retries need deadlines, backoff, jitter, and budgets?
  6. What before/after metrics would you use to defend a 10K req/sec performance claim?

Concise answer key: more pods can multiply downstream queries; API bottlenecks show CPU/thread/request-queue pressure while database bottlenecks show pool waits, locks, slow queries, I/O, and wait events; cache misses can stampede the source; stale/reject/wait depends on the product correctness contract; retries without limits amplify overload; defend the claim with P95/P99 latency, throughput, error rate, hit rate, pool waits, dependency latency, freshness, and headroom.

Ask follow-up questions about any unclear piece. Useful capacity questions here are: "What is the user promise?", "Where does work queue?", "What is saturated?", "Who can slow down?", and "What metric proves the fix worked?"
