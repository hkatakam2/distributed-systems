Lesson 0009

Replication, Quorums, and Consistency

The ninth mental model: replicated state is a promise, not a copy. A backend engineer must know which replicas can accept writes, which reads are fresh enough, and what the system does when replicas disagree.

Mission link: this is the judgment behind PostgreSQL replicas, Spanner-like databases, Dynamo-style key-value stores, Redis/materialized reads, inventory correctness, billing projections, and incident explanations about stale or divergent data.

Where This Fits

Lesson 0008 treated production change as a compatibility problem. This lesson treats production state as a failure problem: machines, zones, regions, and networks fail, but users still expect data to be durable, available, and not misleading.

  3. Rolling update compatibility: old and new code may share rows, events, cache payloads, config, and API shapes at the same time.

  5. Roll forward case: rolling forward can be safer when schema, data, or events have already moved beyond what old code understands.
  6. Canary decision signals: compare latency, errors, saturation, freshness, and correctness by version, cohort, and dependency.

The Big Idea

Replication creates multiple copies of state so the system can survive hardware failure, zone failure, regional distance, maintenance, and load. But more copies create a harder question: when two copies disagree, which answer should the system believe?

The Google File System paper frames replication as a response to commodity-machine failure. The Dynamo paper shows a high-availability design that uses configurable N, R, and W values, object versioning, sloppy quorum, hinted handoff, and conflict reconciliation. The Spanner replication docs describe a different choice: synchronous, Paxos-based replication with leaders, voting replicas, and write quorums. The Spanner consistency docs explain the stronger user contract: externally consistent transactions and strong reads.

Replication decision path:

business invariant
  -> acceptable stale-read window
  -> write availability requirement
  -> conflict mergeability
  -> replica topology
  -> commit rule
  -> read rule
  -> repair and observability plan

The practical skill is not memorizing a consistency model name. It is matching the data boundary to the failure behavior the business can survive.

Scenario: Inventory And Billing State

Your resume has two useful examples: inventory availability at Flipkart and billing metrics at Stripe. These look similar because both are replicated state, but their correctness contracts differ.

Inventory reserveDo not sell the last unit twice.
Billing ledgerDo not invent or lose money.
MRR dashboardShow recent enough metrics.
Redis cacheServe fast derived reads.
Event replayRepair projections deterministically.

For inventory reservation or a billing ledger, rejecting writes during a partition may be correct because accepting conflicting writes can violate a hard invariant. For an MRR dashboard, a labeled stale answer may be acceptable if it is within the product's freshness contract and can be rebuilt from source events.

Two Questions Before Any Replica Design

Every replicated system answers two questions, whether the product admits it or not.

Question Strong-leaning answer Availability-leaning answer
When is a write successful? After a leader or majority has ordered and durably accepted it. After any reachable coordinator accepts it, with later repair.
Who can answer a read? A leader, a quorum, or a replica proven to include recent commits. A nearby replica, cache, or older snapshot with staleness allowed.

Neither column is morally better. The strong answer protects invariants but may reject work when a quorum is unavailable. The available answer keeps serving but pushes complexity into versioning, conflict resolution, and user-visible staleness.

N, R, and W: The Quorum Dial

In Dynamo-style notation, N is the intended replica count for a key, W is the number of replicas that must acknowledge a write, and R is the number of replicas consulted for a read. A common intuition is R + W > N: the read set and write set should overlap.

Example:

N = 3 replicas
W = 2 acknowledgements for a successful write
R = 2 responses for a successful read

R + W = 4, which is greater than N = 3.
Under stable membership, the read should contact at least one replica
that saw the latest successful write.

That overlap is useful, but it is not magic. Real systems still need clear membership, version metadata, failure detection, conflict handling, repair, and a policy for slow or unreachable replicas. Dynamo deliberately chooses availability under some failures, then exposes versioning and reconciliation to deal with divergent histories.

Strong Replication: Majority Before Success

Spanner represents the other side of the design space. Its docs describe synchronous, Paxos-based replication where voting replicas vote on each write before commit. Within each replica set, a leader handles writes, and a write commits when a majority of voting replicas agree.

Choice What it buys What it costs
Leader orders writes One authority sequences conflicting writes. Write latency depends on leader placement and failover.
Majority commit A committed write survives one replica failure in a three-voter group. Writes pause when no majority can form.
Strong reads Readers observe the committed state promised by the system. Non-leader reads may need coordination.
Stale reads Nearby replicas can serve older versions faster. The caller must tolerate the timestamp being older.

The senior judgment is recognizing why a database may intentionally reject a write during a partition. If accepting the write could violate money, inventory, auth, or ordering invariants, unavailability is the safer failure mode.

Eventual Consistency: Availability With A Repair Bill

Eventual consistency is not "random correctness." It is a contract: replicas may disagree temporarily, and the system must converge later through propagation, read repair, anti-entropy, replay, or application-level reconciliation.

client writes preference in region A
  -> local replica accepts quickly
  -> region B may still show old preference
  -> background replication catches up
  -> conflict resolver handles concurrent edits
  -> metrics prove lag and conflicts are bounded

This is reasonable when the business operation is mergeable, reversible, or not safety-critical. It is dangerous when two accepted writes can both look valid locally while violating a global invariant.

Caches And Projections Are Replicas Too

The Redis materialization layer from earlier lessons is a derived replica of source events. It is fast because it is specialized, but it should not silently pretend to be the source of truth.

Derived state Correctness contract Operational control
Redis dashboard cache Fresh within a defined age, such as "as of 10:31:04". TTL, versioned keys, fallback, invalidation, freshness metric.
Flink projection Deterministically rebuildable from Kafka offsets and source events. Checkpointing, replay, idempotent upserts, drift checks.
Search index Eventually includes committed source records. Index lag, dead-letter handling, backfill, reconciliation.

A useful production answer names the authority. If the cache lies, what truth source corrects it? If the projection drifts, what replay or rebuild restores it?

How To Defend The Resume Bullet

Suppose someone asks: "How did you keep inventory or billing data correct with distributed caches and streams?" A strong answer separates authoritative writes from derived reads.

Strong answer shape:

  1. For hard invariants such as inventory reservation or billing facts, writes went through an authoritative store with transactional or quorum-backed durability.
  2. Redis and dashboard projections were treated as derived replicas, not as the authority for money or stock ownership.
  3. Each derived record carried version, source offset, or as-of metadata so stale answers could be detected and bounded.
  4. Stream consumers used idempotent upserts and replay-safe version guards so retries or replays could not move state backward.
  5. Freshness, consumer lag, drift, conflict count, and rebuild progress were monitored as correctness signals, not just performance signals.
  6. During incidents, the system could degrade to a labeled stale read, fall back to source truth, pause unsafe consumers, or rebuild the projection from the log.

Reflection Questions

No homework is required. These are the checks that show whether you can reason about replicated state:

  1. Why does adding replicas improve durability but complicate reads?
  2. When is rejecting a write better than accepting it?
  3. Why is R + W > N useful but not a complete correctness proof?
  4. Which data in your resume examples can safely be stale, and which cannot?
  5. What metadata would you attach to a materialized dashboard record to make staleness visible?
  6. What metrics would prove a derived replica is converging after an incident?

Ask follow-up questions about any unclear piece. Useful replication questions here are: "Who is the authority?", "What makes the write committed?", "Can readers tolerate staleness?", "Can conflicts be merged?", and "How do we prove replicas converged?"
