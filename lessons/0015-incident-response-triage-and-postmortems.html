Lesson 0015

Incident Response, Triage, and Postmortems

The fifteenth mental model: during an incident, the goal is not to prove you are clever. It is to protect the user promise, coordinate change, preserve evidence, and make the system harder to break next time.

Mission link: this turns everything so far into senior backend judgment under pressure: APIs, storage, Kafka/Flink, caches, deployments, observability, SLOs, and recovery all meet in the incident room.

Where This Fits

Lesson 0014 taught how to define the user-visible promise and alert when error budget burns. This lesson starts when the page fires: what do you do first, who decides, how do you avoid conflicting fixes, and how does the incident become durable learning?

Concise Answers From Lesson 0014

  1. Start from users: SLOs should measure completed promises, not component greenness.
  2. Define the ratio: an SLI is good eligible events divided by total eligible events.
  3. Separate spec and source: the behavior you want to measure is not the same as the telemetry source you use.
  4. Budget is a decision tool: remaining error budget changes rollout, paging, mitigation, and reliability investment.
  5. Lag is not always the promise: users usually care about visible freshness, not only broker offset distance.
  6. Burn rate sets urgency: fast burn pages; slow burn often creates planned reliability work.

The Big Idea

An incident is a coordination problem wrapped around a technical problem. The technical problem may be a bad deploy, hot database row, Kafka partition skew, Redis stampede, broken rollout, or retry storm. The coordination problem is making sure only the right people change production state, stakeholders know the truth, the team keeps a live record, and mitigation happens before curiosity consumes the error budget.

The Google SRE chapter on Managing Incidents frames incident management as preparation, role clarity, communication, a live state document, and handoff. Its guidance is practical: declare early when customer visibility, multi-team coordination, or prolonged uncertainty appears; then prioritize stopping the bleeding, restoring service, and preserving evidence. The Emergency Response chapter adds the deeper point: teams do not naturally respond well under stress without preparation and practice.

Incident reasoning path:

detect promise risk
  -> declare and assign roles
  -> stabilize user impact
  -> preserve evidence and narrow hypotheses
  -> communicate current truth and next update
  -> recover, clean up, and write the postmortem
  -> verify follow-up actions changed the system

The trap is treating root cause as the first milestone. In a burning incident, mitigation comes first when user impact is active. You can diagnose deeply after you stop making the user pay for the investigation.

Scenario: Freshness Burn After a Release

Suppose a subscription analytics platform has a dashboard freshness SLO: 99.5% of merchant dashboard views should use revenue projection data no older than five minutes over a rolling 30-day window. A new release changes a Flink sink that writes projection rows to PostgreSQL and refreshes Redis keys. Twenty minutes after rollout, the freshness SLO starts burning at 15x.

APIDashboard reads return 200s but stale projection ages.
RedisHot dashboard keys are not being refreshed quickly enough.
PostgresProjection upserts show rising lock waits and slow commits.
FlinkCheckpoint duration and sink latency climb.
KafkaConsumer lag grows on several high-volume merchant partitions.

A narrow response says "debug Flink." A production response says "declare the incident, stop freshness budget burn, coordinate production changes, then debug the path from release to user-visible stale views."

Step 1: Declare Before the Room Gets Crowded

The incident threshold should be lower than "total outage." Declare when the work needs coordination, when user impact is visible, when a second team is needed, or when focused investigation has not converged. Declaring is not an admission of disaster; it is how you buy structure early.

Signal Why it deserves incident structure First action
Freshness burn is 15x. The dashboard promise will be exhausted quickly if the trend continues. Declare severity based on user impact and budget burn.
Flink, PostgreSQL, Redis, and deploy history are all plausible. Several owners may need to inspect state or change controls. Assign roles so only approved changes happen.
Merchants see old revenue numbers. A 200 response is not good if the product promise is stale. Communicate impact honestly and set update cadence.
A rollback may lose temporary sink fixes. The system may diverge from normal state during recovery. Track every mitigation and cleanup task.

Step 2: Split Roles to Reduce Cognitive Load

Google's incident model separates incident command, operational work, communications, and planning. The point is not ceremony. The point is that the person debugging a failing stream sink should not also hold stakeholder status, remember every temporary config, approve every production change, and plan handoff.

Incident commander: owns high-level state, current priority, role assignment, and the next decision.

Ops lead: makes or coordinates approved production changes: rollback, pause, traffic routing, config, throttling.

Communications lead: writes periodic updates: impact, current status, mitigation, next update time, known unknowns.

Planning lead: tracks follow-ups, cleanup, handoff, temporary state, and postmortem inputs.

The key safety property is no freelancing. If three engineers independently "just look" and one silently restarts workers while another changes Redis TTLs and another rolls back the sink, the system becomes harder to reason about than the original failure.

Step 3: Stabilize Before Deep Diagnosis

Mitigation reduces impact before the full causal story is known. In this scenario, a reasonable incident commander asks the ops lead for reversible options that protect the freshness promise while evidence is still available.

Option When it fits Risk to watch
Pause or roll back the release. Freshness burn correlates strongly with the new sink version. Rollback may not clear already accumulated lag or locks.
Serve stale-labeled dashboard data. Users can tolerate old values if the UI is honest about age. Stale data must not drive irreversible business actions.
Throttle low-priority recomputations. High-value merchant views need capacity before offline refresh jobs. Delayed work must be tracked so it is not forgotten.
Split hot merchants to a safer path. A small set of tenants dominates lag or lock waits. Special routing creates cleanup and consistency obligations.

The strongest mitigation is reversible, measurable, and tied to the SLO. "We rolled back version 2026.06.30.4 and freshness burn fell from 15x to 2x" is stronger than "we changed some settings and things looked better."

Step 4: Diagnose From Evidence, Not Drama

The Google SRE chapter on Effective Troubleshooting is useful here because it treats debugging as hypothesis management. Start from the user symptom, narrow the path, compare against recent changes, and test the cheapest discriminating hypothesis.

Evidence chain for this incident:

fresh dashboard views dropped
  -> Redis key age increased
  -> projection upsert latency increased
  -> PostgreSQL lock waits concentrated on merchant_id
  -> Flink sink retries increased after release
  -> new sink changed batch shape and transaction duration

This chain may be wrong. That is why the live incident document should show hypotheses with evidence for and against them. If rollback does not reduce burn, the team should say so and move to the next hypothesis rather than defend the first theory.

Step 5: Communicate Current Truth

Good incident communication is not an essay. It is a repeated, timestamped snapshot: impact, current status, mitigation, next action, next update time, and known unknowns. This protects the responders from repeated status interruptions and protects stakeholders from guessing.

14:10 ET - Dashboard freshness SLO is burning at 15x.
Impact: some merchants see revenue projections older than five minutes.
Mitigation: rollout paused; ops is preparing rollback of sink version 2026.06.30.4.
Current evidence: staleness follows Flink sink latency and PostgreSQL lock waits.
Next update: 14:25 ET, or earlier if rollback changes burn rate.

Notice what this update does not do: it does not promise a root cause before one exists, hide uncertainty, or flood non-responders with low-level logs.

Step 6: Postmortem the System, Not the Person

The Google SRE chapter on Postmortem Culture defines a postmortem as a written record of impact, actions, root causes, and follow-up actions. Its strongest norm is blamelessness: assume people acted reasonably with the information and tools they had, then improve the system around those decisions.

Weak postmortem Stronger postmortem Why it matters
"Engineer shipped bad sink code." "Canary did not include high-cardinality merchant partitions, so sink lock amplification was not detected." The second version creates a testable rollout improvement.
"Flink was slow." "Sink retry loop extended transaction duration, increasing Postgres lock waits and projection age." The second version names the mechanism.
"We need better monitoring." "Add freshness burn alert by top merchant cohort and include sink retry count in the dashboard." The second version is owned, measurable, and reviewable.

A useful postmortem produces action items that change future behavior: rollout gates, safer batch sizes, lock wait alerts, runbook updates, replay drills, load tests, ownership, or cleanup automation. A postmortem that only records blame has not strengthened the system.

Defend the Resume Bullet

Suppose someone asks: "Tell me about a production incident in your event-driven analytics platform." A strong answer avoids both heroics and vagueness. It shows calm control of the system.

Strong answer shape:

  1. We detected a dashboard freshness SLO fast burn after a stream-sink release.
  2. I helped declare the incident early because impact crossed the user promise and required Flink, Postgres, Redis, and release owners.
  3. We assigned incident command, ops, communications, and planning so production changes were coordinated.
  4. We paused rollout, rolled back the sink, and served stale-labeled views while lag drained, which reduced budget burn.
  5. We used traces, sink metrics, database lock waits, Redis key age, and deploy history to isolate the mechanism.
  6. The postmortem changed rollout gates, high-cardinality canary coverage, sink batch limits, and freshness alerts.

Reflection Questions

No homework is required. These are the checks that show whether you can reason under production pressure:

  1. Why is an incident a coordination problem as much as a technical problem?
  2. When would you declare an incident before knowing the root cause?
  3. Why does mitigation often come before diagnosis?
  4. What should be in a live incident state document?
  5. How can a rollback be both a mitigation and an incomplete fix?
  6. What makes a postmortem action item stronger than "add better monitoring"?

Concise answer key: incidents require coordinated decisions, changes, communication, and handoffs; declare when user impact, fast burn, multi-team work, or prolonged uncertainty appears; mitigation protects users while diagnosis continues; the state document should track impact, roles, timeline, hypotheses, actions, owners, and next update; rollback can stop new harm while leaving lag, bad data, or cleanup behind; strong action items name a concrete system change, owner, priority, and verification signal.

Ask follow-up questions about any unclear piece. Useful incident questions here are: "What user promise is burning?", "Who owns the next decision?", "What mitigation is reversible?", "What evidence would falsify this hypothesis?", and "How will the follow-up be verified?"
