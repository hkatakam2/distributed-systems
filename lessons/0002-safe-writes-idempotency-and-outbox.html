Lesson 0002

Safe Writes: Idempotency and the Transactional Outbox

The second mental model: a production write path is designed around ambiguity. The client may retry, the service may crash, the broker may duplicate, and the system still has to produce one durable business fact.

Mission link: this is the correctness core behind event-driven pipelines, payment retries, inventory updates, stream materialization, and defensible resume bullets about reliable distributed systems.

Where This Fits

Lesson 0001 gave the whole map: request, durable fact, log, processor, serving state, and operations. This lesson zooms into the riskiest boundary: turning a retry-prone command into a durable fact and a publishable event.

Concise Answers From Lesson 0001

  1. Cancellation command vs fact: cancel_subscription is the command; subscription_canceled is the durable fact.
  2. Required billing order: usually subscription order; merchant order is useful for merchant aggregates, but global order is too expensive and unnecessary.
  3. Crash after Redis update before checkpoint: the processor may replay the event and update Redis again, so the write must be idempotent or guarded by version/event ID.
  4. Detect Redis drift: compare Redis projections against database/log-derived truth with sampled checks, reconciliation jobs, freshness metrics, and aggregate audits.
  5. Queue vs replayable log: choose a queue for one-time task distribution; choose a log when ordering, replay, multiple consumers, or derived-state rebuilds matter.
  6. Paging metric: all can page under different SLOs; user-visible latency, freshness age, consumer lag, and DLQ growth represent different failures.

The Big Idea

A distributed write has an unavoidable ambiguity: if a client sends POST /subscriptions/sub_123/cancel and times out, neither side can know from the timeout alone whether the command committed. Retrying may be necessary, but retrying a non-idempotent write can create duplicate side effects.

Amazon's Builders' Library article on idempotent APIs frames the production contract: callers should be able to retry safe operations, while services accept the implementation burden of identifying duplicate intent. The preferred shape is a caller-provided unique request identifier, not just a hash of parameters, because identical parameters can still represent different business intent.

The second ambiguity appears after the database write: the service must publish an event, but the database and broker usually do not share one transaction. The transactional outbox pattern solves this by storing the event in the database transaction that changes business state. A relay publishes the outbox row later.

Safe write path:

client command + idempotency key
  -> validate request
  -> start database transaction
  -> record idempotency key
  -> mutate source-of-truth state
  -> insert outbox event
  -> commit transaction
  -> relay publishes event to Kafka
  -> consumers process idempotently

Scenario: Cancel a Subscription

Assume a billing API receives a cancellation command. The user-visible requirement is simple: cancel once. The production requirement is sharper: retries, crashes, duplicate events, and stream replay must not produce multiple cancellations or inconsistent downstream metrics.

ClientSends command with Idempotency-Key.
APIChecks whether this key was seen for this caller.
DBChanges subscription and records an outbox event atomically.
RelayPublishes pending outbox rows to Kafka.
MetricStream processor updates MRR and churn projections.

Minimal schema shape

idempotency_keys(
  caller_id, key, request_hash, response_status, response_body, expires_at,
  unique(caller_id, key)
)

subscriptions(
  id, merchant_id, status, version, canceled_at
)

outbox_events(
  id, aggregate_type, aggregate_id, sequence, event_type, payload, status, created_at,
  unique(aggregate_type, aggregate_id, sequence)
)

Transaction shape

begin;

-- 1. Claim or inspect the idempotency key for this caller.
-- Same key + same request means return the original semantic result.
-- Same key + different request means reject the command.

select * from subscriptions where id = :subscription_id for update;

-- 2. Make the state transition only if it is valid.
update subscriptions
set status = 'canceled',
    version = version + 1,
    canceled_at = now()
where id = :subscription_id
  and status in ('active', 'past_due');

-- 3. Store the event in the same transaction as the state change.
insert into outbox_events(...)
values (..., 'subscription_canceled', ..., 'pending', now());

-- 4. Store the response attached to the idempotency key.
commit;

PostgreSQL row locks such as FOR UPDATE are one way to guard the state transition. For queue-like outbox relays, SKIP LOCKED can help multiple workers avoid contending on the same rows, but PostgreSQL explicitly warns that it gives an inconsistent view and is appropriate for queue-like access rather than general reads.

The Failure Matrix

Failure Bad design Production design
Client times out after commit Retry creates a second cancellation or a confusing conflict. Same idempotency key returns a semantically equivalent response.
Service crashes after DB commit The subscription changes, but no event reaches the pipeline. Outbox row is already committed and can be published later.
Service publishes before DB commit Downstream sees a fact that may roll back. Publish only after the committed outbox row exists.
Relay crashes after publish Restart may publish the same event again. Consumers dedupe by event ID or write idempotently.
Two updates race on one subscription Order depends on timing and may corrupt state. Lock, version, sequence, or conditional transition guards the aggregate.
Same key, different request Service treats different intent as a duplicate. Reject as conflict because the idempotency contract was violated.

Why This Is Not "Exactly Once"

Kafka's design documentation separates producer durability, consumer position, and processing effects. It also notes that at-least-once processing can replay messages after a crash, while exactly-once claims depend on what systems participate in the transaction. Kafka transactions help when reading from Kafka and writing to Kafka, but writing to an external system such as Redis, PostgreSQL, or a payment provider still requires cooperation from that system.

The practical rule: design every boundary as if duplicates can happen. Use idempotency keys for client commands, outbox event IDs for publication, consumer-side dedupe for event handling, and reconciliation for catching the cases your assumptions missed.

How to Defend the Resume Bullet

Suppose someone asks: "How did you make the billing event pipeline reliable?" Do not only say "Kafka retries" or "we used DLQs." A stronger answer shows the write boundary.

Strong answer shape:

  1. Client writes used idempotency keys so retries did not create duplicate business effects.
  2. The source-of-truth database transaction updated billing state and inserted an outbox event atomically.
  3. A relay published committed outbox rows to Kafka, accepting that publish attempts could duplicate.
  4. Events carried stable event IDs, aggregate IDs, sequence/version fields, and schema versioning metadata.
  5. Consumers wrote idempotently and tracked processed event IDs where duplicate effects were unsafe.
  6. Operations watched outbox depth, oldest unpublished event age, publish error rate, consumer lag, DLQ count, and reconciliation drift.

Reflection Questions

No homework is required. These are the checks that show whether the write boundary is solid:

  1. For POST /inventory/reserve, what should the idempotency key represent?
  2. What database uniqueness constraint prevents the same caller key from being claimed twice?
  3. Why is "publish to Kafka, then commit the database" unsafe?
  4. If an outbox relay publishes the same event twice, where should deduplication happen?
  5. What ordering key would you use for subscription lifecycle events?
  6. Which operational signal tells you that committed facts are not reaching Kafka quickly?

Ask follow-up questions about any unclear piece. Good debugging questions here are: "What committed?", "What can be retried?", "What can duplicate?", "Who dedupes?", and "Where is the event waiting?"
