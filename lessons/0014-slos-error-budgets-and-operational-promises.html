Lesson 0014

SLOs, Error Budgets, and Operational Promises

The fourteenth mental model: production reliability is not "keep every component green." It is choosing the user-visible promises that matter, measuring them honestly, and spending the reliability budget deliberately.

Mission link: this ties together high-throughput APIs, PostgreSQL correctness, Kafka/Flink freshness, Redis serving state, Kubernetes rollouts, observability, and incident defense into one operational contract.

Where This Fits

Lesson 0013 taught how to find saturated boundaries and protect the user promise under load. This lesson asks a prior question: what exactly is the user promise, and how do you know whether the system is meeting it?

Keep Reference 0014: SLOs, Error Budgets, and Operational Promises nearby. It is the compressed design checklist for this lesson.

Concise Answers From Lesson 0013

  1. Scale after diagnosis: adding pods helps only if the pod layer is the limiting resource.
  2. Work multiplies: traffic, fanout, latency, retries, and misses can turn one user action into many downstream operations.
  3. Backpressure protects: bounded queues, deadlines, shedding, and throttles prevent a limit from becoming collapse.
  4. Cache misses are capacity events: lower hit rate can become database pressure and user latency.
  5. Kafka lag is a symptom: the real question is whether user-visible derived state is still within its freshness promise.
  6. Metrics defend claims: throughput claims need latency, errors, saturation, freshness, and headroom.

The Big Idea

An SLO is the bridge between architecture and operations. It says: for this user journey, this measurable behavior must be good enough over this window. The Google SRE book chapter on Service Level Objectives frames SLIs as quantitative measures of service behavior, and SLOs as target values for those measures. The Google SRE Workbook chapter on implementing SLOs gives the practical recipe: define the user, pick the important journey, specify good events over total events, choose an implementation, and iterate.

The useful form is usually a ratio:

SLI = good events / total eligible events

SLO = target for that SLI over a window

error budget = total eligible events x (1 - SLO target)

If a checkout API has a 99.9% SLO over 10,000,000 eligible attempts in 30 days, the budget is 10,000 bad attempts. That number is not a trophy. It is a decision boundary: how much unreliability the team agreed users can tolerate while the product still moves forward.

The first trap is aiming for 100%. The SRE Workbook argues that 100% is usually the wrong reliability target because it makes change, cost, and real-world dependency failures impossible to reason about. The second trap is measuring components instead of users. CPU, pod restarts, cache hit rate, Kafka lag, and database waits are cause signals. They explain why the promise is in danger. They are not usually the promise itself.

Scenario: Revenue Platform With Real-Time Views

Suppose the system accepts subscription changes, writes a durable ledger row in PostgreSQL, publishes events through an outbox to Kafka, computes revenue projections in Flink, and serves merchant dashboards through Redis-backed read models.

Client/APISubscription writes and dashboard reads.
PostgresLedger facts, constraints, transactions.
Outbox/KafkaDurable event publication and replay.
FlinkStateful revenue projection and checkpoints.
Redis/UIFast reads with freshness boundaries.

A weak reliability posture says "Postgres is up, Kafka is green, and pods are running." A production SLO posture asks: can users make the critical write, can they see a fresh enough view, and can operators prove the system is inside the agreed promise?

Step 1: Choose User Journeys, Not Components

SLOs should start from the behavior users or downstream systems need, then map back to components for diagnosis. Different journeys deserve different promises.

User promise Good event Why not a component SLO?
Subscription change completes safely. The API commits exactly one intended state change or returns a valid business reject within 300 ms. HTTP 200 rate alone misses duplicate writes, timeout ambiguity, and correctness failures.
Merchant dashboard is fresh enough. A dashboard view uses projection data no older than five minutes. Kafka lag alone does not say whether a user saw stale revenue data.
Ledger data remains auditable. An accepted ledger write can later be read intact by audit and reconciliation paths. Database uptime alone does not prove the particular data users need is durable and readable.
Degraded mode is honest. The response either meets the normal data contract or clearly labels stale/degraded fields. A 200 response can still be bad if it silently omits required information.

Step 2: Separate SLI Specification From Implementation

The SRE Workbook makes a useful distinction: first specify what you mean, then choose how to measure it. The specification is the user-facing behavior. The implementation is the telemetry source.

Specification: proportion of dashboard views where revenue data is no older than five minutes.

Implementation A: server logs record dashboard response freshness at render time.

Implementation B: client telemetry reports freshness after the browser receives the response.

Implementation C: a periodic probe checks freshness for representative merchants.

Each implementation has blind spots. Server logs are cheap but may miss network or browser failures. Client telemetry is closer to user experience but requires instrumentation and its own reliable ingestion path. Probes are controlled and repeatable but may not represent all tenants or skewed traffic. Good SLO design states the blind spot instead of pretending measurement is perfect.

Step 3: Translate the Promise Into Budget

Error budget turns a percentage into operational permission. If the system serves 10,000,000 eligible dashboard views in 30 days and the freshness SLO is 99.5%, the service can have 50,000 stale views before missing the objective. If the checkout write SLO is 99.9% over 2,000,000 eligible attempts, the budget is 2,000 bad attempts.

This math changes priorities. A deployment causing 1,000 bad checkout attempts spends half of the checkout budget in one incident. The same number of stale dashboard views may be serious or ordinary depending on the dashboard's target, user base, and business promise.

budgeted bad rate = 1 - SLO target
observed bad rate = bad events / total events
burn rate = observed bad rate / budgeted bad rate

If a 99.9% SLO budgets a 0.1% bad rate, then a 1% observed bad rate burns the budget at 10x. That means the service is spending unreliability ten times faster than planned.

Step 4: Make Budget a Decision Tool

An SLO without an action policy becomes another dashboard number. The SRE Workbook is explicit that SLOs need stakeholder approval, ownership, and a policy for using the budget in prioritization.

Budget state What the team does Example backend decision
Healthy Ship with normal rollout controls. Proceed with a canary release and monitor checkout and freshness SLIs.
Fast burn Page and mitigate. Roll back a bad deploy, shed low-value dashboard reads, or switch to stale-labeled mode.
Slow burn Ticket and fix trend. Investigate rising Flink checkpoint duration before it becomes a freshness miss.
Exhausted Pause risky launches and repay reliability debt. Prioritize idempotency fixes, query-plan repair, consumer throughput, or rollback safety over new features.

This is where SLOs become senior-engineering judgment. The point is not to stop all change. The point is to decide which change is worth the remaining risk.

Step 5: Alert on Burn, Diagnose With Components

The SRE Workbook chapter on alerting on SLOs recommends alerting on meaningful error-budget burn rather than every noisy symptom. Burn-rate alerts answer: if this continues, how quickly will users lose the reliability we promised?

For high-traffic services, multiwindow burn-rate alerts are useful because they can page when budget is burning quickly and ticket when budget is burning slowly. The exact thresholds depend on service criticality, traffic volume, and page load, but the shape is stable:

fast burn over short + medium windows -> page
slow burn over long window           -> ticket
component metrics                    -> diagnosis, not the user promise

If the dashboard freshness SLO is burning, component signals help narrow cause: Kafka lag, hot partitions, Flink backpressure, checkpoint duration, sink latency, Redis stale-key age, database query waits, or a recent deployment. The SLO tells you the user promise is at risk. The components tell you where to intervene.

Defend the Resume Bullet

Suppose someone asks: "How did you make a real-time revenue platform production-ready?" A strong answer does not stop at "we had dashboards and alerts." It explains the operational contract.

Strong answer shape:

  1. We identified separate promises for write correctness, dashboard freshness, and audit durability.
  2. For each promise, we defined eligible events, good events, thresholds, and measurement sources.
  3. We treated Kafka lag, Redis hit rate, database waits, and pod health as cause metrics, not the SLO itself.
  4. We translated targets into error budgets so incidents and launches had a shared decision rule.
  5. We paged on fast budget burn, created tickets for slow burn, and used traces/logs/metrics to localize causes.
  6. We revised SLOs when user pain and measured reliability diverged, instead of treating the first version as sacred.

Reflection Questions

No homework is required. These are the checks that show whether you can reason from architecture to operational promises:

  1. Why should an SLO start from a user journey rather than a component dashboard?
  2. How would you define good and total events for a checkout write endpoint?
  3. Why is Kafka lag a weak SLO by itself for a merchant dashboard?
  4. What is the practical difference between SLI specification and SLI implementation?
  5. How does an error budget change release and incident decisions?
  6. Why might a slow burn create a ticket while a fast burn creates a page?

Concise answer key: users care about completed promises, not whether every component is green; checkout good events include correct commits or valid business rejects under deadline over eligible attempts; Kafka lag is only a cause signal because users care about visible state freshness; specification names the desired behavior while implementation names the telemetry source; error budget creates a shared rule for risk, rollout, and reliability work; fast burn threatens the SLO quickly, while slow burn often needs planned repair rather than immediate interruption.

Ask follow-up questions about any unclear piece. Useful SLO questions here are: "Who is the user?", "What event is eligible?", "What counts as good?", "What does the measurement miss?", and "What action changes when budget burns?"
