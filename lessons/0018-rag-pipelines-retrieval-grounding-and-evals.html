Lesson 0018

RAG Pipelines: Retrieval, Grounding, and Evals

The eighteenth mental model: a RAG system is not a prompt trick. It is a production pipeline that must retrieve the right evidence, constrain generation to that evidence, and prove quality with stage-specific evals.

Mission link: this is the judgment behind defending a RAG pipeline over API docs, support tickets, and integration logs with precision@5 and faithfulness evals.

Where This Fits

Lesson 0017 handled ownership and fencing. This lesson zooms back out into AI infrastructure: RAG combines ingestion, storage, retrieval, generation, evaluation, observability, privacy, and operations.

Keep Reference 0018: RAG Pipelines nearby. It is the compact checklist for turning a resume AI bullet into a defensible system design.

Concise Answers From Lesson 0017

  1. Lease versus token: a lease grants temporary ownership; a fencing token lets downstream resources reject stale owners.
  2. Lock is not enough: a paused holder can lose ownership, wake up late, and still attempt harmful side effects.
  3. Enforce near the resource: PostgreSQL can reject stale tokens with conditional updates or versioned rows.
  4. Consumer group scope: Kafka assigns partition ownership, but external side effects still need idempotency or fencing.
  5. Evidence matters: watch leadership churn, renewal failures, stale-token rejections, duplicate attempts, and repair success.

The Big Idea

The original RAG paper frames retrieval-augmented generation as combining a language model's internal knowledge with explicit external memory retrieved at inference time. In production, that idea becomes two connected pipelines: an ingestion pipeline that turns trusted sources into searchable evidence, and a query pipeline that retrieves, ranks, and uses that evidence to answer.

OpenAI's embedding docs describe embeddings as vectors whose distances measure relatedness between texts, and the retrieval docs show the practical serving shape: semantic search over vector stores, with chunks, metadata, scoring, and synthesis. The production lesson is broader than any one vendor: retrieval is a serving path with correctness, latency, freshness, privacy, and rollback concerns.

RAG path:

docs, tickets, logs, runbooks
  -> normalize, redact, chunk
  -> embed, index, version
  -> retrieve candidates
  -> filter and rerank
  -> synthesize grounded answer
  -> cite evidence
  -> evaluate retrieval and generation separately

The trap is treating "we added vector search" as the whole design. Vector search may return plausible context, but plausible context is not the same as authoritative context, current context, permitted context, or sufficient context.

Scenario: Billing Integration Debugger

Suppose you build an internal assistant for billing integration debugging. It can search API docs, resolved support tickets, and integration logs. Engineers ask questions such as "Why is this subscription update failing after migration?" or "Which retry strategy worked for this payment error pattern?"

SourcesDocs, tickets, logs.
IndexChunks, embeddings, metadata.
RetrieveFilters, top-k, rerank.
AnswerGrounded synthesis, citations.
EvalsPrecision, faithfulness, relevance.

This looks like an AI feature, but it is also a distributed systems feature. Data arrives from several owners, indexing is asynchronous, queries need authorization, latency has a budget, answers must be observable, and quality can regress after corpus changes.

Step 1: Design the Corpus Contract

Before chunk size or model choice, decide what each source is allowed to prove. The system should not treat a three-year-old support workaround as equal to the current API docs, and it should not retrieve another customer's logs just because the text is similar.

Source What it proves Required metadata
API docs Canonical behavior for a versioned public contract. Endpoint, version, product area, release date, owner.
Support tickets Real symptoms, historical fixes, and edge cases. Status, resolution, age, product, sensitivity label.
Integration logs Observed facts for a specific request, tenant, and time window. Tenant, trace ID, timestamp, retention, access scope.
Runbooks Operational procedure if reviewed and current. Owner, last reviewed date, incident class, rollback path.

That table is a production control. It tells retrieval which chunks may compete, which must be filtered, which should be weighted, and which should be cited as authoritative versus anecdotal.

Step 2: Treat Retrieval as a Serving Path

Retrieval has its own failure modes. Chunks can be too small to preserve meaning or too large to rank cleanly. Metadata can be missing. Indexing can lag. Deletions can be eventually consistent. A high-similarity chunk can still be the wrong authority.

Good retrieval design: chunk by user task, attach source metadata, filter by permissions and version, retrieve more candidates than you show, rerank when precision matters, and record which chunk IDs influenced the answer.

Weak retrieval design: dump every document into a vector store, use default top-k forever, and only measure whether the final answer feels reasonable.

OpenAI's retrieval guide notes that vector-store files may be processed asynchronously and that removed files can briefly appear in search results after deletion. Whether or not you use that exact API, the lesson transfers: indexing state, source version, and deletion behavior are part of your system contract.

Step 3: Constrain the Generator

The model should not be asked to "be helpful" in a vacuum. It needs an answer contract: use the retrieved context, distinguish authoritative docs from historical tickets, cite source IDs, and say when evidence is missing.

Answer contract:

Answer from retrieved sources only.
Prefer current API docs over old support tickets.
Use logs only for the tenant and trace IDs allowed by this request.
If the retrieved context is insufficient, say what evidence is missing.
Cite document IDs, ticket IDs, or trace IDs for operational follow-up.

Grounding is not just a prompt instruction. The system should log retrieval inputs, selected chunks, source versions, model output, citations, user feedback, and eval outcomes so a bad answer can be debugged like any other production failure.

Step 4: Measure the Split

Ragas and ARES both separate RAG evaluation into multiple dimensions. That split is the key engineering habit: do not collapse retrieval, grounding, and usefulness into one vague "accuracy" number.

Metric What it catches Likely repair
Precision@5 Top chunks are noisy, stale, or irrelevant. Better chunking, filters, source weights, reranking.
Context recall Needed evidence is absent from retrieved context. Hybrid search, query expansion, more top-k, corpus repair.
Faithfulness Answer includes unsupported or contradicted claims. Tighter answer contract, citations, abstention, judge review.
Answer relevance Answer is grounded but does not solve the user task. Improve task routing, prompt structure, or synthesis examples.
Serving health Quality is fine offline, but production is slow or stale. SLOs, tracing, cache policy, index freshness alerts, cost budgets.

A resume claim like "> 0.85 accuracy through precision@5 and faithfulness evals" becomes defensible only if you can explain the eval set, the labels or judges, the failure cases, and how the metric changed system behavior.

Step 5: Defend the Design

When challenged, avoid saying "we used LangChain and Pinecone." That names tools, not the production argument.

Weak answer: "We built a RAG bot over docs and tickets."

Strong answer: "We treated the assistant as a retrieval pipeline. API docs, resolved tickets, and integration logs were classified by authority, freshness, and permissions before indexing. Each chunk carried version, product, source, tenant, and sensitivity metadata. Retrieval used filters and reranking so current docs outranked old anecdotes, while the generator had to cite source IDs and abstain when evidence was missing. We evaluated retrieval with precision@5, generation with faithfulness and answer relevance, and production health with latency, token cost, index freshness, and user correction signals."

The shape is the point: corpus contract, retrieval controls, grounded generation, separate evals, and operational evidence.

Reflection Questions

No homework is required. These are the checks that show whether you can defend RAG as infrastructure instead of naming an AI framework:

  1. Why is "we indexed docs in a vector database" not enough to prove answer quality?
  2. What metadata would you attach to API docs, support tickets, and integration logs?
  3. How do precision@5 and faithfulness catch different failure modes?
  4. When should the assistant refuse to answer or ask for more evidence?
  5. What production signals would you watch after a large corpus update?

Concise answer key: vector indexing only creates candidates, not authority or grounding; useful metadata includes source type, version, product area, date, tenant, trace ID, permission scope, owner, and sensitivity; precision@5 catches bad retrieved chunks while faithfulness catches unsupported generated claims; the assistant should abstain when evidence is missing, stale, unauthorized, or contradictory; production signals include index freshness, retrieval relevance, answer feedback, latency, cost, error rate, token usage, and quality-regression evals.

Ask follow-up questions about any unclear piece. Useful review questions here are: "What can this source prove?", "What did retrieval miss?", "Which claim lacks evidence?", and "Which eval would catch this regression?"
