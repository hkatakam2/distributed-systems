Lesson 0006

Observability: Signals, Traces, and Debugging Across the Path

The sixth mental model: observability is not a pile of dashboards. It is the contract that lets you ask, "what did the user experience, where did the request or event go, and which component changed the outcome?"

Mission link: this is the practical layer behind production debugging, SLOs, OpenTelemetry, incident response, latency claims, Kafka lag investigations, cache freshness alerts, and defending whether a system is actually operable.

Where This Fits

Lesson 0005 explained how fast read paths use projection tables, Redis caches, and freshness contracts. This lesson asks the operational question: when the dashboard is slow, stale, or wrong, how do you see enough of the system to debug it?

Keep Reference 0006: Observability and Debugging Checklist nearby. It is the compressed checklist for this lesson.

Concise Answers From Lesson 0005

  1. PostgreSQL projection plus Redis: the projection is durable, query-shaped, versioned, and rebuildable; Redis is expendable acceleration for hot reads.
  2. "Real time" vs 30 seconds: "MRR is under 30 seconds old" is stronger because it is measurable, alertable, and honest about staleness.
  3. Replay without version guard: an older event can overwrite newer derived state and move the dashboard backward.
  4. Bypass Redis: bypass when a write just happened, data is too stale, the cache is unhealthy, or correctness requires source or projection truth.
  5. Cache and projection metrics: watch hit rate, misses, evictions, latency, hot keys, projection age, source lag, error rate, and drift.
  6. Rebuild without side effects: replay retained facts into a controlled target with emails, payments, webhooks, and partner calls disabled or guarded.

The Big Idea

Monitoring tells you when something important is broken. Observability gives you enough structured evidence to explain how work moved through the system and where it changed shape. In a backend system, that evidence usually comes from metrics, traces, logs, and domain checks.

Google's SRE monitoring chapter separates symptoms from causes and names four user-facing signals: latency, traffic, errors, and saturation. OpenTelemetry gives names to telemetry signals: traces show a request path, spans represent units of work, metrics measure runtime behavior, logs record events, and context propagation carries correlation across process boundaries.

Observable request and event path:

HTTP request with trace context
  -> API span: validate, authorize, write transaction
  -> outbox publish metric and log
  -> Kafka producer span or linked trace
  -> consumer span: process event and update projection
  -> Redis metric: hit, miss, set, eviction
  -> dashboard response with freshness metadata
  -> alert on user-visible breach, not random noise

The skill is not "add more logs." The skill is to decide which signal answers which production question.

Scenario: Merchant Dashboard Is Slow and Stale

Suppose a merchant reports that the dashboard loads slowly and shows old MRR. A weak debugging path opens five dashboards and guesses. A stronger path follows the user-visible symptom backward through the system.

UserLatency and freshness breach on dashboard API.
APITrace shows Redis miss and projection read time.
CacheMetrics show hit rate drop and evictions.
StreamLag and projection age show delayed updates.
SourceLogs confirm facts were committed and emitted.

That path keeps the investigation anchored. The first question is not "is Kafka lagging?" It is "what did the user experience?" Then you ask which internal signal explains that symptom.

Signals Have Jobs

Metrics, traces, and logs overlap, but they are not interchangeable. Treat them as different indexes into production behavior.

Signal Best at answering Common mistake
Metric How often, how slow, how full, how old, how many. Using only averages and missing tail latency or hot partitions.
Trace Where one request or operation spent time across services. Tracing HTTP calls but losing the causal path at queues and async work.
Log What discrete thing happened, with stable fields for search. Writing prose strings with no request ID, event ID, merchant ID, or version.
Domain check Whether the result is correct according to business truth. Thinking "200 OK" proves the dashboard number is right.

For the merchant dashboard, a metric can show that p99 latency crossed 500 ms. A trace can show the slow request spent 430 ms waiting on PostgreSQL after a Redis miss. A log can show which projection version was read. A domain check can show that projected MRR differs from source truth by 2.1 percent.

Start With Symptoms, Then Causes

For paging, symptoms beat causes. A page should usually mean users are affected or are about to be affected. "Dashboard freshness is older than 30 seconds for 5 percent of merchant reads" is better than "consumer lag is nonzero." Lag may explain a freshness breach, but lag alone is not always a user-visible problem.

Symptom-first alert shape:

  1. Latency: dashboard p95 or p99 exceeds the product budget.
  2. Traffic: request rate, event rate, and cache lookup rate changed sharply.
  3. Errors: explicit failures, bad responses, and policy failures such as stale data.
  4. Saturation: constrained resource is nearing the point where latency or errors rise.

Cause metrics still matter. CPU, pool saturation, Kafka lag, checkpoint duration, Redis evictions, and database lock waits are excellent debugging signals. They should support the investigation instead of creating noisy pages by themselves.

Trace the Critical Path

A trace is useful when it follows the work boundary the user cares about. For synchronous APIs, that boundary is usually one request. For event-driven systems, the boundary may cross an outbox, Kafka topic, consumer group, stream job, projection table, and cache invalidation path.

OpenTelemetry spans can be server, client, producer, consumer, or internal spans. That vocabulary matters because async work breaks the simple parent-child shape: the producer may finish before the consumer starts. In that case, use span links or equivalent correlation to connect the cause without pretending the consumer is a synchronous child.

trace_id=abc
HTTP POST /subscriptions/cancel
  span api.cancel_subscription
  span db.transaction
  span outbox.insert
  span kafka.produce billing_events

linked trace_id=def, link=abc
consumer billing_events partition=7 offset=120391
  span projection.update merchant_dashboard_summary
  span redis.del dash:{merchant_id}

The goal is causal visibility: from a customer action to the event it produced, to the projection it changed, to the cached value a later read served.

Use Stable Fields

Unstructured logs force humans to read text. Structured logs and span attributes let tools join evidence. Do not log sensitive data, but do include stable identifiers that let you reconstruct the path.

Field Why it helps Where it appears
trace_id Correlates logs, spans, and metrics for one operation. HTTP request, producer, consumer, projection update.
request_id Names one externally observed API call. Gateway, API logs, response headers.
event_id Supports dedupe, replay debugging, and side-effect guards. Outbox row, Kafka record, consumer logs.
merchant_id Finds hot keys, tenant-specific impact, and projection drift. API, stream job, projection, cache.
source_version Shows whether stale writes or replay moved state backward. Events, projection rows, dashboard response.
as_of_event_time Turns "real time" into a measurable freshness claim. Projection table, API response, freshness metrics.

Debug by Narrowing the Path

Google's troubleshooting chapter frames debugging as iterating between observations, hypotheses, and tests. For distributed systems, a practical version is path narrowing: split the end-to-end path into segments and find the first segment where expected behavior becomes actual bad behavior.

Path-narrowing loop:

  1. Name the user-visible symptom and time window.
  2. Find one concrete affected request, merchant, event, or trace.
  3. Walk the path backward: response, cache, projection, consumer, topic, outbox, source transaction.
  4. At each boundary, compare expected input, actual input, expected output, and actual output.
  5. Prefer tests that rule out a whole class of causes.
  6. Mitigate user impact before spending too long on root cause.

That last point matters. During a real incident, restoring service and preserving evidence beat perfect root-cause analysis. You can disable a risky cache path, route reads to the projection, or pause a bad deploy while keeping the notes needed for later diagnosis.

What to Put on the Dashboard

A useful dashboard mirrors the system map. It should show user symptoms first, then the major internal causes that explain those symptoms.

Layer Symptom signal Cause signal
API p95/p99 latency, error rate, stale response rate. DB wait, Redis wait, pool saturation, deploy marker.
Kafka Event age for user-visible projections. Consumer lag by partition, produce errors, hot keys.
Stream job Projection freshness and dropped or late corrections. Checkpoint duration, backpressure, watermark lag, restart count.
Projection Stale or wrong dashboard rows. Upsert errors, version rejections, lock waits, drift checks.
Redis Cache-induced latency and miss bursts. Hit rate, evictions, memory, hot keys, connection errors.

How to Defend the Resume Bullet

Suppose someone asks: "How did you know the real-time dashboard was healthy in production?" A strong answer names the user contract, the telemetry model, and the debugging path.

Strong answer shape:

  1. We defined user-visible SLOs for dashboard latency, error rate, and freshness, not just internal job health.
  2. Responses included freshness metadata such as as_of_event_time, so stale data was measurable.
  3. Metrics covered the four golden signals at the API plus domain metrics such as projection age and drift.
  4. OpenTelemetry traces carried context across HTTP and database calls, and async events used producer and consumer spans or links.
  5. Structured logs included request IDs, event IDs, tenant IDs, versions, offsets, and projection update results.
  6. Dashboards were symptom-first, with internal cause panels for Kafka lag, checkpoints, Redis, PostgreSQL, and deploys.
  7. During incidents, we mitigated user impact first, then narrowed the path from response to cache to projection to stream to source truth.

Reflection Questions

No homework is required. These are the checks that show whether you can reason about production observability:

  1. Why is "dashboard freshness breach" a better page than "Kafka lag is nonzero"?
  2. For a slow dashboard request, which evidence would you want from metrics, traces, logs, and domain checks?
  3. What breaks if trace context is not propagated from the API into async event processing?
  4. Which fields would you include in structured logs for a projection update?
  5. How would you debug a dashboard that is fast, returns 200, but shows the wrong MRR?
  6. What is one mitigation you might apply before finishing root-cause analysis?

Ask follow-up questions about any unclear piece. Useful debugging questions here are: "What did the user experience?", "Which request or event proves it?", "Where did the path first diverge?", and "What evidence would rule out this hypothesis?"
