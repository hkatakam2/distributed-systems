Partitions, Consumer Groups, and Replay

The Big Idea

A log is not a single global timeline. In production it is usually split into partitions. Each partition is an ordered append-only sequence, and each record receives an offset inside that partition. Kafka's consumer documentation treats the offset as the consumer's position in that partition, while its design docs frame the log as the replayable storage structure behind Kafka's throughput and recovery model.

The key move is accepting local order instead of demanding global order. If all events for subscription_sub_123 go to the same partition, that subscription's lifecycle can be processed in order. Events for unrelated subscriptions can be processed in parallel on other partitions.

Log consumption shape:

outbox relay publishes event
  -> topic chooses partition from key
  -> record gets partition offset
  -> consumer group owns partitions
  -> handler applies side effect
  -> consumer commits offset
  -> lag and event age reveal freshness

Partitions: The Unit of Order and Scale

A topic can have many partitions. A producer typically assigns a record to a partition using the record key, although custom partitioners and keyless records can change that behavior. The design decision is not "Kafka or not Kafka." The real decision is: which facts must be ordered with which other facts?

Key choice What it preserves What it costs
subscription_id Lifecycle order for one subscription. Merchant aggregates must combine many independent ordered streams.
merchant_id Order for all billing events of one merchant. Large merchants can become hot partitions.
sku_id Inventory updates for one SKU stay ordered. High-volume SKUs can dominate one partition.
random key Load spreads evenly. Related events can arrive out of order.

There is no free global order. Global order usually means one partition or expensive coordination. One partition is simple, but it caps consumer parallelism and makes one slow partition everyone's problem. Good systems choose the smallest ordering scope that preserves correctness.

Consumer Groups: One Logical Subscriber, Many Processes

Kafka consumer groups let many processes act as one logical subscriber. The official consumer docs describe the important constraint: within a group, each partition is assigned to exactly one consumer. That is what prevents two workers in the same group from racing over the same partition stream.

Topicbilling_events has 12 partitions.
Groupmrr-projector has 4 consumers.
AssignEach consumer receives about 3 partitions.
ScaleAdding consumers helps until partitions run out.
RebalanceFailure or membership change moves partitions.

Two different consumer groups can both read the same topic without duplicating stored data. For example, mrr-projector, search-indexer, and audit-archiver can each consume all billing events for different purposes. Inside each group, the partitions are divided among that group's workers.

This gives you both queue-like and pub/sub-like behavior. One group spreads work like a queue. Multiple groups independently subscribe like pub/sub.

Offsets: What Recovery Actually Means

A consumer has a current position and a committed position. The current position moves as records are returned by poll. The committed position is the durable recovery point the consumer group can resume from after restart. This distinction is where many production bugs hide.

Commit timing Failure window Delivery shape
Commit before processing Crash after commit can skip work forever. At-most-once, usually unsafe for business facts.
Process, then commit Crash after side effect but before commit can replay work. At-least-once, requires idempotent effects.
Atomic sink and offset transaction Only works when all participating systems share the transaction. Exactly-once for that bounded boundary.

The common production default is process first, commit after. That means duplicates are normal after failure. The answer is not wishful thinking about "exactly once"; it is idempotent handlers, event IDs, versions, conditional writes, and reconciliation.

Scenario: Rebuilding MRR Materialization

Suppose the MRR projection in Redis is wrong because a bug undercounted discounts. A log-based architecture gives you a repair path: fix the projection code, start from an older offset or a fresh consumer group, replay billing events, and rebuild the derived state.

Replay is powerful because the log keeps facts separate from the derived read model. But replay is only safe when old events are still retained, schemas can still be decoded, side effects are controlled, and the projection is deterministic enough to rebuild the same state from the same facts.

Replay checklist:

  1. Choose whether to replay into a shadow store or overwrite the live projection.
  2. Start from a known offset, timestamp, or empty materialized view.
  3. Disable irreversible side effects such as emails, external payments, and partner webhooks.
  4. Apply events idempotently using event IDs, aggregate versions, or full recomputation.
  5. Compare rebuilt aggregates with database truth, old projection, and sampled merchant totals.
  6. Cut over only after lag, freshness, and correctness checks are acceptable.

Lag, Hot Partitions, and Backpressure

Consumer lag is the distance between produced records and consumed records for a group, usually inspected per partition. It is useful, but it is not the whole story. A group can have low total lag while one hot partition is far behind, or low record lag while old events are stuck behind a few expensive messages.

For production systems, pair lag with event age, processing latency, retry counts, DLQ growth, and downstream saturation. The user-visible question is not "is Kafka healthy?" It is "how old is the data being served, and which partition, key, dependency, or deployment is making it stale?"

How to Defend the Resume Bullet

Suppose someone asks: "How did the inventory pipeline handle millions of events per day?" A strong answer names the partitioning and recovery model, not just the broker.

Strong answer shape:

  1. We keyed high-throughput inventory facts by the smallest correctness boundary, usually SKU or fulfillment-center SKU.
  2. Kafka partitions gave parallelism while preserving per-key order where allocation correctness depended on it.
  3. Consumer groups let each downstream workflow scale independently without duplicating stored topic data.
  4. Consumers processed records before committing offsets, so duplicate handling was part of the design.
  5. Slow or malformed records used retry, backoff, DLQ routing, and reconciliation instead of blocking the whole pipeline forever.
  6. Operations watched per-partition lag, event age, hot keys, DLQ count, retry rate, and downstream write latency.

Reflection Questions

No homework is required. These are the checks that show whether you can reason about log consumption:

  1. For subscription lifecycle events, why is global ordering usually unnecessary?
  2. If a topic has 12 partitions and one consumer group has 20 consumers, how many consumers can actively read that topic?
  3. What can happen if a consumer commits an offset before updating Redis?
  4. What can happen if a consumer updates Redis and crashes before committing the offset?
  5. How would you detect a hot partition in an MRR pipeline?
  6. When replaying old events, which side effects must be disabled or guarded?

Ask follow-up questions about any unclear piece. Useful debugging questions here are: "What is the key?", "Which partition is behind?", "What offset committed?", "Can this side effect run twice?", and "Can we replay without harming users?"
