Lesson 0010

Transaction Isolation and Concurrency Control

The tenth mental model: correctness is not only about where data is replicated. It is also about what happens when many requests try to read and write the same authority at the same time.

Mission link: this is the judgment behind PostgreSQL transactions, inventory reservation, billing ledgers, idempotency tables, safe retries, outbox writes, and defending why a production write path stays correct under concurrent traffic.

Where This Fits

Lesson 0009 asked which replica is allowed to accept or answer state. This lesson zooms inside one authoritative database boundary and asks: once a request reaches the authority, what prevents concurrent requests from violating the business rule?

Keep Reference 0010: Transaction Isolation and Concurrency Control nearby. It is the compressed decision sheet for this lesson.

Concise Answers From Lesson 0009

  1. Replicas complicate reads: durability improves because more copies survive failure, but reads must know which copy is fresh enough.
  2. Rejecting a write: rejection is better when accepting during a partition could violate money, inventory, auth, or ordering invariants.
  3. R + W > N limit: overlap helps, but membership, versioning, repair, conflict handling, and failure detection still matter.
  4. Safely stale data: dashboards, recommendations, and search can often be stale; ledgers, reservations, and access decisions usually cannot.
  5. Materialized metadata: attach source offset, source version, as-of timestamp, projection version, and freshness age.
  6. Convergence metrics: watch lag, drift, conflict count, replay backlog, repair backlog, and stale-read age.

The Big Idea

A transaction gives a group of operations an all-or-nothing commit boundary. Isolation defines what that group can observe while other transactions run at the same time. Concurrency control is how the database preserves the isolation contract through snapshots, locks, constraints, aborts, and retries.

PostgreSQL's transaction isolation documentation defines the standard phenomena: dirty reads, nonrepeatable reads, phantom reads, and serialization anomalies. It also explains PostgreSQL's three real behaviors: Read Committed, Repeatable Read, and Serializable. The explicit locking docs explain row locks and SELECT FOR UPDATE. The constraints docs and INSERT / ON CONFLICT docs show a production habit: express invariants in the database when you can.

Concurrent write decision path:

business invariant
  -> rows and tables involved
  -> simplest database guard
  -> expected conflict outcome
  -> retry boundary
  -> observability for contention and correctness

The practical skill is to stop saying "we used a transaction" as if that answers the question. A senior answer says which invariant the transaction protects, which isolation or lock behavior is required, and what the application does when the database rejects a concurrent execution.

Scenario: Reserve Inventory and Emit an Event

Suppose checkout reserves one unit of inventory and emits an event for downstream billing and fulfillment. Two customers can hit the same SKU at the same time, and retries can send the same client request more than once.

RequestClient sends idempotency key.
DedupUnique key records one logical attempt.
ReserveInventory update must not go negative.
OutboxEvent commits with state change.
RetryConflicts return known result or retry safely.

The invariant is not "run SQL in a transaction." The invariant is: one logical checkout should reserve at most once, inventory must not go below zero, and any successful reservation must have a corresponding outbox event.

Pick the Smallest Correct Guard

The strongest tool is not always the best first tool. The right tool depends on the shape of the invariant.

Invariant Useful guard Why it works
Same request must not create two reservations. UNIQUE (merchant_id, idempotency_key) plus ON CONFLICT. The database arbitrates duplicates even when app servers race.
Inventory must not go below zero for one SKU row. UPDATE inventory SET available = available - 1 WHERE sku = $1 AND available > 0. Conflicting row updates wait; the predicate is rechecked against the current row.
Only one active plan per merchant. Unique or partial unique index if the condition fits the schema. A constraint is more reliable than checking in application code before insert.
At least one operator must remain on call. Serializable transaction, or lock a concrete guard row before changing membership. The rule depends on a set, so row-by-row snapshots can be misleading.

If a constraint can express the invariant, prefer that. If one conditional statement can express it, prefer that. Use explicit locks or Serializable isolation when the invariant spans a changing set of rows that cannot be reduced to a simple constraint.

Read Committed: Each Statement Gets Its Own View

Read Committed is PostgreSQL's default isolation level. A plain SELECT sees data committed before that statement began. Two SELECT statements inside the same transaction can see different results if another transaction commits between them.

Good fit: a simple keyed update where every statement names the exact row and carries the predicate that protects the invariant.

BEGIN;

WITH attempt AS (
  INSERT INTO request_dedupe (merchant_id, idempotency_key, status)
  VALUES ($1, $2, 'started')
  ON CONFLICT (merchant_id, idempotency_key) DO NOTHING
  RETURNING id
),
reserved AS (
  UPDATE inventory
  SET available = available - 1
  WHERE sku = $3
    AND available > 0
    AND EXISTS (SELECT 1 FROM attempt)
  RETURNING sku
)
INSERT INTO outbox (event_type, aggregate_id, payload)
SELECT 'inventory_reserved', sku, $4
FROM reserved;

COMMIT;

This shape still needs application handling for zero rows inserted into outbox: either the request was a duplicate, or no inventory remained. The trap is moving the predicate into application memory: SELECT available, compute in code, then later UPDATE inventory SET available = new_value. Under concurrency, that shape can overwrite a fact learned by another transaction. Put the invariant in the statement or in a constraint.

Repeatable Read: Stable Snapshot, Not Full Safety

Repeatable Read gives a transaction a stable snapshot from the start of the transaction's first real statement. In PostgreSQL, that prevents nonrepeatable reads and phantoms. But it can still allow serialization anomalies: the final result may not match any one-at-a-time ordering of the same transactions.

Write skew shape:

rule: at least one operator must remain on call

T1 reads: Alice on call, Bob on call
T2 reads: Alice on call, Bob on call
T1 turns Alice off call
T2 turns Bob off call
both commit under a snapshot-isolation style contract

final state: nobody is on call

Each transaction made a locally reasonable choice from its snapshot. Together they violated the cross-row invariant. The fix is not "try Repeatable Read harder." The fix is to make the conflict concrete: use Serializable with retries, lock a shared guard row, or redesign the rule into a constraint the database can enforce.

Serializable: Correct or Retry

PostgreSQL Serializable isolation emulates serial execution for committed transactions. It does not mean every transaction succeeds. It means the database may abort one transaction when the concurrent pattern cannot be proven equivalent to a safe serial order.

Choice What it buys What it costs
Serializable transaction Cross-row business rules can be protected without manually locking every predicate. The app must retry the whole transaction after serialization failure.
Short transaction body Less time for conflicts, locks, and stale decisions to accumulate. You must keep network calls, user waits, and slow work outside the boundary.
Generic retry handler Deadlocks and serialization conflicts become expected control flow. The transaction body must be idempotent from the caller's point of view.

The retry boundary matters. If a transaction fails with a serialization error, retry the whole transaction from the beginning so it reads a new consistent view. Retrying only the last statement can reuse a decision made from a snapshot the database has already rejected.

Locks: Make the Conflict Concrete

SELECT FOR UPDATE locks the rows returned by a query as though they are about to be updated. Other transactions that try to update, delete, or acquire conflicting locks on those rows must wait until the transaction ends.

Useful pattern: lock the smallest row that represents the contested resource.

BEGIN;

SELECT *
FROM merchant_limits
WHERE merchant_id = $1
FOR UPDATE;

-- Now recalculate and update related rows while every
-- conflicting limit change queues behind the same row.

COMMIT;

Row locks do not block ordinary reads. They block conflicting writers and lockers. The operational cost is waiting and possible deadlocks. Acquire locks in a consistent order, keep transactions short, and do not hold locks while waiting on an external API, human input, or a long computation.

Outbox and Isolation Belong Together

The transactional outbox from Lesson 0002 only works if the state change and the event row commit in the same database transaction. Isolation decides whether the state change itself was valid under concurrency.

Question Weak answer Stronger answer
Can duplicate requests reserve twice? App server checks an in-memory request cache. Unique idempotency key in the database.
Can inventory go negative? Read quantity, subtract in code, write back later. Conditional update that succeeds only when enough stock remains.
Can event publish without state? Commit state, then call Kafka directly. Write outbox row in the same transaction, then publish asynchronously.
Can retries double-publish? Assume the worker runs once. Outbox event id plus idempotent consumer or producer behavior.

Observe Contention as a Correctness Signal

Concurrency bugs are not only logical. They have operational fingerprints. A healthy system can have some waiting and retries. A struggling system shows rising waits, aborts, long transactions, deadlocks, and retry storms.

Lock waitsWhich query and relation block progress?
DeadlocksWhich code paths acquire locks in different orders?
40001Can serialization retries eventually succeed?
DurationWhich transactions hold state too long?
ConflictsAre idempotency and uniqueness conflicts expected?

In an interview or design review, metrics make the answer credible. "We used Serializable" is incomplete. "We used Serializable for this cross-row invariant, retried SQLSTATE 40001 at the transaction boundary, and watched serialization failures, retry success rate, and transaction duration" is a production answer.

How to Defend the Resume Bullet

Suppose someone asks: "How did you prevent duplicate billing or overselling when requests retried and multiple workers ran concurrently?" A strong answer names the invariant and the database mechanism.

Strong answer shape:

  1. Each externally retried operation carried an idempotency key, enforced by a unique constraint in PostgreSQL.
  2. Single-row inventory or balance changes used conditional updates so the invariant lived in the SQL statement, not only in application memory.
  3. Cross-row rules used Serializable transactions with whole-transaction retries, or a concrete guard row locked with SELECT FOR UPDATE.
  4. The outbox event was inserted in the same transaction as the authoritative state change.
  5. Consumers were idempotent, so outbox publish retries could not double-apply downstream side effects.
  6. We monitored lock waits, deadlocks, serialization failures, retry success, duplicate-key conflicts, and transaction duration.

Reflection Questions

No homework is required. These are the checks that show whether you can reason about concurrent database writes:

  1. What is the difference between "using a transaction" and naming the invariant protected by the transaction?
  2. Why is a unique constraint stronger than checking for duplicates in application code?
  3. When is a conditional UPDATE better than SELECT then UPDATE?
  4. Why can Repeatable Read still be unsafe for cross-row business rules?
  5. Why must Serializable failures retry the whole transaction?
  6. What should you measure to know whether concurrency control is hurting production?

Concise answer key: a transaction boundary is not the same as a correctness argument; constraints arbitrate races inside the authority; conditional updates keep the predicate with the write; snapshot transactions can miss cross-row conflicts; serialization failures reject the whole observed execution; watch waits, aborts, retries, deadlocks, conflicts, and transaction duration.

Ask follow-up questions about any unclear piece. Useful concurrency questions here are: "What is the invariant?", "Can a constraint express it?", "What rows are locked?", "What retries the transaction?", and "What metric proves contention is controlled?"
