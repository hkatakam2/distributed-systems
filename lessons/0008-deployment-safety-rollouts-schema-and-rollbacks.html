Lesson 0008

Deployment Safety: Rollouts, Schema Changes, and Rollbacks

The eighth mental model: deployment is controlled change. A production engineer does not merely push code; they manage artifact identity, compatibility, traffic exposure, health gates, observability, and recovery.

Mission link: this is the practical layer behind Kubernetes, CI/CD, schema migrations, feature flags, incident rollback, and defending how a backend system changes safely while serving real users.

Where This Fits

Lesson 0007 explained runtime controls for dependency failure and overload. This lesson asks the adjacent production question: how do you introduce a new version without creating the failure yourself?

Keep Reference 0008: Deployment Safety Checklist nearby. It is the compressed decision sheet for this lesson.

Concise Answers From Lesson 0007

  1. Deadline versus timeout: a deadline carries the remaining user budget across the whole call chain; local timeouts can overspend the total budget.
  2. Safe write retry: retry only when duplicate execution is harmless through idempotency keys, event IDs, version guards, or a read-only operation.
  3. Backoff and jitter: backoff slows repeated attempts, and jitter spreads clients so recovery is not hit by synchronized retry waves.
  4. Optional dependency down: fail fast or open the breaker, then serve the core dashboard with an honest degraded response.
  5. Bulkhead targets: isolate checkout writes from dashboard reads, projection workers from webhook delivery, tenants from one another, and optional features from core paths.
  6. Retries worsening outage: watch retry attempts per original request, retry budget exhaustion, dependency saturation, tail latency, errors, and recovery time.

The Big Idea

A deploy is not one change. It is several change planes moving together: code artifact, configuration, schema, data, traffic routing, and telemetry. Most painful rollouts fail because one plane changed faster than the others could tolerate.

The Kubernetes Deployment documentation describes how Deployments manage ReplicaSets and rolling updates. The Kubernetes probe guide separates readiness, liveness, and startup checks. PostgreSQL's ALTER TABLE and CREATE INDEX docs show why database changes need their own rollout thinking. Pete Hodgson's feature toggle taxonomy gives a practical way to separate deployment from release.

Safe change path:

build immutable artifact
  -> apply backward-compatible schema expansion
  -> deploy new pods with readiness gates
  -> expose small cohort or flag
  -> compare symptoms, causes, and domain correctness
  -> increase exposure or rollback
  -> contract old schema only after rollback is no longer needed

The engineering skill is to make every step reversible or at least survivable. "Pods are running" is not success. Success means users are still within the contract and the business result is still correct.

A weak deployment changes all of this at once and hopes. A stronger deployment lets old and new code coexist, limits traffic exposure, and keeps the rollback path alive until the new path has been observed under real load.

Separate Deployment From Release

Deployment means the code exists in production. Release means users experience the new behavior. Feature flags, canary cohorts, and config-driven routing let you deploy a new path while keeping most traffic on the old path.

Move What it controls Production judgment
Deploy image Which code version runs in pods or tasks. Use immutable versions and record commit, build, and config.
Flip flag Which behavior a request, tenant, region, or cohort sees. Expose the smallest useful slice first, then widen with evidence.
Change config Runtime parameters such as limits, timeouts, or feature settings. Audit it like code because it can break production just as quickly.
Run migration Database, topic, cache, or message shape. Design compatibility before code depends on the new shape.

Kubernetes ConfigMaps are one mechanism for decoupling environment-specific configuration from images, but the deeper principle applies everywhere: when behavior can change without rebuilding code, that behavior needs ownership, review, metrics, and rollback.

Kubernetes Rollouts: Replace Pods Gradually

A Deployment creates and manages ReplicaSets. A new rollout is triggered by changing the pod template, such as the container image or template labels. With the default rolling update strategy, Kubernetes gradually scales up new pods and scales down old pods. maxSurge controls how many extra pods can exist during the rollout; maxUnavailable controls how much desired capacity can be unavailable.

What a strong rollout specifies:

  1. Enough replicas and capacity headroom for old and new pods to overlap.
  2. A readiness probe that keeps unready pods out of Service traffic.
  3. A liveness probe only for states where restart is a useful repair.
  4. A startup probe or initial delay for slow-starting containers.
  5. A progress deadline or deployment monitor that catches stuck rollouts.
  6. Deploy markers in telemetry so symptoms can be compared by version.

The common mistake is to treat liveness as a general health check. If a liveness probe fails because a database is briefly slow, Kubernetes may restart healthy app processes during a dependency incident. Readiness is the gate for traffic. Liveness is for "this container should be restarted."

Schema Changes: Expand Before You Depend

Database changes have different failure modes from code changes. ALTER TABLE can require locks, constraints can scan existing data, indexes can add I/O load, and old application versions may still be running while the schema changes. The safest general pattern is expand and contract.

Phase Trial revenue example Rollback value
Expand Add nullable trial_conversion_revenue_cents to the projection. Old code ignores it; new code can start writing it.
Write both Stream job writes old dashboard totals and the new metric. Readers can switch back without losing the old representation.
Backfill Fill historical merchants in bounded batches with pause and resume. Bad batches can stop without corrupting live writes.
Switch reads API returns the new field for internal users, then a small cohort. Flag can be turned off before reverting the image.
Contract Remove old compatibility logic after no consumers need it. Done only after rollback to the old path is no longer required.

For large tables, prefer migration steps that are small, observable, and pauseable. PostgreSQL supports options such as validating some constraints after creation and building indexes concurrently, but every production migration still needs workload-specific review because reduced blocking can mean more total work and more background load.

Message And Cache Compatibility

In an event-driven system, schema compatibility is not only a database problem. Old consumers may read new events. New consumers may replay old events. Cache readers may see payloads written by an older code version.

new producer emits event_v3
  old consumer must ignore optional field or route to dead letter safely
  new consumer must handle missing field during replay of event_v2
  projection must use version guards so replay cannot move state backward
  Redis payload should include schema version or use versioned keys

The rule is simple: any boundary with independent deploy timing needs compatibility. That includes APIs, events, database rows, cache payloads, files, partner webhooks, and scheduled jobs.

Observe The Rollout, Not Just The Pods

A rollout monitor should compare the new version against the old version using the signals from Lesson 0006 and the controls from Lesson 0007.

Signal Rollout question Trial revenue example
Latency Did the new version add request or stream processing time? Dashboard p95 and p99 by version.
Errors Did exceptions, timeouts, or validation failures rise? API 5xx, consumer failures, projection upsert errors.
Saturation Did the change consume extra DB, Redis, CPU, or queue capacity? DB locks, I/O, connection pools, consumer lag.
Freshness Did the new computation delay the dashboard? Projection age and cache age by merchant cohort.
Correctness Does the new number match source truth? Trial revenue drift checks against billing facts.

This is where deployment safety becomes operational judgment. You should know before the rollout what metric will stop it, what metric will allow the next cohort, and what metric would require rollback versus roll forward.

Rollback Is A System Design Problem

Rollback sounds like "put the old image back." In distributed systems, that is often incomplete. The old image may not understand new rows, new events, new cache payloads, or new config. A rollback plan has to name every plane that changed.

Rollback decision example:

  1. Flag off the new metric first so no more users enter the new read path.
  2. Rollback API pods if error rate or latency remains elevated.
  3. Pause or rollback stream job if it writes bad projection values.
  4. Invalidate affected Redis keys if bad payloads were cached.
  5. Keep expanded columns until old and new paths are stable.
  6. Run a correction or replay only if the projection data is wrong.

Sometimes rolling forward is safer than rolling back, especially if the schema or data has already moved. Senior judgment is not "always rollback." It is choosing the recovery path with the smallest user impact and the clearest correctness story.

How to Defend the Resume Bullet

Suppose someone asks: "How did you deploy backend changes safely?" A strong answer names compatibility, blast radius, health gates, and recovery.

Strong answer shape:

  1. We built immutable artifacts and tied every deploy to a commit, image, config version, and dashboard marker.
  2. For schema and event changes, we used expand-and-contract so old and new code could coexist.
  3. We deployed through Kubernetes rolling updates with readiness probes, controlled surge and unavailable capacity, and rollout progress monitoring.
  4. Risky behavior was released separately through flags or canary cohorts, not exposed globally just because code was deployed.
  5. Rollout gates watched user latency, error rate, saturation, freshness, and domain correctness by version or cohort.
  6. Rollback plans covered code, config, stream jobs, cache payloads, data correction, and whether the old version could read new data.

Reflection Questions

No homework is required. These are the checks that show whether you can reason about deployment safety:

  1. Why is "pods are running" not enough evidence that a deployment is healthy?
  2. How does a feature flag separate deployment from release?
  3. What compatibility problems can appear between old and new code during a rolling update?
  4. Why does expand-and-contract make database rollback easier?
  5. When would rolling forward be safer than rolling back?
  6. What signals would you use to decide whether a canary should continue, pause, or rollback?

Ask follow-up questions about any unclear piece. Useful deployment questions here are: "Can old and new versions coexist?", "What changed besides code?", "What limits blast radius?", "What proves correctness?", and "What exactly would rollback do?"
