Lesson 0012

Online Schema Migrations and Backfills

The twelfth mental model: changing stored data is not a one-time SQL task. It is a rollout across code, schema, historical rows, indexes, constraints, replicas, and rollback paths.

Mission link: this is the judgment behind production PostgreSQL migrations, live backfills, replay-safe ledgers, idempotency tables, feature rollouts, and defending how a backend system evolves without downtime.

Where This Fits

Lesson 0011 taught you to diagnose query performance from plans, indexes, and production cost. This lesson asks the next operational question: how do you safely change the table and historical data that those queries depend on?

Keep Reference 0012: Online Schema Migrations and Backfills nearby. It is the compressed rollout checklist for this lesson.

Concise Answers From Lesson 0011

  1. "Add an index" is incomplete: name the query path, access pattern, before plan, after plan, and write-side cost.
  2. Index Cond versus Filter: an index condition narrows index access; a filter checks rows already reached.
  3. Sequential scans can be right: broad reads can be cheaper than many random index-driven heap visits.
  4. ORDER BY ... LIMIT matters: the best index can emit the first page directly instead of sorting a large candidate set.
  5. Statistics can beat indexes: stale or insufficient estimates can make the planner choose the wrong path.
  6. Live index risk: watch locks, I/O, replication lag, write latency, plan choice, and index usage.

The Big Idea

An online migration has three clocks. Old code is still running, new code is arriving gradually, and historical rows still have the old shape. A migration is safe only when every clock can coexist for the whole rollout.

PostgreSQL's ALTER TABLE documentation is explicit that table-definition changes have lock behavior, validation scans, and rewrite risks. The UPDATE documentation warns that large updates can cause table bloat, replica lag, and lock contention, so batching can be appropriate. The CREATE INDEX documentation explains why concurrent index builds trade less write blocking for more total work.

Safe stored-data change path:

expand schema
  -> deploy compatible writers
  -> backfill historical rows in batches
  -> validate data and performance
  -> enforce constraints and indexes
  -> switch reads gradually
  -> contract old shape after rollback is no longer needed

The skill is to avoid making the database change the irreversible center of the deploy. First create compatibility, then move data, then enforce, then remove compatibility.

Scenario: Add Source Event IDs to Ledger Rows

Suppose your payment ledger was originally written from API calls and stream events, but old rows do not store the source event ID. During replay and incident debugging, you now need every ledger row to carry source_event_id so operators can trace a row back to the exact event that produced it.

SchemaAdd nullable field first.
WritersNew code fills it.
BackfillOld rows get values.
ValidateNulls and drift go away.
EnforceConstraints and indexes land.

A weak plan is: add NOT NULL, run one giant update, deploy code, and hope. A production plan treats each step as a reversible exposure decision.

Step 1: Expand Without Depending on It

Start by adding structure that old code can ignore and new code can populate. For this scenario, that means a nullable column and no immediate reader dependency:

ALTER TABLE ledger_entries
ADD COLUMN source_event_id text;

The ALTER TABLE docs say that most subforms acquire an ACCESS EXCLUSIVE lock unless noted otherwise, so even a fast metadata change should be reviewed for lock timing. They also distinguish fast column additions from rewrite-heavy ones: a non-volatile default can avoid rewriting existing rows, while volatile defaults, some generated columns, constrained domain types, and many type changes can rewrite the table and its indexes.

Production rule: adding a column is not automatically dangerous, but depending on it immediately is.

Old pods, old jobs, old consumers, and old rollback images must tolerate the expanded schema. This is the same compatibility principle from Lesson 0008, now applied to persistent state.

Step 2: Make New Writes Compatible

Deploy writers that populate source_event_id for new ledger rows, while readers still tolerate missing values. Instrument the null rate before starting the historical backfill.

Question Strong answer Why it matters
Can old code still run? Yes, the new column is nullable and ignored by old code. Rollback does not fail because the schema is expanded.
Can new writes prove progress? Yes, dashboards show null rate by writer version. You know whether the new code is actually filling the field.
Can reads switch gradually? Yes, the API keeps fallback behavior until validation passes. Readers are not coupled to a backfill finishing perfectly.
Can replay stay idempotent? Yes, each batch can be rerun without changing completed rows. A failed job does not require starting from scratch.

Step 3: Backfill Like a Production Job

A backfill is a writer. It creates WAL, dirties pages, competes for locks, can increase replica lag, can trigger autovacuum work, and can change query plans after statistics shift. That is why the PostgreSQL UPDATE docs recommend smaller batches for large updates and show a common-table-expression pattern because UPDATE has no direct LIMIT clause.

WITH batch AS (
  SELECT l.id, e.event_id
  FROM ledger_entries AS l
  JOIN payment_events AS e
    ON e.payment_id = l.payment_id
  WHERE l.source_event_id IS NULL
  ORDER BY l.id
  FOR UPDATE OF l SKIP LOCKED
  LIMIT 1000
)
UPDATE ledger_entries AS l
SET source_event_id = batch.event_id
FROM batch
WHERE l.id = batch.id
RETURNING l.id;

This is not the only valid SQL shape. The important properties are bounded work, stable ordering, idempotent predicates, and a way to know how much work was actually done. If you use UPDATE ... FROM, the PostgreSQL docs warn that each target row should join to at most one source row, or the chosen source row is not predictable.

Backfill control loop:

run one batch
  -> record rows updated and last key range
  -> sleep or throttle if latency, locks, or replica lag rise
  -> repeat until no rows remain
  -> run final verification without SKIP LOCKED

Step 4: Validate Before You Enforce

Validation turns "the job finished" into evidence. Count remaining nulls, sample joined rows against source events, look for ambiguous joins, compare ledger totals before and after, and check whether write latency or replica lag changed.

SELECT count(*) AS missing_source_event_id
FROM ledger_entries
WHERE source_event_id IS NULL;

SELECT source_event_id, count(*) AS ledger_rows
FROM ledger_entries
GROUP BY source_event_id
HAVING count(*) > 1
ORDER BY ledger_rows DESC
LIMIT 20;

The second query is not automatically an error because one event might legitimately produce multiple ledger rows. The point is to force the business rule into the open. The invariant must be named before the database can enforce it.

Step 5: Enforce in Low-Blast-Radius Pieces

Once new writes populate the field and old rows are backfilled, add the guardrails. PostgreSQL supports NOT VALID for check, foreign-key, and not-null constraints; the docs say this skips the initial scan while still applying the constraint to later inserts and updates, then VALIDATE CONSTRAINT scans existing rows with a lower lock level than a blocking add.

ALTER TABLE ledger_entries
ADD CONSTRAINT ledger_entries_source_event_id_present
CHECK (source_event_id IS NOT NULL) NOT VALID;

ALTER TABLE ledger_entries
VALIDATE CONSTRAINT ledger_entries_source_event_id_present;

If the lookup path needs an index, build it with production cost in mind:

CREATE INDEX CONCURRENTLY ledger_entries_source_event_lookup_idx
ON ledger_entries (merchant_id, source_event_id);

The CREATE INDEX docs say CONCURRENTLY avoids locks that block inserts, updates, and deletes, but it performs more work, takes longer, waits for transactions, cannot run inside a transaction block, and can leave an invalid index after failure. That means your migration runner and rollback plan must understand it.

Step 6: Switch Reads, Then Contract

After validation, switch readers gradually: internal users, one tenant cohort, one region, then broader traffic. Watch the same rollout signals as earlier lessons: latency, errors, saturation, freshness, correctness, and rollback health.

Phase Safe move Stop condition
Read switch Use source_event_id for a small cohort first. Trace lookups fail, latency regresses, or null fallback fires.
Broad release Increase traffic after comparing old and new paths. Ledger drift, replay mismatch, or elevated database pressure.
Contract Remove fallback code after old versions are gone. Any rollback image still needs the fallback path.
Cleanup Drop old columns, jobs, flags, or indexes later. Consumers, exports, dashboards, or incident tools still read them.

Contracting is where many teams break rollback. Do it only after the old code path is no longer a recovery option.

Observe the Migration, Not Just the SQL

PostgreSQL's progress reporting docs list progress views for operations such as CREATE INDEX, ANALYZE, and VACUUM. Combine those database views with service telemetry so the rollout is judged by user and system impact, not by whether a command returned successfully.

Rowsremaining, updated, skipped.
Lockswaiters and blocked writers.
Lagreplica and consumer delay.
Bloatdead tuples and vacuum pressure.
Userslatency and correctness.

A good backfill can pause. A great backfill knows when to pause before users notice.

How to Defend the Resume Bullet

Suppose someone asks: "You said you ran an online migration for a high-volume ledger. What made it safe?" A strong answer is operational, not ceremonial.

Strong answer shape:

  1. We first expanded the schema with a nullable field so old and new code could coexist.
  2. We deployed writers that populated the new field and measured null rate by version.
  3. We backfilled historical rows in ordered, idempotent batches with checkpoints and throttling.
  4. We monitored write latency, locks, replica lag, dead tuples, and user-facing latency during the job.
  5. We validated data completeness and business correctness before adding constraints or switching reads.
  6. We used NOT VALID validation and concurrent index builds where appropriate, with explicit recovery for failed or invalid indexes.
  7. We removed fallback behavior only after the old code path was no longer needed for rollback.

Reflection Questions

No homework is required. These are the checks that show whether you can reason about schema change as production engineering:

  1. Why is "run a migration" not a complete rollout plan?
  2. What must be true before a reader can depend on a new column?
  3. Why should a large backfill be idempotent and pauseable?
  4. What can go wrong when adding a constraint to a large live table?
  5. Why can a failed concurrent index build still require cleanup?
  6. When is it safe to remove fallback code or old schema?

Concise answer key: migrations affect code, schema, data, indexes, replicas, and rollback; readers should wait for compatible writers, backfill, validation, and guarded rollout; pauseable batches limit locks, bloat, replica lag, and recovery cost; constraints may scan and lock; failed concurrent indexes can remain invalid and still add write overhead; contract only after old versions and rollback paths no longer need the old shape.

Ask follow-up questions about any unclear piece. Useful migration questions here are: "Can old and new code coexist?", "How do we pause this job?", "What proves the data is correct?", "What blocks writers?", and "What exactly is the rollback path?"
