Reference 0019

Real-Time Metrics Platform

A compact checklist for designing, operating, and defending a stream-powered metrics platform with fresh, correct, repairable derived data.

Core Rule

Real-time metrics are a derived-data contract, not a tool stack.

Defend the contract by naming metric semantics, source facts, event ordering, stateful aggregation, serving materialization, freshness, correctness, replay, and evidence.

Pipeline Shape

accepted billing facts
  -> transactional publication or CDC
  -> Kafka topic keyed for ordering
  -> dedupe and normalize stream
  -> subscription state update
  -> merchant aggregate update
  -> Redis or database projection upsert
  -> dashboard read with freshness metadata
  -> audit, replay, and repair

Vocabulary

Metric contract: the precise definition of what changes a metric, which time semantics apply, and how corrections are handled.

Source fact: a durable accepted business event, not an attempted request or temporary support note.

Ordering boundary: the entity whose events must be sequential for correctness, often subscription, account, order, or SKU.

Derived state: state computed from source facts, such as per-subscription lifecycle state or per-merchant MRR.

Materialized read model: precomputed serving state optimized for reads, usually rebuildable from source history.

Freshness: how old the visible metric is when read.

Correctness audit: comparison between stream-derived output and an authoritative reference such as ledger or batch recomputation.

Replay: re-consuming source history to rebuild or repair derived state.

Design Checklist

  1. Define the metric before choosing the streaming topology.
  2. Identify the accepted source facts and reject non-authoritative inputs.
  3. Choose event keys based on required ordering, not convenience.
  4. Decide where repartitioning is needed for aggregate ownership.
  5. Make dedupe and correction behavior explicit.
  6. Checkpoint state and prove sink writes are replay-safe.
  7. Materialize reads with computed-at, watermark, and pipeline-version metadata.
  8. Separate freshness SLOs from correctness audits.
  9. Track lag, backpressure, checkpoint duration, sink conflicts, Redis hit rate, and audit diffs.
  10. Keep runbooks for replay, rebuild, rollback, and affected-merchant repair.

State Table

State Purpose Recovery question
Billing ledger or lifecycle facts Authoritative source of accepted business changes. Can every metric be recomputed from these facts?
Kafka log Ordered replayable event history within partitions. Is retention long enough for rebuild and audit needs?
Flink operator state Per-key memory for subscriptions, aggregates, timers, and corrections. Are checkpoints healthy, restorable, and compatible with new code?
Redis projection Low-latency dashboard serving state. Can keys be rebuilt after eviction, corruption, or deployment rollback?
Audit outputs Evidence that derived metrics match authoritative truth. Can diffs be attributed to specific facts, keys, and pipeline versions?

Failure Matrix

Failure Likely cause Control
Metric is fresh but wrong. Bad metric semantics, duplicate events, missed corrections, schema bug. Audit diffs, replay tests, schema compatibility checks, correction contract.
Metric is correct but stale. Kafka lag, Flink backpressure, slow sink, checkpoint pressure. Freshness SLO, lag-age alerts, checkpoint monitoring, sink scaling.
Replay double-counts revenue. Blind increments or non-idempotent sink writes. Upserts by metric key and version, event dedupe, checksum verification.
One merchant delays many others. Skewed key, hot partition, large correction, expensive aggregate. Skew dashboard, split aggregate, tenant throttles, bounded repair queue.
Dashboard hides stale data. No freshness metadata in materialized values. Return computed-at, watermark, source version, and stale labels.

SLI Set

Concern Signal Decision it supports
Freshness Age of metric at read time; watermark lag; Kafka lag age. Page, degrade, or show stale label.
Correctness Batch-vs-stream diff, checksum, sampled ledger audit. Block rollout, replay, or repair affected keys.
Recovery Replay duration, rebuild duration, failed keys, sink conflicts. Choose repair scope and communicate impact.
Serving Redis hit rate, evictions, key age, API latency, errors. Tune cache policy or protect source systems.
Change safety Canary diffs, schema errors, DLQ count, mixed-version behavior. Continue, pause, rollback, or backfill.

Defense Script

When defending a real-time metrics platform:

  1. Start with the product promise and metric contract.
  2. Name the source of truth and accepted source facts.
  3. State the ordering boundary and partition or repartition strategy.
  4. Explain stateful aggregation, checkpointing, dedupe, and corrections.
  5. Explain the materialized read model and freshness metadata.
  6. Separate freshness, correctness, serving, and recovery signals.
  7. Close with replay, audit, rollback, and ownership.
