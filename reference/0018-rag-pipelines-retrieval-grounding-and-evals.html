Reference 0018

RAG Pipelines

A compact checklist for designing, evaluating, and defending retrieval-augmented generation systems as production pipelines.

Core Rule

A RAG system has two promises: retrieve the right evidence, then answer only within that evidence.

RAG can make model outputs more grounded and easier to update, but retrieval does not automatically make an answer true. Corpus authority, chunking, metadata, generation instructions, evals, and observability all carry part of the reliability contract.

Vocabulary

Corpus: the documents, tickets, logs, runbooks, or records the system may retrieve from.

Chunk: a retrievable slice of source material with enough local context to be useful.

Embedding: a vector representation used to compare semantic relatedness between text.

Vector index: searchable storage for embeddings plus source text and metadata.

Semantic search: retrieval by meaning, not only exact keyword overlap.

Metadata filter: a constraint such as product area, version, date, tenant, permission, or source type applied before or during retrieval.

Reranker: a second-stage ranker that reorders candidate chunks using a more precise relevance model.

Grounding: tying generated claims to retrieved source evidence.

Faithfulness: whether the answer's claims are supported by the retrieved context.

Precision@k: the share of the top k retrieved chunks that are relevant.

Production Pipeline

source systems
  -> normalize and redact
  -> chunk with source metadata
  -> embed and index
  -> retrieve candidates
  -> filter and rerank
  -> synthesize grounded answer
  -> cite source evidence
  -> evaluate retrieval and generation
  -> monitor latency, cost, failures, freshness

Corpus Contract

Source Authority Control
API docs High for intended public behavior. Version, product area, endpoint, release date.
Support tickets Useful symptoms, not canonical policy. Resolution status, age, product, sensitive-data redaction.
Integration logs Concrete evidence for one case. Tenant permission, retention, trace ID, time window.
Runbooks Operational procedure if current. Owner, last reviewed date, incident scope.

Design Checklist

  1. What user question is the system allowed to answer?
  2. Which sources are authoritative, anecdotal, stale, private, or case-specific?
  3. What metadata must travel with every chunk?
  4. How are documents versioned, redacted, indexed, deleted, and reindexed?
  5. Does retrieval need keyword search, semantic search, hybrid search, reranking, or filters?
  6. Can the generator say "not enough evidence" instead of guessing?
  7. Are answers required to cite source IDs, document versions, or trace IDs?
  8. Which evals separate retrieval failure from generation failure?
  9. What production metrics show freshness, relevance, latency, cost, errors, and user corrections?

Evaluation Matrix

Metric Question Common fix
Precision@5 Are the top five chunks mostly useful? Improve chunking, filters, ranking, or corpus hygiene.
Context recall Did retrieval include the needed evidence somewhere? Change chunk size, query expansion, hybrid search, or top-k.
Faithfulness Are generated claims supported by retrieved context? Tighten answer contract, citations, abstention, and judge prompts.
Answer relevance Did the final answer solve the user's task? Improve prompt framing, reranking, synthesis, or task routing.
Serving health Is the system fast, fresh, affordable, and observable? Add SLOs, budgets, tracing, caching, queue controls, and alerts.

Failure Modes

Failure Likely cause Control
Correct doc missing from results. Bad chunking, weak query, missing metadata, indexing lag. Retrieval evals, freshness checks, hybrid retrieval, reranking.
Old ticket outranks current docs. No authority model or source weighting. Source hierarchy, date filters, version metadata.
Answer leaks private case data. Missing permission filter or redaction. Access checks before retrieval, tenant filters, PII scrubbing.
Answer sounds right but is unsupported. Generator fills gaps from model memory. Faithfulness eval, citation requirement, abstention behavior.
Quality drops after corpus update. Ingestion changed retrieval distribution. Regression eval suite, canary index, rollback path.

Answer Shape

When defending a RAG pipeline:

  1. Name the user task and allowed corpus.
  2. Classify sources by authority, freshness, and permissions.
  3. Describe ingestion: normalize, redact, chunk, embed, index, version.
  4. Describe retrieval: filters, top-k, reranking, and source weighting.
  5. Describe generation: grounded answer contract, citations, abstention.
  6. Separate evals: retrieval quality, faithfulness, answer relevance, latency, cost.
  7. Close with production controls: tracing, dashboards, regression tests, index rollback, and owner.
