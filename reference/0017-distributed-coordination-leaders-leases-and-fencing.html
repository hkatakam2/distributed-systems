Reference 0017

Distributed Coordination

A compact checklist for leader election, leases, fencing tokens, ownership transfer, and safe side effects.

Core Rule

Leader election chooses who may try. Fencing decides whose side effects are accepted.

A lease without fencing can still allow an old holder to write late after a pause, network delay, or missed heartbeat. Correctness-sensitive resources must reject stale owners.

Vocabulary

Consensus: agreement among machines on ordered decisions despite failures.

Coordination service: a small, highly available control-plane system used for metadata, leader election, sessions, leases, and configuration.

Leader election: a process by which candidates choose one current owner for a role.

Session: a client relationship with a coordination service, usually maintained by heartbeats.

Lease: time-bounded ownership that expires if it is not renewed.

Fencing token: monotonically increasing ownership value included in side effects so stale owners can be rejected.

Epoch or generation: another common name for an ownership term or monotonic version.

Decision Table

Problem Likely primitive Safety check
A duplicate task only wastes work. Best-effort lock, idempotent work, or no lock. Duplicates are harmless and bounded.
One process claims one database job row. Atomic update, row lock, or transaction. Claim is committed close to the data.
One owner runs long-lived control work. Lease or session with heartbeat. Every side effect carries a fencing token.
Machines must agree on ordered metadata decisions. Consensus-backed service. Majority-backed decision and durable log.
Stream partitions need assignment and failover. Consumer group or shard lease. Sink writes remain idempotent or fenced.

Safe Ownership Loop

candidate starts
  acquire lease or session
  receive fencing token or epoch
  publish current ownership state
  perform work with token attached
  downstream resource checks token
  renew lease while healthy
  stop work immediately if renewal fails
  alert on churn, stale writes, and duplicate attempts

Fencing Pattern

owner token = 8

UPDATE projection_repair
SET status = 'assigned',
    owner_token = 8,
    updated_at = now()
WHERE repair_id = :repair_id
  AND owner_token < 8;

if rows_updated == 0:
  stop; a newer owner already acted

The exact syntax changes by database or storage system. The invariant does not: stale tokens must fail at the resource being changed.

Review Checklist

  1. Is this lock for efficiency, scheduling, or correctness?
  2. What exact invariant can a stale owner violate?
  3. What grants ownership: database row, consumer group, lease, or consensus-backed election?
  4. How does the system detect lost ownership?
  5. Does every correctness-sensitive side effect include an epoch or fencing token?
  6. Where is stale-token rejection enforced?
  7. Can old and new owners overlap during failover, pause, or network delay?
  8. Are duplicate actions idempotent, rejected, or repaired?
  9. What metrics show leadership churn, renewal failures, stale writes, and duplicate attempts?
  10. Who owns the runbook for stuck leases, repeated failover, and repair cleanup?

Common Weak Claims

Weak claim Stronger version
"We use a distributed lock." "A consensus-backed lease chooses the owner, and sinks reject stale fencing tokens."
"Only one pod runs the job." "Only the newest ownership token can assign accepted work after failover."
"Kafka handles ownership." "Consumer group assignment owns partitions; sink writes are still idempotent or fenced."
"The lock has a TTL." "The lease expires for failover, and stale owners cannot write because resources check tokens."

Answer Shape

When defending coordination:

  1. Classify the risk: efficiency, scheduling, or correctness.
  2. Name the owner and what it is allowed to do.
  3. Name the coordination primitive and why it fits the control plane.
  4. Describe the lease/session lifecycle and failover behavior.
  5. Explain the fencing token and where stale tokens are rejected.
  6. State the duplicate, pause, and network-delay failure modes.
  7. Close with production evidence: churn, renewal failures, stale rejections, duplicate attempts, and repair success.
