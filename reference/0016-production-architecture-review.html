Reference 0016

Production Architecture Review

A compact checklist for reviewing a backend design as testable claims, failure modes, controls, evidence, and ownership.

The Recurring Shape

ClaimState what the architecture must guarantee for a user journey.
MechanismName the component, contract, or pattern that provides the guarantee.
FailureAsk what breaks the claim under traffic, change, duplication, or delay.
ControlAdd the limit, fallback, invariant, rollout guard, or repair path.
EvidenceDefine the metric, trace, log, test, or runbook that proves it works.

Vocabulary

Architecture claim: a specific statement about what the system guarantees, such as ordering, freshness, durability, idempotency, replay, or bounded degradation.

Mechanism: the design choice that supports a claim: transaction, constraint, outbox, partition key, checkpoint, cache TTL, canary, timeout, or SLO.

Invariant: a condition that should remain true even under retries, concurrency, failure, replay, or partial deployment.

Failure mode: a concrete way the claim can break.

Control: a prevention, detection, containment, mitigation, or repair mechanism for a failure mode.

Evidence: the observable proof that a claim is currently holding or has failed.

Owner: the person or team responsible for the control, signal, runbook, and repair path.

Review Loop

for each critical user journey:
  write the user promise
  list the architecture claims that support it
  for each claim:
    name the mechanism
    name the invariant
    force one likely failure mode
    choose the control
    choose the evidence signal
    assign the owner
    check the rollback or repair path

Five Review Lenses

Lens Questions Common weak answer
User promise Which journey matters? What is good enough? What burns the SLO? "All services are up."
State Where is truth? What can drift? Which invariant is enforced durably? "Everything is in the database."
Time What ordering is required? What can be late, replayed, duplicated, or stale? "Kafka handles ordering."
Failure What happens under retry storms, hot tenants, slow sinks, lost workers, or partial deploys? "We can just retry."
Operations What signal pages? What runbook repairs? Who owns cleanup and verification? "We have dashboards."

Review Questions

  1. What is the most important user promise this design makes?
  2. Which claim would be most expensive if wrong?
  3. Where is the source of truth, and what states are rebuildable?
  4. What ordering guarantee is needed, and what partition key provides it?
  5. What happens when the same command, event, or batch runs twice?
  6. What can be stale, and how does the user or operator know?
  7. What backpressure protects the first shared bottleneck?
  8. What rollout, schema, or migration path keeps old and new code compatible?
  9. What signal pages, what signal tickets, and what signal only helps diagnosis?
  10. Who owns replay, DLQ repair, stale data cleanup, and post-incident verification?

Answer Shape

When defending an architecture:

  1. Start with the user promise and scale or freshness target.
  2. Name the durable source of truth and enforced invariants.
  3. Explain how asynchronous work is published, ordered, replayed, and consumed.
  4. Explain how serving state is built, bounded, monitored, and repaired.
  5. State the biggest tradeoff and why it is acceptable.
  6. Name the failure modes and controls.
  7. Close with evidence: metrics, tests, SLOs, drills, and incident learnings.
