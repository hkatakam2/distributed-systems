Reference 0015

Incident Response, Triage, and Postmortems

A compact runbook for declaring an incident, stabilizing the user promise, coordinating work, debugging from evidence, and turning the event into durable system improvement.

The Recurring Shape

DeclareName the incident early when impact, uncertainty, or coordination cost crosses the threshold.
StabilizeStop budget burn with rollback, traffic shift, throttling, degradation, or feature disablement.
CoordinateAssign command, operations, communications, and planning so changes are not freelanced.
DiagnoseUse evidence to narrow the path from symptom to cause without delaying mitigation.
LearnWrite the postmortem, assign preventive actions, and verify the system got harder to break.

Vocabulary

Incident: an event that threatens or violates a user promise and requires coordinated response.

Incident commander: the person who owns high-level state, priorities, role assignment, and decision flow during the incident.

Ops lead: the person or team making approved production changes.

Communications lead: the person responsible for periodic stakeholder updates and current incident status.

Planning lead: the person tracking follow-up work, handoff needs, cleanup tasks, and system divergence.

Mitigation: an action that reduces user impact before the full root cause is known.

Remediation: an action that removes or reduces the underlying cause after diagnosis.

MTTD: mean time to detect; how long it takes to know a bad event is happening.

MTTA: mean time to acknowledge; how long it takes for an owner to accept responsibility.

MTTR: mean time to recover; how long it takes to restore the promised service behavior.

State document: the live record of impact, hypotheses, decisions, actions, owners, timestamps, and next update time.

Postmortem: a written record of impact, timeline, contributing causes, mitigation, and follow-up actions.

Declare Early When

  1. The issue is user-visible or threatens an SLO fast burn.
  2. A second team is needed to understand or fix the problem.
  3. One focused responder has spent too long without narrowing cause.
  4. Multiple engineers need to change, inspect, or coordinate production state.
  5. The system has diverged from normal operation and will need cleanup.
  6. Stakeholders need status, impact, risk, or ETA separated from debug chatter.

Role Table

Role Owns Avoids
Incident command Impact, priority, roles, decision log, escalation, and handoff. Getting buried in one terminal and losing the incident-wide picture.
Operations Approved production changes, rollback, traffic movement, config, and repair commands. Uncoordinated fixes from multiple engineers changing the same system.
Communications Stakeholder updates, status page input, customer-facing summaries, next-update cadence. Making the primary debugger answer repeated status questions.
Planning Follow-ups, cleanup, staffing, handoffs, action items, and divergence from normal state. Losing temporary changes and leaving reliability debt unowned.

Mitigation Table

Symptom Likely first mitigation Evidence to preserve
Bad deploy burns request SLO. Rollback, pause rollout, disable flag, or route traffic away. Release version, canary metrics, traces, error samples, config diff.
Database saturation raises API latency. Throttle callers, shed low-value reads, reduce concurrency, kill unsafe query. Wait events, query IDs, pool waits, locks, connection counts.
Kafka/Flink freshness falls behind. Pause unsafe inputs, scale within partition limits, bypass slow sink, label stale data. Lag age, partition skew, checkpoint duration, backpressure, sink errors.
Cache miss storm overloads source. Serve bounded stale data, coalesce misses, warm hot keys, shed optional reads. Hit rate, hot keys, TTL changes, database fallback rate, eviction metrics.
Dependency failure cascades. Open circuit, reduce retries, apply deadlines, degrade response, isolate tenant. Dependency latency, retry volume, timeout rate, request fanout, client versions.

Postmortem Checklist

  1. State customer impact in terms of the user promise, not just internal symptoms.
  2. Record a factual timeline with timestamps, observations, actions, and results.
  3. Separate triggers from contributing causes.
  4. Explain why existing controls did not prevent, detect, or contain the issue sooner.
  5. Name what went well so the useful parts of the response are preserved.
  6. Create action items that change systems, tests, runbooks, alerts, ownership, or rollout gates.
  7. Assign each action item one owner, one priority, and one verification signal.
  8. Share the learning with the people who operate adjacent systems.

Answer Shape

When defending incident work:

  1. Name the SLO or user journey that was at risk.
  2. Explain when the incident was declared and why.
  3. State the mitigation that stopped the burn.
  4. Describe the evidence path used to isolate cause.
  5. Show how coordination prevented conflicting production changes.
  6. Summarize the postmortem action items and how they were verified.
