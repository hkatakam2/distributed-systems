Reference 0013

Capacity, Backpressure, and Bottlenecks

A compact checklist for reasoning about throughput, latency, queues, saturation, autoscaling, and overload across an end-to-end backend path.

The Recurring Shape

DemandName arrival rate, burst shape, tenants, and priority.
WorkEstimate service time, fanout, queueing, and retry cost.
LimitFind the saturated pool, store, partition, or dependency.
ControlApply backpressure, shedding, batching, caching, or scaling.
VerifyWatch user latency, errors, freshness, saturation, and cost.

Vocabulary

Throughput: completed useful work per unit time, such as requests per second or events per second.

Arrival rate: work entering the system per unit time, before queueing, rejection, or retries.

Service time: time a worker or dependency spends actively processing one unit of work.

Concurrency: work in progress at the same time, including active work and queued work if measured at the boundary.

Utilization: how busy a resource is relative to its practical capacity.

Saturation: a resource has more demand than it can serve promptly, so queues, waits, errors, or latency rise.

Queue depth: work waiting to be processed.

Backpressure: a deliberate signal that slows or rejects upstream work before a downstream limit collapses.

Load shedding: rejecting or dropping lower-value work to preserve the core user promise.

Bottleneck: the limiting resource that determines end-to-end throughput under current load.

Fanout: one request causing multiple downstream calls, queries, messages, or writes.

Headroom: spare practical capacity before user-visible latency, errors, or freshness violate the SLO.

Retry amplification: extra work created when clients retry during slowness, often worsening overload.

Freshness: age of derived state relative to the source facts that produced it.

Diagnosis Checklist

  1. Name the user-visible symptom: latency, errors, stale data, dropped work, or cost spike.
  2. Draw the critical path: gateway, service pods, connection pools, caches, databases, logs, workers, and sinks.
  3. Measure demand at the entry point and at each fanout boundary.
  4. Compare arrival rate with completed throughput at each stage.
  5. Look for queue growth, pool waits, partition lag, lock waits, CPU saturation, memory pressure, I/O waits, and external dependency latency.
  6. Check whether retries are increasing demand during the incident.
  7. Identify the first saturated resource, not the loudest symptom.
  8. Apply the smallest control that protects the user promise.
  9. Verify the control with latency, errors, freshness, saturation, and cost.
  10. Document the new operating limit and the next bottleneck.

Control Table

Pressure Useful controls Main caution
API pods are CPU-bound. Optimize hot path, cache, reduce fanout, scale pods, shed low-value work. More pods may shift pressure to the database or cache.
Database pool waits rise. Reduce query count, add indexes carefully, cap concurrency, split read paths. Larger pools can overload the database faster.
Kafka consumer lag grows. Scale consumers up to partition limits, reduce per-event cost, batch, pause unsafe work. More consumers do not help beyond available partitions in a group.
Redis memory or hot keys saturate. Set TTLs, shard hot keys, cache only useful shapes, add request coalescing. Eviction and stampedes can convert cache pressure into database pressure.
Retries amplify load. Use deadlines, backoff, jitter, budgets, idempotency, and circuit breakers. Retries without limits can turn partial failure into overload.
Derived state becomes stale. Expose freshness, throttle producers, prioritize critical events, rebuild from source. Serving stale data is acceptable only when the product contract says so.

Fast Estimation

work in progress ~= arrival rate x end-to-end latency

database queries/sec ~= API requests/sec x queries per request

consumer catch-up time ~= backlog events / sustainable events per second

required headroom ~= peak burst demand / safe sustained capacity

Use estimates to find the suspicious boundary, then confirm with telemetry. Estimation chooses where to look; measurement decides what to change.

Answer Shape

When defending capacity work:

  1. Start with the user promise and the exact symptom under load.
  2. Name the path and the demand shape, including bursts and fanout.
  3. Identify the bottleneck with evidence: queue, pool wait, lag, CPU, lock, or memory signal.
  4. Explain the control you chose and why other controls were weaker.
  5. Explain how you avoided pushing the problem into the next dependency.
  6. State the before and after metrics: P95/P99 latency, throughput, error rate, freshness, and headroom.
  7. State the new limit and the runbook signal that tells operators when the limit is close again.
