Serving State, Cache, and Projection Checklist

A compact checklist for designing fast read paths without confusing derived state, caches, and source-of-truth data.

The Recurring Shape

TruthWrite facts to the authoritative store and log.
ProjectTransform facts into query-shaped serving rows.
CacheKeep hot copies close to the request path.
BoundName the freshness, invalidation, and rebuild contract.
ObserveTrack latency, errors, saturation, hit rate, and staleness.

Design Checklist

Question Good answer Common trap
What is source truth? The write database, event log, or system of record that can rebuild derived state. Treating Redis or a dashboard table as truth because reads are fast.
What query is being served? Shape the projection around one concrete read path and its filters. Building a generic mirror that is no faster or simpler than the source.
How stale may it be? Define an explicit freshness budget, such as "merchant MRR is under 30 seconds old." Saying "real time" without an age metric or user-facing fallback.
How are updates applied? Use idempotent upserts with version, event-time, or sequence guards. Letting older replayed events overwrite newer projection state.
How is cache validity bounded? Use TTL, event-driven invalidation, versioned values, or a mix. Keeping cached values forever because invalidation is inconvenient.
What happens on cache miss? Load from projection or source, set TTL, and protect hot keys from stampedes. Letting one hot expired key fan out into many identical database reads.
Can it be rebuilt? Retain source facts, keep schema compatibility, and rehearse backfill into a controlled target. Discovering during an incident that the projection has no trustworthy rebuild path.
What proves health? Watch request latency, errors, cache hit rate, evictions, projection age, and drift. Monitoring only Redis uptime while serving stale or wrong values.

Vocabulary

Source of truth: the authoritative state that owns correctness and can regenerate derived copies.

Derived state: data computed from source facts for a faster or more convenient read path.

Projection table: a query-shaped table maintained by application code, jobs, or stream processors.

Materialized view: a stored query result that can be refreshed from its defining query.

Cache: an expendable copy kept near the request path to reduce latency or load.

TTL: time to live, after which a cached key expires and must be recomputed or reloaded.

Eviction: removing cached keys, often because memory is constrained.

Invalidation: marking cached data unusable after the underlying data changes.

Freshness budget: the maximum acceptable age of served derived data.

Hit rate: the share of cache lookups served from cache instead of the backing store.

Cache stampede: many requests simultaneously recomputing or reloading the same missing hot key.

Reconciliation: comparing derived state with source truth and repairing drift.

Useful Questions

  1. Which store is allowed to answer "what is true?"
  2. Which exact read path is this projection or cache optimizing?
  3. What is the user-visible freshness budget?
  4. Can the write path safely update, invalidate, or version the derived copy?
  5. Can replay or backfill run without corrupting newer values?
  6. What happens if Redis is empty, full, slow, or down?
  7. Which keys are hot, and how do you prevent stampedes?
  8. How would you rebuild the projection from zero?
  9. Which metric proves the served value is fresh enough?
