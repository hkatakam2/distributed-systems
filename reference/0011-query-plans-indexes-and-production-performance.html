Reference 0011

Query Plans, Indexes, and Production Performance

A compact guide for turning a slow PostgreSQL query into a defensible performance diagnosis: plan, estimate, access path, index, rollout, and observation.

The Recurring Shape

QueryCapture SQL, parameters, data shape, and latency target.
PlanRead scans, joins, sorts, loops, filters, and row estimates.
CauseFind selectivity, stale stats, missing index, or wrong query shape.
ChangeAdd or adjust index, rewrite query, or refresh statistics.
OperateRoll out safely and watch latency, I/O, writes, locks, and usage.

Vocabulary

Query plan: the tree of operations PostgreSQL chooses to execute a query.

Plan node: one operation in that tree, such as scan, sort, aggregate, hash, or join.

Sequential scan: reading a table directly, often sensible for small tables or queries that need a large fraction of rows.

Index scan: using an index to find rows, then usually fetching matching table rows.

Bitmap scan: collecting row locations through one or more indexes, then visiting the table in a more efficient physical order.

Index Cond: a predicate used to navigate or restrict the index access path.

Filter: a predicate checked after rows have already been reached by the current node.

Row estimate: the planner's predicted row count. A large estimate-versus-actual mismatch often explains a bad plan.

loops: how many times a node ran. Multiply actual time or rows by loops to understand repeated inner work.

Selectivity: the fraction of rows expected to match a predicate.

Multicolumn index: an index over multiple keys, most efficient when the leading columns match the query shape.

Partial index: an index over only rows satisfying a predicate, useful for hot subsets such as open orders or unprocessed jobs.

Covering index: an index with enough key or included columns to answer a query with fewer heap visits, sometimes enabling index-only scans.

Statistics: approximate metadata collected by ANALYZE that helps the planner estimate row counts and choose plans.

Bloat: extra table or index space from churn and dead row versions, increasing I/O and maintenance pressure.

Plan Triage Checklist

  1. Is the slow query the exact SQL shape and parameter set seen in production?
  2. Did you run EXPLAIN (ANALYZE, BUFFERS) only where executing the query is safe?
  3. Where is the largest time spent: scan, join, sort, aggregate, or repeated loop?
  4. Are estimated rows close to actual rows?
  5. Does the plan use Index Cond for the selective predicates, or only Filter?
  6. Is the query returning a small page with ORDER BY and LIMIT?
  7. Can one index satisfy equality filters, ordering, and the limit?
  8. Would a partial index cover the hot subset instead of indexing the whole table?
  9. Are stale statistics, correlated columns, or skewed values misleading the planner?
  10. Will the fix increase write latency, storage, vacuum work, or migration risk?

Index Choice Table

Workload shape Likely tool Reason
Lookup one entity by stable identity. Primary key or unique B-tree index. The key narrows to one or very few rows and also protects identity correctness.
Filter by tenant, then page recent rows. Multicolumn index such as (tenant_id, created_at DESC). The leading equality narrows the tenant; the next key provides the desired order.
Only a small active subset is queried constantly. Partial index with a predicate such as WHERE status = 'open'. The hot index stays smaller and avoids maintaining entries for cold rows.
Query needs narrow output columns from a hot path. INCLUDE columns if they are small and stable. A covering index can reduce heap visits, but duplicates data and can bloat writes.
Planner badly misestimates correlated predicates. Fresh ANALYZE or extended statistics. An index cannot fix a plan if the planner chooses poorly because its inputs are wrong.
Writes dominate and reads are broad scans. Fewer indexes, better query shape, or different serving model. Each index adds write, storage, and maintenance cost.

Production Checklist

  1. Name the endpoint, query, table size, cardinalities, and latency target.
  2. Capture a before plan with production-like data.
  3. Explain why the current plan is slow in terms of rows, loops, buffers, sorts, or joins.
  4. Design the smallest index that matches the query's stable predicates and ordering.
  5. Use CREATE INDEX CONCURRENTLY for large live tables when avoiding write blocking matters.
  6. Schedule heavy builds with I/O headroom and monitor progress, locks, replication lag, and write latency.
  7. Refresh or validate statistics after major data distribution changes.
  8. Compare before and after plans and p95/p99 latency.
  9. Track index usage and remove unused or redundant indexes only after evidence.
  10. Keep the rollback plan simple: drop the new index if it hurts writes or the planner chooses poorly.

Answer Shape

When defending a database performance fix:

  1. Name the user-facing symptom and the exact query path.
  2. Read the plan: scan type, joins, sorts, filters, estimates, actual rows, loops, and buffers.
  3. Explain why the old plan was expensive.
  4. Explain why the new index or query shape matches the workload.
  5. State the production cost: write overhead, storage, lock behavior, and maintenance.
  6. State the rollout and proof: concurrent build, monitoring, before/after plan, and latency change.
