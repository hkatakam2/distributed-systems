Reference 0012

Online Schema Migrations and Backfills

A compact guide for changing PostgreSQL schema and historical data while old code, new code, live writes, replicas, and rollback paths still exist.

The Recurring Shape

ExpandAdd compatible schema without forcing new behavior.
WriteDeploy writers that populate both old and new expectations.
BackfillMove old rows in bounded, observable, pauseable batches.
ValidateProve completeness, correctness, and production cost.
ContractRemove fallback only after rollback no longer needs it.

Vocabulary

Online migration: a schema or data change performed while the system continues serving traffic.

Expand and contract: add compatible structure first, move traffic gradually, then remove old structure later.

Backfill: a job that updates historical rows to match a new representation or invariant.

Dual-write: writing old and new representations during a compatibility window.

Read switch: moving readers from old representation to new representation, usually behind a flag or cohort.

Validation: proving that existing rows satisfy the intended rule before depending on or enforcing it.

Contract: removing old columns, fallback logic, jobs, flags, or indexes after they are no longer needed.

Table rewrite: a physical rewrite of table data, often much riskier than a metadata-only change on large tables.

NOT VALID constraint: a constraint added without the initial full validation scan, while still checking later inserts or updates.

VALIDATE CONSTRAINT: the later scan that proves pre-existing rows satisfy a not-valid constraint.

Concurrent index build: an index build that avoids blocking writers but performs more work and has special failure behavior.

Invalid index: an index left after a failed concurrent build; it may be ignored by queries but still require cleanup.

Replica lag: delay between primary writes and replica application, often worsened by heavy backfills.

Bloat: dead or unused table and index space created by churn, increasing storage and I/O pressure.

Migration Playbook

  1. Name the business invariant and the exact consumers that will rely on it.
  2. Add compatible schema first, such as nullable columns or optional fields.
  3. Deploy writers that fill the new representation while old readers still work.
  4. Measure new-write coverage, such as null rate by service version.
  5. Backfill historical rows in bounded, idempotent batches with stable ordering.
  6. Throttle or pause based on latency, locks, replica lag, dead tuples, and error rate.
  7. Validate completeness and business correctness before switching readers.
  8. Add constraints and indexes with production lock and I/O behavior in mind.
  9. Switch reads gradually and compare old versus new behavior.
  10. Remove fallback and old schema only after old versions and rollback paths are gone.

Risk Table

Move Main risk Safer habit
Add nullable column. Short lock still conflicts with long transactions. Run during quiet windows and watch lock waiters.
Add volatile default or change type. Table and index rewrite on large data. Split into expand, backfill, validate, and contract phases.
Run one huge update. Bloat, WAL, lock contention, and replica lag. Use ordered batches, checkpoints, throttling, and pause controls.
Add constraint directly. Long validation scan and blocked updates. Use NOT VALID where appropriate, then validate separately.
Build normal index. Writers block until the build finishes. Use CREATE INDEX CONCURRENTLY when production writes must continue.
Contract old shape early. Rollback image cannot read new data or schema. Keep fallback until old code and consumers are gone.

Backfill Control Loop

while rows remain:
  select a bounded batch in stable order
  update only rows still missing the new value
  record rows changed and high-water mark
  emit latency, lock, lag, and error metrics
  sleep, throttle, or pause if production is stressed
  repeat the final check without SKIP LOCKED

Prefer idempotent predicates such as WHERE source_event_id IS NULL. A restarted batch should either finish missing work or do nothing.

SQL Patterns

Compatible expansion:

ALTER TABLE ledger_entries
ADD COLUMN source_event_id text;

Bounded update:

WITH batch AS (
  SELECT l.id, e.event_id
  FROM ledger_entries AS l
  JOIN payment_events AS e
    ON e.payment_id = l.payment_id
  WHERE l.source_event_id IS NULL
  ORDER BY l.id
  FOR UPDATE OF l SKIP LOCKED
  LIMIT 1000
)
UPDATE ledger_entries AS l
SET source_event_id = batch.event_id
FROM batch
WHERE l.id = batch.id
RETURNING l.id;

Deferred validation:

ALTER TABLE ledger_entries
ADD CONSTRAINT ledger_entries_source_event_id_present
CHECK (source_event_id IS NOT NULL) NOT VALID;

ALTER TABLE ledger_entries
VALIDATE CONSTRAINT ledger_entries_source_event_id_present;

Lower-blocking index build:

CREATE INDEX CONCURRENTLY ledger_entries_source_event_lookup_idx
ON ledger_entries (merchant_id, source_event_id);

Production Checks

  1. Are old application versions, workers, and rollback images compatible with the expanded schema?
  2. Do new writes populate the new representation, and is coverage measured by version?
  3. Can the backfill pause, resume, retry, and safely run twice?
  4. Are batch size and ordering chosen to reduce locks, deadlocks, bloat, and replica lag?
  5. Is there a stop threshold for latency, error rate, lock waits, I/O, and lag?
  6. Are constraints validated only after the data is actually clean?
  7. Does the index build plan account for CONCURRENTLY caveats and invalid-index cleanup?
  8. Are readers switched by cohort with old-versus-new comparison?
  9. Is the contract step delayed until rollback no longer needs the old shape?
  10. Are dashboards and incident notes updated so operators know which phase is active?

Answer Shape

When defending an online migration:

  1. Name the invariant, table, consumers, and traffic risk.
  2. Explain how old and new code coexisted during expansion.
  3. Explain how historical rows were backfilled with bounded, idempotent batches.
  4. State what was monitored: latency, locks, lag, bloat, errors, and correctness.
  5. State how validation proved the data was ready.
  6. State how constraints, indexes, and read switches were rolled out.
  7. State when fallback was removed and what rollback looked like before then.
