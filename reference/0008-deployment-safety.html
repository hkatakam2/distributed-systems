Deployment Safety Checklist

A compact guide for shipping backend code, configuration, schema, stream jobs, and cache changes without turning one bad change into a broad outage.

The Recurring Shape

ArtifactBuild one immutable version you can identify and roll back.
CompatibleMake old and new code tolerate shared data and messages.
RolloutExpose the change gradually with readiness gates and small blast radius.
VerifyWatch user symptoms, internal causes, and domain correctness.
RecoverRollback or roll forward with a plan for code, config, data, and schema.

Change Plane Checklist

Plane Safe question Common trap
Code artifact Can we identify the exact image, commit, build, and dependency set? Mutable tags, unknown library drift, or manual server edits.
Configuration Can config be changed, audited, and reverted separately from code? A config flip that changes behavior globally with no owner or metric.
Schema Can old and new code both run while this schema exists? Deploying code that requires a column before every pod sees the schema.
Data and backfill Can backfill run in batches, pause, resume, and avoid side effects? One huge migration that locks hot tables or emits duplicate events.
Traffic Can we limit exposure by pod, tenant, region, or feature cohort? Sending 100 percent of traffic to a new path before observing it.
Telemetry Can we tell whether the change improved, broke, or hid behavior? Calling the deploy successful because pods are running.

Kubernetes Rollout Checks

  1. Does the Deployment use an immutable image tag or digest?
  2. Does the pod template change intentionally trigger a new rollout?
  3. Are maxSurge and maxUnavailable chosen for the service's real capacity headroom?
  4. Does the readiness probe prove the pod can serve the traffic it is about to receive?
  5. Is the liveness probe only for states that are better fixed by restart?
  6. Does a slow-starting app use a startup probe or conservative initial delay?
  7. Is there a progress deadline or rollout monitor that catches stuck deployments?
  8. Are new pods compared against old pods for latency, errors, saturation, freshness, and correctness?

Expand And Contract Schema Changes

Step Purpose Risk to avoid
Expand Add nullable columns, new tables, new topics, or optional fields. Breaking old code that still ignores or lacks the new shape.
Write both Make new code populate old and new representations. Creating a split-brain period where reads disagree silently.
Backfill Fill historical data in bounded, observable batches. Locking, saturating I/O, or replaying business side effects.
Switch reads Move readers to the new path behind a flag or small cohort. Global cutover before drift and latency are measured.
Contract Drop old fields only after no code, jobs, dashboards, or exports need them. Making rollback impossible because the old representation is gone.

Rollback Checklist

  1. What exact symptom or threshold triggers rollback?
  2. Is the bad change code, config, schema, data, traffic routing, or a dependency?
  3. Can the old code read data written by the new code?
  4. Can the old consumers handle messages emitted by the new producers?
  5. Will rollback re-run non-idempotent work such as payments, emails, or webhooks?
  6. Does rollback require disabling a feature flag before reverting the image?
  7. Does rollback require cache invalidation, replay, or projection rebuild?
  8. What evidence proves recovery: user symptoms, dependency health, and domain correctness?

Vocabulary

Deployment: putting a specific build or configuration into an environment.

Release: exposing behavior to users; release can happen after deployment when a flag is enabled.

Rollout: gradual replacement or exposure of one version with another.

Canary: a small, observed cohort that receives a change before broad release.

Readiness probe: a health check that controls whether a pod receives service traffic.

Liveness probe: a health check that restarts a container when restart is the right recovery action.

Startup probe: a health check that gives slow-starting containers time before liveness begins.

Feature flag: a runtime decision point that separates deploying code from releasing behavior.

Expand and contract: a migration pattern that adds compatible structure first, moves traffic gradually, and removes old structure later.

Rollback: returning to a previous known-good state.

Roll forward: fixing production by shipping a new change when rollback is unsafe or insufficient.
