Stateful Stream Processing Checklist

A compact checklist for designing Flink-style jobs with keyed state, event time, watermarks, checkpoints, replay, and materialized view sinks.

The Recurring Shape

KeyGroup events by the boundary that owns the state.
StateRemember only what future events need.
TimeChoose processing time or event time deliberately.
CheckpointPersist state plus source positions for recovery.
SinkWrite projections with replay-safe semantics.

Design Checklist

Question Good answer Common trap
What owns the state? Key by subscription, merchant, SKU, account, or another correctness boundary. Using a convenient key that breaks ordering or creates hot state.
What state is stored? Store the minimum data needed for dedupe, ordering, aggregation, or joins. Keeping unbounded history inside the stream processor.
Which clock matters? Use event time when the business fact's timestamp determines the result. Letting backlogs and replays change historical totals.
How do windows close? Use watermarks, allowed lateness, and correction-friendly sinks. Dropping late but valid events without visibility.
What survives failure? Checkpoint operator state and source positions to durable storage. Assuming in-memory state survives worker loss.
Can the sink repeat? Yes. Use idempotent upserts, versions, event IDs, or transactional connectors. Assuming internal exactly-once automatically covers Redis or partner APIs.
What proves freshness? Track source lag, event age, watermark lag, checkpoint health, and projection age. Looking only at consumer lag while event-time progress is stuck.

Vocabulary

Stateful operator: a processing step that remembers information across records.

Keyed state: state scoped to a specific event key, such as subscription_id.

Window: a finite time bucket used to aggregate an unbounded stream.

Event time: the time when the business fact happened.

Processing time: the time when the worker processes the record.

Watermark: event-time progress signal used to close windows and detect lateness.

Allowed lateness: extra time for late events to update an already emitted window.

Checkpoint: durable snapshot of operator state plus source positions.

Savepoint: operator-triggered state snapshot commonly used for controlled upgrades or migrations.

Replay-safe sink: external write path that tolerates repeated records after recovery or backfill.

Useful Questions

  1. What key owns the state this operator reads and writes?
  2. Can any key become hot, and what happens if it does?
  3. What state can be recomputed instead of stored forever?
  4. Does this result depend on event time or processing time?
  5. What should happen to late events?
  6. Where are checkpoints stored, and how long does recovery take?
  7. Can the sink tolerate duplicate writes after replay?
  8. How do you reconcile the projection with source truth?
