Observability and Debugging Checklist

A compact checklist for instrumenting and debugging backend systems across APIs, logs, stream processors, projections, caches, and user-visible contracts.

Design Checklist

Question Good answer Common trap
What pages a human? User-visible latency, errors, stale data, wrong data, or imminent saturation. Paging on every internal metric anomaly regardless of user impact.
What are the four golden signals? Latency, traffic, errors, and saturation, measured at the service boundary. Watching only CPU and assuming users are fine.
What do metrics answer? How often, how slow, how full, how old, and how many. Depending on averages while tail latency or hot keys hurt users.
What do traces answer? Where one request or operation spent time and crossed boundaries. Losing the path when work becomes asynchronous.
What do logs answer? Which discrete event happened, with searchable structured fields. Logging prose without stable IDs or versions.
Which context is propagated? Trace ID, span ID, request ID, event ID, tenant ID, and safe domain IDs. Passing PII or secrets as baggage or log fields.
How do you debug? Pick one affected request or event and narrow the path boundary by boundary. Opening many dashboards and searching for correlations without a hypothesis.
What proves correctness? Domain checks compare served state with source truth and freshness budgets. Treating HTTP 200 as proof that the answer was correct.

Vocabulary

Monitoring: collecting and displaying quantitative data to understand system behavior and alert on important problems.

Observability: the ability to inspect telemetry and infer how a system produced an outcome.

Metric: a runtime measurement, often aggregated over time, such as latency, request count, lag, or cache hit rate.

Trace: the causal path of a request or operation through services and components.

Span: one timed unit of work inside a trace, such as an HTTP handler, database query, produce operation, or consumer update.

Log: a timestamped event record; structured logs use stable fields and types.

Context propagation: carrying correlation context across process and network boundaries so telemetry can be joined.

Symptom: what users or callers experience, such as slow, failed, stale, or wrong responses.

Cause: the internal condition that explains a symptom, such as DB saturation, cache eviction, lag, or a bad deploy.

Domain check: a correctness check tied to business truth, such as projection MRR versus source-of-truth MRR.

Useful Questions

  1. What did the user experience, and over what time window?
  2. Which concrete request, trace, merchant, event, or projection row proves the problem?
  3. Is this a latency, traffic, error, saturation, freshness, or correctness issue?
  4. Which signal answers the next question: metric, trace, log, or domain check?
  5. Where does trace context stop propagating?
  6. Which boundary first turns good input into bad output?
  7. What changed recently: deploy, config, load shape, data distribution, or dependency behavior?
  8. What can be mitigated safely before root cause is complete?
  9. What evidence would prove the same failure cannot recur silently?
