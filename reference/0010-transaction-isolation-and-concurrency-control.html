Reference 0010

Transaction Isolation and Concurrency Control

A compact guide for choosing constraints, locks, isolation levels, and retries when concurrent requests touch the same state.

The Recurring Shape

InvariantName what must remain true after commit.
ScopeIdentify one row, many rows, or many tables.
GuardChoose constraint, conditional update, lock, or serializable check.
RetryHandle duplicate, deadlock, and serialization outcomes.
ObserveTrack contention, aborts, waits, and drift.

Vocabulary

Transaction: a group of database operations that commits or aborts as a unit.

Invariant: a correctness rule that must remain true, such as no negative inventory or no duplicate idempotency key.

Isolation level: the database contract for what one transaction can observe while other transactions run concurrently.

Read Committed: PostgreSQL's default isolation level; each statement sees a fresh committed snapshot.

Repeatable Read: a transaction-level snapshot in PostgreSQL; successive reads see the same snapshot, but serialization anomalies can still occur.

Serializable: the strictest PostgreSQL isolation level; committed transactions must be equivalent to some serial order, or one transaction aborts.

Serialization failure: an abort that tells the application to retry the whole transaction from the beginning.

Row lock: a lock on selected rows; it blocks conflicting writers and lockers, not ordinary readers.

SELECT FOR UPDATE: a locking read that prevents selected rows from being concurrently modified or locked incompatibly until the transaction ends.

Write skew: an anomaly where concurrent transactions each observe a valid snapshot but together commit a state that violates a cross-row rule.

Deadlock: two or more transactions wait for locks held by one another; the database aborts one so progress can resume.

Decision Table

Invariant shape Safer default Reason
One row must not go negative. Atomic conditional update: UPDATE ... WHERE available >= needed. The database serializes conflicting row writes and rechecks the predicate.
One logical request must run once. Unique idempotency key plus ON CONFLICT. The uniqueness check is the concurrency guard, not application memory.
A fixed row controls a resource. SELECT FOR UPDATE on the guard row, then update dependents. Conflicting writers wait on the same concrete lock.
A cross-row rule must hold. Serializable transaction with whole-transaction retry, or redesign into a constraint or guard row. Snapshot reads alone may not catch write skew.
Read-only report needs a stable view. Repeatable Read or Serializable Read Only where appropriate. The report should not mix different moments in one answer.

Isolation Cheat Sheet

Level Snapshot boundary What to remember
Read Committed Each statement. Fast default; good for simple keyed updates, risky for multi-statement reasoning over changing sets.
Repeatable Read First statement in the transaction. Stable reads; PostgreSQL prevents phantoms, but serialization anomalies remain possible.
Serializable Transaction snapshot plus anomaly detection. Strongest contract; design a generic retry path for SQLSTATE 40001.

Correctness Checklist

  1. What exact invariant can concurrent requests break?
  2. Can a database constraint express it directly?
  3. Can a single conditional statement express it atomically?
  4. Which rows, if locked, force all conflicting work through the same gate?
  5. Does the transaction read a set and then write based on that set?
  6. If using Serializable, does the caller retry the whole transaction after 40001?
  7. If using explicit locks, are locks acquired in a consistent order?
  8. Is the transaction short, with no external network call or user wait inside it?
  9. Does the outbox event commit in the same transaction as the state change?
  10. What metric proves contention is acceptable?

Metrics To Watch

  • Serialization failure count and retry success rate.
  • Deadlock count and aborted transaction count.
  • Lock wait time by relation, query, and endpoint.
  • Transaction duration and idle-in-transaction sessions.
  • Unique violation rate and idempotency conflict rate.
  • Conditional update miss rate, such as insufficient inventory.
  • Rows locked or updated per transaction.
  • Queue depth for workers using locked rows or SKIP LOCKED.

Answer Shape

When defending a concurrent write path:

  1. Name the invariant and its scope.
  2. Name the database primitive protecting it: constraint, conditional update, lock, or Serializable.
  3. Name the expected conflict outcome: wait, no-op, unique violation, deadlock abort, or serialization retry.
  4. Name the retry boundary: statement retry for safe idempotent work, whole-transaction retry for serialization failures.
  5. Name what is deliberately outside the transaction to keep locks short.
  6. Name the metrics that prove contention and correctness are under control.
