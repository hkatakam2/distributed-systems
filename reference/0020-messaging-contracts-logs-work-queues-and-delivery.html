Reference 0020

Messaging Contracts

A compact checklist for choosing between replayable event logs, routed work queues, and dual messaging designs without hiding the delivery and failure contract.

Core Rule

Do not choose a broker first. Choose the message contract first.

Name whether the message is durable history, pending work, a command, a notification, or a rebuildable projection update. Then choose the tool and controls that fit that contract.

Contract Map

Contract Best mental model Typical controls
Event history Something happened and may need replay by many consumers. Kafka topic, partition key, retention, offsets, consumer groups, replay tools.
Pending work Something must be processed by a worker and acknowledged. RabbitMQ exchange, queue, binding, consumer ack, retry, dead-letter exchange.
Command One system asks another to perform an action. Idempotency key, authorization, timeout, retry budget, result tracking.
Notification Consumers should learn about a change, but source truth lives elsewhere. Stable event ID, version, dedupe, source lookup, missed-message repair.
Projection update A read model must converge toward source truth. Versioned upsert, freshness metadata, reconciliation, replay or rebuild.

Kafka Versus RabbitMQ

Question Kafka-shaped answer RabbitMQ-shaped answer
What is stored? Retained records in partitioned logs. Messages waiting in queues for consumers.
How do consumers progress? They advance and commit offsets. They acknowledge deliveries.
How do many consumers share facts? Separate consumer groups can read the same log independently. Separate queues can receive routed copies through exchanges and bindings.
How do you replay? Seek to earlier offsets or timestamps if retention allows. Requeue, retry, or republish work; queues are not usually long-term history.
What is the ordering boundary? Partition key and one consumer per partition in a group. Queue order, affected by multiple consumers, redelivery, priority, and retry design.
What is failure ownership? Consumer lag, retry topics, DLQs, offset policy, replay owner. Unacked messages, redeliveries, dead-letter exchange, retry owner.

Dual Messaging Shape

source transaction
  -> update_id and source facts
  -> outbox row
  -> Kafka event history for replay and analytics
  -> RabbitMQ routed work for explicit processing
  -> idempotent consumers on both paths
  -> reconciliation by update_id

Use the same source update identity everywhere. Do not allow Kafka and RabbitMQ messages to invent different versions of the same business fact.

Design Checklist

  1. Name whether each message is history, work, command, notification, or projection update.
  2. Choose the source of truth before choosing the broker.
  3. Assign a stable message or update ID at the source boundary.
  4. Choose the ordering key around the smallest entity that needs sequential state.
  5. Publish durably and record publisher failures.
  6. Acknowledge or commit only after durable, idempotent processing.
  7. Bound retries and route poison messages to an owned dead-letter path.
  8. Track backlog age, lag, unacked messages, redelivery, DLQ rate, and processing latency.
  9. Measure end-to-end business freshness, not only broker health.
  10. Reconcile source facts against processed outputs and repair missing update IDs.

Failure Matrix

Failure Likely cause Control
Message published to one path but not the other. Dual write without outbox or reconciliation. Single source fact, outbox publication, update-ID audit.
Duplicate update changes inventory twice. At-least-once redelivery with non-idempotent handler. Dedupe by update ID and versioned upsert.
Old update overwrites newer stock value. Out-of-order delivery or retry. Per-SKU sequence, event time, or source version guard.
One bad message blocks useful work. Poison message retries forever in hot queue. Bounded retries, dead-letter exchange, owner and repair tool.
Broker dashboard is green but inventory is stale. Monitoring component health instead of business freshness. Source-to-projection age by SKU and fulfillment center.

Operational Signals

Layer Signals Question answered
Kafka Lag age, processing rate, partition skew, rebalance count. Can stream consumers keep up with event history?
RabbitMQ Ready messages, unacked messages, redelivery rate, confirm latency. Is routed work being accepted, delivered, and completed?
Handlers Processing latency, idempotency conflicts, retry count, failed side effects. Are consumers safely applying updates?
Dead letters DLQ rate, oldest dead letter age, failure reason, owner. Is failed work visible and repairable?
Business output Source-to-projection freshness, audit diffs, missing update IDs. Did important updates reach the visible system state?

Answer Shape

When defending a messaging design:

  1. Start with the product promise and source of truth.
  2. Classify each message as history, work, command, notification, or projection update.
  3. Explain why the chosen broker contract fits that message.
  4. Name the ordering key, replay or retry path, and acknowledgement point.
  5. State the delivery semantics honestly, usually at-least-once plus idempotency.
  6. Describe poison-message handling and ownership.
  7. Close with freshness, lag, backlog, redelivery, DLQ, and reconciliation evidence.
