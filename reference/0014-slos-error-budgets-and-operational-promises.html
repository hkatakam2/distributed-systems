SLOs, Error Budgets, and Operational Promises

A compact checklist for turning user-visible behavior into SLIs, SLOs, error budgets, alerts, and engineering decisions.

The Recurring Shape

PromiseName the user journey and the behavior that must be reliable.
SLIDefine good events divided by eligible total events.
TargetChoose a threshold, objective percentage, and time window.
BudgetTranslate tolerated unreliability into allowed bad events.
ActionAlert, slow releases, mitigate, or invest based on burn.

Vocabulary

SLI: service level indicator; a quantitative measure of service behavior users care about.

SLO: service level objective; the target range or percentage for an SLI over a time window.

SLA: service level agreement; an external or contractual commitment, often with business consequences.

SLI specification: the behavior you intend to measure, independent of a telemetry source.

SLI implementation: the concrete measurement source, such as load balancer logs, client telemetry, traces, probes, or database checks.

Good event: an eligible user interaction, request, record, or view that satisfied the promised condition.

Total event: all eligible events that should be judged by this SLO.

Error budget: the tolerated amount of bad service during the SLO window.

Burn rate: how fast the service is consuming error budget relative to the planned rate.

Freshness SLI: the proportion of user-visible reads or records updated within an accepted age threshold.

Coverage SLI: the proportion of expected input records successfully processed within a target window.

Correctness SLI: the proportion of outputs that match an independent expectation or validation sample.

SLI Pattern Table

System shape Useful SLI form Common trap
Request API Good requests under latency threshold / eligible requests. Counting only server-side successes and missing client-visible failures.
Checkout write Correct commits or explicit valid rejects under deadline / eligible attempts. Treating every non-2xx response as bad when some rejects are correct product behavior.
Streaming projection User-visible fresh views / total projection views. Using Kafka lag alone when users care about visible state age.
Batch or stream pipeline Records processed correctly within window / expected records. Measuring worker health but not output coverage or correctness.
Storage system Writes later readable and intact / accepted writes. Reporting aggregate durability while the hot data users need is unavailable.
Graceful degradation Undegraded useful responses / eligible responses. Calling every HTTP 200 good even when the answer omits required data.

Formula Sheet

SLI = good events / total eligible events

bad event budget = total eligible events x (1 - SLO target)

observed bad rate = bad events / total eligible events

budgeted bad rate = 1 - SLO target

burn rate = observed bad rate / budgeted bad rate

remaining budget = allowed bad events - observed bad events

Example: 99.9% over 10,000,000 eligible requests allows 10,000 bad requests in the window. A 1% observed bad rate burns a 99.9% SLO at 10x because the budgeted bad rate is 0.1%.

Design Checklist

  1. Name the user group and user journey.
  2. State the product promise in plain language.
  3. Define eligible events: route, tenant, method, status class, or business action.
  4. Define what counts as a good event.
  5. Choose the threshold: latency, freshness age, correctness, coverage, or durability.
  6. Pick the window: rolling 7 days, rolling 30 days, calendar month, or another defensible period.
  7. Choose the SLI implementation and list its blind spots.
  8. Write the error budget policy before the first incident.
  9. Alert on fast budget burn; ticket slow burn; dashboard component causes for diagnosis.
  10. Review after incidents, major launches, and sustained mismatch between user pain and SLO status.

Budget Policy Table

Budget state Engineering posture Decision rule
Healthy budget Ship normally with standard rollout safety. Feature velocity is acceptable because reliability is inside the promise.
Fast burn Page, mitigate, shed load, roll back, or degrade deliberately. The service is spending too much budget too quickly to wait.
Slow burn Create a ticket, investigate trend, and plan reliability work. The SLO may be missed if the issue continues, but immediate paging may not help.
Budget exhausted Freeze risky launches, repay reliability debt, and review the policy. The team has already spent the unreliability it agreed users could tolerate.
SLO never burns Check whether the SLO is too loose, too hidden, or measuring the wrong journey. A silent SLO is not useful if users still feel pain.

Answer Shape

When defending SLO work:

  1. Start with the user promise, not the dashboard.
  2. Define the SLI as good events over eligible total events.
  3. Explain the threshold, window, and target as product tradeoffs.
  4. State the measurement source and what it misses.
  5. Translate the target into an error budget.
  6. Explain what happens during healthy budget, fast burn, slow burn, and exhausted budget.
  7. Connect symptoms to causes with traces, logs, database waits, cache hit rate, lag, and deployment history.
